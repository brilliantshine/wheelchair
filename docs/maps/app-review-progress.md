## Flow

1. The lead sets `ready-for-review` after planning. Each review round starts fresh reviewer sessions: two separate lenses when both families are configured, or one reviewer with both lenses when one family is configured. Later rounds examine changes plus whole-Spec coherence (`protocol/app/lead.md:169`, `:178-194`). Reviewers read IDEA and PLAN, check source, and return severity/lens/evidence lines as their last message; they cannot post cards (`protocol/app/reviewer.md:3-16`, `:48-58`). The lead triages every finding, stops reviewers, and repeats until clean; genuine decisions become questions, and three unclean rounds trigger a needs card. Round counts, summaries and findings otherwise stay out of the thread (`protocol/app/lead.md:196-225`). A clean round leads to approved status, Ready check and an approval card; a spec change returns to review (`protocol/app/lead.md:227-244`). The older slash-command stage separately specifies two reviewers even with one family; app roles replace that stage for app sessions (`protocol/plan-review.md:49-56`, `protocol/app/AGENTS.md:3-6`).
2. The sub-lead writes `implementing` first and posts task-count progress on dispatch and acceptance (`protocol/app/sub-lead.md:18`, `:91-95`, `:126-129`). After all tasks and full validation, it writes COMPLETION, commits `verifying`, and starts one or two verifiers according to configured families and builders (`protocol/app/sub-lead.md:161-182`). The verifier checks code and validation against the Spec and completion claims and reports commit plus PASS or evidence-backed gaps (`protocol/app/verifier.md:10-17`, `:19-28`, `:38-54`). On failure the sub-lead records gaps and remediation tasks, fixes and validates, then starts a fresh verifier; after the same gap survives two fix attempts it asks the lead and waits (`protocol/app/sub-lead.md:183-195`). On pass it reports to the lead, who writes `done` (`protocol/app/sub-lead.md:183-184`, `:197-198`; `protocol/app/lead.md:276`). The schema lists both `implementing` and `verifying` (`protocol/templates/PLAN.md:3`).
3. Progress accepts only integer `done` and `total`, string-array `machines`, and boolean `choice_waiting`; counts must satisfy 0 <= done <= total, unknown fields are rejected, and only lead/sub-lead can post it (`protocol/app/cards.md:123-134`; `viewer/app/card.js:28`, `:81-86`, `:119-139`). The hub validates again, assigns id/time, marks the previous singleton replaced and updates `thread.pinned.progress`; state is persisted in the thread (`viewer/app/cards.js:9-28`, `:38-48`, `:79-80`; `viewer/app/state.js:107-130`; `viewer/app/threads.js:20-32`). Chat returns unreplaced cards and pinned values; the page polls and renders a sticky, foldable pin labeled “Building”, task counts, optional machines, segments and choice indicator (`viewer/app/chat.js:204-231`; `viewer/pages/thread.js:573-588`, `:684-719`, `:800-810`; `viewer/pages/thread.css:23-38`, `:53-59`). The finishing protocol does not prescribe a new progress post during verification, so the last build pin can remain a completed task count (`protocol/app/sub-lead.md:161-198`; `viewer/app/cards.js:22-25`).
4. The hub records each session's role, starter, attempt, live/ready and waiting or starting state, and saves it in the thread (`viewer/app/sessions.js:126-136`, `:175-194`, `:455-472`). Turn-end extracts the final reviewer/verifier message, creates an internal result and marks `finished`; a separate stop marks `live` false (`viewer/app/sessions.js:257-276`, `:392-397`, `:502-514`). `/chat` includes public session records but only assembles lead transcripts (`viewer/app/chat.js:204-222`). Session state can signal an active reviewer or verifier without a new card, but alone cannot identify lead triage, preparation, remediation between verifier sessions, or distinguish a feature verifier from a fix verifier; verifier sessions are also started for small fixes (`protocol/app/lead.md:60-66`, `:102-104`; `protocol/app/sub-lead.md:185-195`). `live` can remain true after a report until stopped, and waiting starts are live, so `live` alone is not equivalent to active checking (`viewer/app/sessions.js:128-133`, `:257-271`, `:502-512`).
5. Features reads PLAN status from the worktree, falling back to cached `last_status`; `ready-for-review` and `approved` both group as Review, while implementing and verifying have separate groups (`viewer/app/views.js:11-18`, `:33-45`, `:98-118`). Features renders those groups; the Threads list obtains labels from `/features`, alongside a working dot based on the lead's turn state (`viewer/pages/features.js:7-14`, `:131-147`, `:174-181`; `viewer/pages/threads.js:11-17`, `:44-46`, `:97-100`, `:111-115`). Thus Review does not itself mean a reviewer is running and Verifying includes remediation.

```text
plan ready -> review sessions -> reports -> lead triage -> clean -> approval
                                        -> revise -> fresh round
build tasks -> completion + verifying -> verifier report -> pass -> lead
                                                   -> gaps -> fixes -> fresh verifier
progress card -> validate -> replace pin -> saved thread -> chat -> Building pin
PLAN status -> features groups -> Features page + Threads list
session start -> recorded state -> report finished -> stop -> recorded state
```
