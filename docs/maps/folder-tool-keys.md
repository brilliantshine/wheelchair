# Map: folder tools and key boundaries

Checked against: `6802372cdc5c1af28742818c90732cd3a83d4f3c` (origin/main). Files covered: `machine/lib/folder-tools.js`, `machine/lib/tool-run.js`, `machine/lib/tool-bridge.js`, `machine/lib/tool-launch.js`, `machine/lib/mcp-stdio.js`, `machine/lib/shared-tools.js`, `machine/lib/project-keys.js`, `machine/lib/project-tools.js`, `machine/lib/env-launch.js`, `machine/lib/screen.js`, `machine/lib/win.js`, `machine/service.js`, `viewer/app/tool-cli.js`, `viewer/app/wc.js`, `viewer/app/routes.js`, `viewer/app/sessions.js`, `viewer/pages/settings.js`, `viewer/pages/project-tools.js`, `connectors/{claude,codex,agy,kimi,pi}/machine.js`, `connectors/{claude,codex,agy,kimi,pi}/manifest.js`, `connectors/common.js`.

```text
Settings selects shared repo and project keys -> machine stores project keys
session starts -> discover project and pinned shared folders -> provider config
  -> MCP bridge or server launcher -> child process -> output to agent
  -> sandboxed Codex, Kimi, Pi: shell runs script through wc.js
```

Folder discovery reads `.wheelchair/tools/*/tool.json` (32 KiB maximum), validates matching names, one-line description, script inputs/run/timeout or server start; it ignores unknown fields, so a `keys` field currently has no effect. Project names hide shared names even if the project entry is invalid; executable presence is checked (`machine/lib/folder-tools.js:7`, `machine/lib/folder-tools.js:39`, `machine/lib/folder-tools.js:60`). The shared repo is chosen in Settings, resolved to a local saved project, fetched at its default-branch tip into a read-only per-commit copy with a 20-second deadline; sessions retain their pinned copy, and the shared project's own worktree skips the copy (`viewer/pages/settings.js:2398`, `machine/service.js:971`, `machine/lib/shared-tools.js:104`). `.mcp.json` names win over folder entries (`machine/service.js:991`).

The service offers one `wheelchair-tools` stdio bridge for scripts and a launcher per server, using empty config env objects (`machine/lib/folder-tools.js:70`, `machine/service.js:995`). The bridge revalidates its offered script before each call; it sends JSON on stdin, returns stdout or error stderr, and the launcher pipes a server's stdio (`machine/lib/tool-bridge.js:10`, `machine/lib/tool-run.js:10`, `machine/lib/tool-launch.js:26`). Both use `toolEnv`, which removes only the session token and adds `WHEELCHAIR_PROJECT_DIR`; inherited project keys therefore remain visible to folder tools (`machine/lib/tool-run.js:5`). Script output currently has no arbitrary-key redaction: stdout capture stops at 2 MiB and returned text is cut at 1 MiB; stderr retains its last 4 KiB (`machine/lib/tool-run.js:16`).

Claude adds folder entries to a per-session `--mcp-config` alongside native project MCP loading (`connectors/claude/machine.js:75`). Codex makes `project_` overrides, first budgets `.mcp.json`, then adds folder entries within its limit; sandboxed sessions get none (`connectors/codex/machine.js:52`, `connectors/codex/machine.js:161`). Gemini's Antigravity connector writes a per-session plugin `mcp_config.json` (`connectors/agy/machine.js:37`). Kimi and OpenRouter's Pi do not load project MCP entries and warn for server tools (`connectors/kimi/machine.js:311`, `connectors/pi/machine.js:138`).

`wc.js tool` resolves the authenticated session's worktree and pinned copy from `/v1/agent/tools`, or the local Git root without a token. `new` copies templates and refuses existing folders; `list` discovers; `check` validates and starts servers for a handshake with a shared 30-second deadline; `run` starts scripts locally with JSON input. Both `check` and `run` use the caller's inherited environment through `toolEnv`, not a machine-side execution route (`viewer/app/tool-cli.js:9`, `viewer/app/tool-cli.js:30`, `viewer/app/tool-cli.js:45`, `viewer/app/tool-cli.js:52`, `viewer/app/tool-cli.js:83`, `machine/service.js:2377`). The Tools page lists folder status and source after a machine read of the default branch and shared copy (`machine/lib/project-tools.js:80`, `viewer/pages/project-tools.js:313`).

Project keys are edited on the project Tools page for a selected machine and project, with key names returned to the page (`viewer/pages/project-tools.js:142`, `viewer/pages/project-tools.js:252`, `machine/lib/project-tools.js:156`, `machine/lib/project-tools.js:181`). Their store is under `~/.local/state/wheelchair/project-keys/`, keyed by a hash of the real Git common directory; the directory is created mode 0700 and atomic temporary JSON files mode 0600 (`machine/service.js:47`, `machine/lib/project-keys.js:42`, `machine/lib/project-keys.js:59`). These modes do not isolate another process running as the same OS user.

At each launch, only Claude and Codex have `injectProjectKeys` enabled (`connectors/claude/manifest.js:136`, `connectors/codex/manifest.js:144`, `connectors/agy/manifest.js:114`, `connectors/kimi/manifest.js:111`, `connectors/pi/manifest.js:107`). The machine selects stored names referenced in `.mcp.json` env or HTTP headers, withholding names also referenced in command, arguments or URL; it writes a mode-0600 session env file and puts `env-launch` before the agent command (`machine/lib/project-keys.js:15`, `machine/lib/project-keys.js:71`, `machine/service.js:1064`, `machine/service.js:1100`). The launcher reads and unlinks that file, merges values into the agent environment, and execs or spawns the CLI (`machine/lib/env-launch.js:6`). This is an agent-env injection, including on Codex, and is separate from folder-entry config generation.

Codex normally starts with workspace-write and network access; reviewer is read-only, unrestricted mode bypasses sandbox (`connectors/codex/machine.js:158`). A session token authenticates agent routes to the machine, including folder-root lookup (`machine/service.js:585`, `machine/service.js:2290`, `machine/service.js:2377`); the server can therefore be asked to do work outside the caller's sandbox if an agent route grants that capability. The screen launcher wraps sandboxed commands with `codex sandbox`; Windows bridge run/start instead refuses them (`machine/lib/screen.js:215`, `connectors/codex/machine.js:125`, `machine/lib/win.js:447`). Same-user store permissions are not a defense against unsandboxed local agents; exact sandbox read/network reach depends on the Codex runtime and platform, not established here.

The existing general scrubber and Pi connector redact OpenRouter-shaped `sk-or-...` strings, including captured panes, and Codex masks project overrides in the recorded command; these are not a general stored-key output redactor (`connectors/common.js:26`, `connectors/pi/machine.js:9`, `machine/service.js:608`, `machine/service.js:1102`). Server tools pass their MCP output directly (`machine/lib/tool-launch.js:26`).

Not looked at: live Codex sandbox behavior on each OS, external MCP server implementations, every transcript and log sink, and unrelated portions of the historical maps.
