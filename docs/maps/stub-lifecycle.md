# Map: stub lifecycle and discovery

Checked against: `7204dd2af8986aa1cdbca73f6b98c25d0fc26095` (origin/main). Files covered: `viewer/app/card.js`, `viewer/app/cards.js`, `viewer/app/threads.js`, `viewer/app/state.js`, `viewer/app/peers.js`, `viewer/app/wc.js`, `viewer/app/sessions.js`, `viewer/app/routes.js`, `viewer/app/hub.js`, `viewer/app/handoff.js`, `viewer/app/chat.js`, `viewer/pages/thread.js`, `viewer/pages/threads.js`, `protocol/app/lead.md`, `protocol/app/cards-lead.md`, `protocol/app/cards.md`, `viewer/test/app-hub.test.js`, `viewer/test/app-lead-list.test.js`, `viewer/test/app-threads.spec.js`, `viewer/test/wc-cli.test.js`.

```text
lead posts stub -> validate and store card -> save child thread with context
                                               -> unopened: wait or open
                                               -> open: queue context for lead
lead lists peers -> same machine and project + prior lead -> peer fields
```

- A lead writes title, summary, dependency and optional commits; `card.js` rejects unknown or invalid fields and other roles cannot post a stub (`protocol/app/cards-lead.md:238`, `viewer/app/card.js:45`, `viewer/app/card.js:170`, `viewer/app/card.js:198`). The CLI posts to the machine, whose authenticated hub card route calls `acceptCard`; the hub validates again, rejects archived/frozen parents and deduplicates delivery IDs, then stores a card and creates a child (`viewer/app/card.js:304`, `viewer/app/routes.js:457`, `viewer/app/cards.js:56`, `viewer/app/cards.js:168`, `viewer/app/cards.js:192`). Delivery-ID deduplication is not content deduplication.
- `createStub` copies project and machine, stores summary as child `context`, parent ID/title, dependency and commits, and attaches the child ID to the parent card (`viewer/app/threads.js:93`). The child and parent card are separate stored records; state reads JSON thread files and sorts by `updated_at` (`viewer/app/state.js:161`, `viewer/app/state.js:194`). The card documentation promises the same CLI, but creation does not copy `cli`; a test confirms the opened lead follows configured lead order instead (`protocol/app/cards-lead.md:249`, `viewer/app/threads.js:93`, `viewer/test/app-hub.test.js:691`).
- Opening a dependent child without `ready` or `start_now` saves `waiting_on_parent`; otherwise it starts a lead and queues `[wc:context stub]` plus commit IDs (`viewer/app/threads.js:109`, `viewer/app/routes.js:666`). The merge poll watches dependent, unarchived children without sessions, whether or not explicitly opened, and sets `ready` after the parent's branch has a merged PR (`viewer/app/threads.js:494`). The marker is hidden in chat, replaced with a parent attribution; restart supplies current `context` as `stub_summary` (`viewer/app/chat.js:125`, `viewer/app/threads.js:138`, `protocol/app/cards.md:190`).
- `session leads` sends a machine session request; the hub permits only leads and `listLeads` requires the same resolved machine and, for same-project entries, a prior lead. It excludes archived and frozen threads, includes linked cross-project threads, and exposes no stub context (`viewer/app/wc.js:71`, `viewer/app/sessions.js:670`, `viewer/app/peers.js:6`, `viewer/app/peers.js:41`). Thus unopened same-project stubs are absent; opened stubs retain `stub: true` and can appear after a lead exists (`viewer/app/threads.js:93`, `viewer/app/threads.js:109`).
- The list page marks only unopened stubs and shows waiting/ready, not context; its lean response explicitly drops `context` (`viewer/pages/threads.js:43`, `viewer/app/routes.js:488`). The child page displays `context` only while unopened and unarchived and includes it in its rerender signature; the parent card displays its own `summary`, not the child context (`viewer/pages/thread.js:522`, `viewer/pages/thread.js:1219`, `viewer/pages/thread.js:1434`). Updating context alone would not update the original card or deliver a new message to an already-started lead; opening enqueues a string snapshot (`viewer/app/threads.js:118`, `viewer/app/cards.js:168`).
- A stub can be unopened, waiting, ready, opened with a live or dead lead, archived, handed off/frozen, or have its own merged PR; these are separate fields/events, not one stub state (`viewer/app/threads.js:109`, `viewer/app/threads.js:199`, `viewer/app/threads.js:463`, `viewer/app/handoff.js:88`). Archive and frozen threads are excluded from lead discovery; handoff export rejects archived and merged/closed work (`viewer/app/peers.js:11`, `viewer/app/handoff.js:122`).
- Coverage: creation, start, waiting, merged-parent polling, commits and restart context are exercised in `viewer/test/app-hub.test.js:667`, `:710`, `:728`, `:1534`, `:2198`; discovery filters and role gate in `viewer/test/app-lead-list.test.js:10`; CLI request in `viewer/test/wc-cli.test.js:66`; list/card/open UI in `viewer/test/app-threads.spec.js:114`, `:485`, `:614`.
