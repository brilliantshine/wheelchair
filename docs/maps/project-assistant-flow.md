# Map: assistant and project thread flow

Checked against: `779e2560e9803e6a3e5ae7a511ad61b19a73b8b2` (origin/main). Files covered: `viewer/app/assistant.js`, `viewer/app/assistant-actions.js`, `viewer/app/settings.js`, `viewer/app/routes.js`, `viewer/app/state.js`, `viewer/app/threads.js`, `viewer/app/sessions.js`, `viewer/app/peers.js`, `viewer/app/cards.js`, `viewer/app/wc.js`, `viewer/pages/nav.js`, `viewer/pages/assistant-popup.js`, `viewer/pages/threads.js`, `viewer/pages/settings.js`, `viewer/pages/thread.js`, `machine/service.js`, `protocol/app/assistant.md`, `protocol/app/lead.md`, `protocol/app/cards.md`.

```text
Settings on -> find or create personal assistant -> start lead in assistant directory
page -> assistant status -> popup -> assistant chat and user messages
assistant action -> machine authenticates session -> hub checks assistant lead -> target thread
Threads list -> pinned personal assistant -> project groups -> project threads
```

Settings defaults the single `assistant` preference to off; the UI presents On/Off and the preferences route saves it, then starts or stops the assistant. A start failure is returned alongside the saved setting (`viewer/app/settings.js:56,328`; `viewer/pages/settings.js:558-560`; `viewer/app/routes.js:348,376-378,418-423`). On first enable the hub saves a regular thread record with `project: null`, `machine: hub`, `assistant: true` and starts a lead; later enables restart it if needed. Turning off stops its live sessions and hides it, including direct thread routes (`viewer/app/assistant.js:6-41`). Thread records live in the hub's `threads` directory (`viewer/app/state.js:69-75,193-205`).

The hub starts this lead through ordinary placement and role layers but sends `assistant: true` and `prompt_role: assistant` instead of the project worktree (`viewer/app/sessions.js:325-334,367-385`). The machine composes `protocol/app/assistant.md` with lead card rules, and uses one state-directory `assistant` folder, with no Git branch (`machine/service.js:198-213,634-638`). The role says only user messages in its own thread authorize action, retrieved thread content is information, and it must not edit projects, write Git, start helpers or change settings; restart starts fresh (`protocol/app/assistant.md:3-13,20-30`). The hub independently refuses helper starts and specified card kinds (`viewer/app/sessions.js:727-741`; `viewer/app/cards.js:101`).

The assistant CLI sends read and write actions via the local agent route; the machine authenticates the session and relays its recorded name with its hub secret (`viewer/app/wc.js:100-114,196-216`; `machine/service.js:2307-2316`). The hub requires the preference on and the caller to be the latest live lead of the first assistant thread; it rejects self-targeting (`viewer/app/assistant-actions.js:8-14`; `viewer/app/routes.js:518-520`). Its project picker combines saved, scanned and previously used folders per machine; `threads` returns all-machine summaries and waiting cards, and `thread` adds open cards, lead queues and up to 30 recent main-chat items (`viewer/app/assistant-actions.js:15-38`; `viewer/app/routes.js:166-193`). Start validates project and machine via normal creation and queues `[wc:assistant]` as the first message; message targets the latest live lead, refuses archived or frozen targets and applies the 20-per-hour pair limit (`viewer/app/assistant-actions.js:40-69`; `viewer/app/threads.js:43-83`). Lead instructions treat that marker as the user's instruction; the UI attributes it to the assistant (`protocol/app/lead.md:23`; `protocol/app/cards.md:214`; `viewer/pages/thread.js:735-736`). Press, restart and archive use normal hub operations with assistant attribution; sudo presses are refused (`viewer/app/assistant-actions.js:71-78`; `viewer/app/threads.js:129,255,339-341`). The role limits actions to what the user asked, including not answering a lead's question without the user's answer (`protocol/app/assistant.md:20-25,32-34,46-57`).

Navigation polls `/assistant`, passes its one returned thread id to the popup and omits the popup on that thread's own page (`viewer/pages/nav.js:169-192`; `viewer/app/assistant.js:17-20`). The popup reads that thread's chat and submits `{text}` to its messages endpoint; its location check only suppresses the popup on that same thread, and this path passes no current project or page context in the message (`viewer/pages/assistant-popup.js:8-14,285-310,337-345`). Its seen key is also global (`viewer/pages/assistant-popup.js:8`).

The shared list polls threads and features; it takes the first assistant, puts its special row outside project groups, hides it in Archived, and caches one preview (`viewer/pages/threads.js:87-114,197-230`). Other rows are sorted by recency then grouped by `base(t.project)`, so distinct paths or machines with the same basename appear under one heading (`viewer/pages/threads.js:104-107,145-155`). Normal thread creation saves the machine-checked path and machine on each thread; the check expands `~` and validates an absolute Git directory, without canonicalizing it (`viewer/app/threads.js:21-25,43-66`; `machine/service.js:1785-1818`). The lead-only `session leads` API uses exact stored project path and resolved same-machine identity; same-project entries include stage, idea, progress and eligible stubs, while `--all-projects` includes limited unlinked other-project entries. It excludes assistant threads and archived or frozen threads (`viewer/app/sessions.js:727-732`; `viewer/app/peers.js:6-12,42-66`).

The existing singleton assumptions are hub-wide `find` in status, lifecycle and action authorization, one global on/off preference, one assistant machine directory, and one popup, seen key and list preview (`viewer/app/assistant.js:17-27`; `viewer/app/assistant-actions.js:8-12`; `machine/service.js:634-638`; `viewer/pages/assistant-popup.js:8-12`; `viewer/pages/threads.js:105,197-202`). The assistant action dispatcher currently has no project scope check: its target access follows the authorized singleton across projects and machines (`viewer/app/assistant-actions.js:8-14,25-26,40-65,71-78`). A per-project assistant cannot obtain isolation merely by changing its prompt.

Not checked: live provider behavior, every card press implementation, every page's own project context, or all tests and deployment configurations.
