```text
plan validation and completion -> independent verifier -> lead pushes PR
                                                   -> GitHub readiness -> done card
                                                   -> thread rendering -> handoff history
```

1. A small fix has no plan: the lead commits, gets independent verification, pushes and opens a PR. For a feature, after the sub-lead's result and stop, the lead commits PLAN status `done`, pushes and opens a PR. An after-done fix on an open PR is committed, verified and pushed, then gets another done card; merged work becomes a stub and a closed PR is left alone (`protocol/app/lead.md:112-122,390-399,411-439`). The lead waits for PR readiness, handles changed heads, failures and conflicts, and supplies the pushed remote tip as `head`; a timeout or login refusal leads to a needs card (`protocol/app/lead.md:444-505`).
2. Done is lead-only and shown, with required `title`, `can_do`, `left_as_is`, `pr_url`, 40-character lowercase hex `head`, and optional `note`; both arrays may be empty. Unknown fields fail validation (`viewer/app/card.js:10-23,25-34,45-48,125-132,160-175,204-207`; `protocol/app/cards-lead.md:121-134`). The CLI validates and posts to the machine; unlike other cards, done is forwarded synchronously and never spooled, so an unreachable hub or backlog fails (`viewer/app/card.js:261-280`; `machine/service.js:1570-1586`).
3. The hub validates the role and schema, checks GitHub before taking the thread lock, then accepts and stores under the lock (`viewer/app/hub.js:167-178`; `viewer/app/cards.js:11-34,51-62`). The gate requires a GitHub PR URL and checks branch, base and exact head, accepts a matching merged PR or an open PR with `CLEAN`, `HAS_HOOKS`, or `BLOCKED` without failed/pending checks; it rejects conflicts, behind, failed/pending checks in blocked/unstable states, unknown state and lookup errors (`viewer/app/pr-gate.js:8-43`). The lead's wait protocol additionally waits five minutes when a ready PR has no checks; this delay is not in the acceptance gate (`protocol/app/lead.md:451-465`; `viewer/app/pr-gate.js:13-28`).
4. Chat returns stored non-replaced cards and pins; done is not a singleton or pin. The page renders title, optional note, each can-do and left-as-is item with a start-thread button, and a PR link; head is not displayed (`viewer/app/cards.js:9-34`; `viewer/app/chat.js:277-282`; `viewer/pages/thread.js:805-834`). A press sends `start-thread` and its item text to the lead, records the answer and requires a live lead (`viewer/pages/thread.js:519-525,813-824`; `viewer/app/threads.js:309-314,358-386`). The list API separately flags any non-replaced done card (`viewer/app/routes.js:439-441`).
5. Handoff flattens a done card into text containing title, can-do, left-as-is and PR URL; it omits note and card head. It retains history as text, truncates long entries, and validates a fixed kind set and schema; its top-level head is the exported branch head (`viewer/app/handoff.js:3-5,18-30,34-46,55-70`). A new field would need explicit history serialization to survive; a new kind also needs its kind allowlist and `historyText` handling (`viewer/app/handoff.js:5,28-30,34-46,62-66`).
6. A new shown kind needs a schema, authorized roles and shown membership (`viewer/app/card.js:10-43,73-153,160-175`); rendering is a `renderCard` case (`viewer/pages/thread.js:601,805-835`). Pins additionally use the hub singleton/approval storage and the page's pinned ordering (`viewer/app/cards.js:9-32`; `viewer/pages/thread.js:8,956-977`). Buttons call the page press helper; the hub maps accepted actions into lead messages, with special restrictions for some kinds (`viewer/pages/thread.js:519-525`; `viewer/app/threads.js:309-369,386-387`). The shared kind table and press forms and lead-only field contract are in `protocol/app/cards.md:20-49,154-166` and `protocol/app/cards-lead.md:121-136`.
7. The plan template calls for concrete validation commands in the Spec (`protocol/templates/PLAN.md:44-48`). The sub-lead runs full validation, records per-item coverage, evidence and residual risks in COMPLETION, then sends that and PLAN to verifier(s); on pass its result names COMPLETION and the verified commit (`protocol/app/sub-lead.md:213-242`). Verifiers independently read code, run available commands and check intent, non-goals and small-fix regressions; their final report names commit, verdict, evidenced gaps and optionally commands run (`protocol/app/verifier.md:13-20,29-31,33-50,52-76`). These are engineering evidence, not an existing prescribed user walkthrough. For example, plan-modes lists Node and browser commands and expected tests (`docs/plans/plan-modes/PLAN.md:456-469`); its COMPLETION records coverage, test results, a read-through and risks (`docs/plans/plan-modes/COMPLETION.md:12-20,80-100`).

Tests: gate identity, readiness, invalid inputs, lookup failures and lock behavior are in `viewer/test/app-done-gate.test.js:17-77`; browser done rendering, PR link and both start-thread buttons are in `viewer/test/app-threads.spec.js:435-498`; handoff text and validation are in `viewer/test/app-handoff.test.js:9-28`; list flag is in `viewer/test/app-thread-list.test.js:28-44`.
