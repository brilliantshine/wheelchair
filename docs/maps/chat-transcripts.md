# Map: chat transcripts

Checked against: `899afb69395ed5dddc5828ae86bad1fd3e765947` (origin/main; covered files match this worktree).
Files covered: `viewer/app/chat.js`, `viewer/app/hub.js`, `viewer/app/state.js`, `viewer/app/sessions.js`, `viewer/app/routes.js`, `viewer/app/machine-client.js`, `viewer/pages/thread.js`, `viewer/pages/nav.js`, `machine/service.js`, `machine/API.md`, `viewer/test/app-handoff.test.js`, `viewer/test/app-asides.test.js`, `viewer/test/app-chat.test.js`, `viewer/test/helpers/app-machine.js`, `machine/test/service.test.js`.

```text
visible thread page -> chat route -> thread lock -> lead transcript requests -> parse and assemble
                                                   -> machine copies source -> kept file -> full reply
                                                   -> failed or empty reply -> cached text -> local path
```

The thread page calls chat immediately and every 2 seconds, skips overlapping polls, and pauses timer ticks when hidden; showing the tab triggers another poll (`viewer/pages/thread.js:7`, `viewer/pages/thread.js:1146`, `viewer/pages/thread.js:1227`, `viewer/pages/nav.js:3`). The route calls `hub.chat`; it holds the per-thread promise queue through chat assembly and slug discovery, and refreshes handoff status outside that lock (`viewer/app/routes.js:518`, `viewer/app/hub.js:115`, `viewer/app/hub.js:250`). A gated test proves a thread mutation waits for a transcript request (`viewer/test/app-handoff.test.js:373`).

Under that lock chat reads a snapshot, fetches each lead session sequentially, parses each nonempty transcript on every poll and combines it with current cards, settings and parent state (`viewer/app/chat.js:318`). The parser depends on CLI, session name and `thread.parent_title` (`viewer/app/chat.js:130`, `viewer/app/chat.js:240`, `viewer/app/chat.js:265`). The separate thread-file cache stats `(mtimeMs, ctimeMs, size, ino)`, reuses only settled entries, deep-freezes parsed records and invalidates on saves; mutable reads remain disk reads (`viewer/app/state.js:10`, `viewer/app/state.js:110`, `viewer/app/state.js:139`). Chat and parent use `readSnapshot`, which can migrate an old provider via mutable read (`viewer/app/chat.js:319`, `viewer/app/chat.js:337`, `viewer/app/hub.js:139`).

`sessionTranscript` keys a lazily created, unbounded map by machine/session and saves every nonempty machine `data`, including report reads. Chat falls back to that text on error or empty data, then reads the legacy local `session.transcript_path`; report reads skip the cached fallback but still try the local path (`viewer/app/chat.js:271`). The only other hub caller is reviewer/verifier report delivery, which first prefers the event's last assistant message and otherwise reads the transcript and extracts the last assistant text, with Kimi turn selection (`viewer/app/sessions.js:428`, `viewer/app/chat.js:244`, `viewer/app/chat.js:290`). This distinction is tested (`viewer/test/app-chat.test.js:362`).

The machine client forwards the URL and secret, defaults to a 5-second timeout, returns parsed JSON or throws for non-2xx (`viewer/app/machine-client.js:10`, `viewer/app/machine-client.js:62`). The machine authorizes the hub and accepts `offset` only, ignoring other query parameters; current hub sends none (`machine/service.js:1917`, `machine/service.js:1929`, `viewer/app/chat.js:282`). The response is `{offset, data}` with byte-sliced data, even though obtaining it reads the full kept file; missing managed copies return empty data, archived sessions use their kept file, and unknown sessions without one fail (`machine/service.js:1228`). An older machine therefore ignores a proposed `known` query and returns the legacy full response; an older hub continues sending the legacy request. There is no transcript capability negotiation in these paths. The separate Ready check compares service and hub commits, but is not called by this read (`viewer/app/ready.js:11`, `viewer/app/chat.js:278`).

For a managed session, the machine binds a source if needed and serializes copies per session; hooks also invoke the same copy (`machine/service.js:1193`, `machine/service.js:1238`, `machine/service.js:1307`). Copy resets the source offset on path, inode or shrink changes (Kimi additionally validates its bound device/inode); it copies only complete newline-terminated records (`machine/service.js:1204`). It rereads `transcripts/<thread_id>/<session>.jsonl`, hashes every kept line and deduplicates new lines before appending; it then updates source offset and atomically rewrites the entire `sessions.json` even with no additions (`machine/service.js:1217`, `machine/service.js:1225`, `machine/service.js:224`, `machine/service.js:488`). The response then rereads the kept file (`machine/service.js:1243`). Source disappearance retains the kept copy (`machine/service.js:1239`, `machine/test/service.test.js:430`); archived copies remain readable (`machine/test/service.test.js:554`). Offset alone is not a generation or continuity check (`machine/service.js:1236`, `machine/service.js:1245`).

The literal `route.endsWith('/transcript')` test stubs in asides and handoff will not match a query suffix (`viewer/test/app-asides.test.js:133`, `viewer/test/app-handoff.test.js:377`); the fake HTTP machine matches `url.pathname`, so query strings do not break its route match, but it always returns legacy data (`viewer/test/helpers/app-machine.js:125`). Copy tests cover shrink deduplication, incomplete lines and concurrent copies (`machine/test/service.test.js:259`, `machine/test/service.test.js:412`, `machine/test/service.test.js:421`).
