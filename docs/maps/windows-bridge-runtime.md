# Map: Linux runtime boundaries for a Windows bridge

Checked against: `dbdc97c540f8c9226a3d0762bdd6fe9b548b9ecf` (origin/main and worktree HEAD).
Files covered: `machine/service.js`, `machine/API.md`, `machine/lib/screen.js`, `machine/lib/screen-input.js`, `machine/lib/screen-args.js`, `machine/lib/project-mcp.js`, `machine/lib/project-tools.js`, `machine/lib/project-programs.js`, `machine/lib/project-keys.js`, `machine/lib/env-launch.js`, `machine/adapters/`, `viewer/app/wc.js`, `viewer/app/state.js`, `viewer/app/threads.js`, `viewer/app/sessions.js`, `viewer/app/machine-client.js`, `viewer/app/cards.js`, `viewer/app/card.js`, `viewer/app/routes.js`, `viewer/pages/thread.js`, `install.sh`, `install/`, `README.md`, `machine/test/`, `viewer/test/`.

```text
pick machine and project -> hub starts session -> Linux worktree and CLI
  -> agent command -> session-token machine route -> Linux screen or git
  -> screenshot file -> image card -> machine upload -> hub -> browser
```

The hub validates the project on the chosen machine, saves that machine on the thread, and starts its lead there; later session starts send the thread's machine, project and worktree information to that machine (`viewer/app/threads.js:21-25,43-78`; `viewer/app/sessions.js:357-383`). The registry is `machines.json`; `hub` resolves to the local machine's matching host and port (`viewer/app/state.js:68,203-219`). The machine client uses HTTP and a machine-secret header, with address and port from that registry (`viewer/app/machine-client.js:56-75`). Install creates the local entry and a mode-600 secret, selecting a Tailscale IPv4 address or loopback (`install.sh:143-173`). This registry represents agent-running machines; these paths do not establish a Windows companion or its relationship to one.

The hub generates a session token and includes it in the machine start request (`viewer/app/sessions.js:329-334,357-364`). The machine makes or selects a worktree; workers get separate branch worktrees and verifiers detached worktrees (`machine/service.js:554-589`). It reads project tools, constructs the adapter command, and launches tmux in the worktree with `WHEELCHAIR_SESSION_TOKEN`, machine origin, state directory and account environment (`machine/service.js:767-783,820-838`). Agent routes authenticate that token against the recorded session using a timing-safe comparison; recovered sessions have no token. Hub routes require the separate machine secret (`machine/service.js:477-489,501-514,2043-2046`). `wc.js` builds fixed git/session/screen requests and POSTs with the session token to the machine origin; screen arguments are sent as an operation and array (`viewer/app/wc.js:13-34,47-68,70-103,163-179`).

Screens are Linux-only and reviewer-denied, validated and serialized per session (`machine/lib/screen.js:233-239`; `machine/lib/screen-args.js:3-5,25-86`). The manager starts Xvfb with Xauthority in a systemd user scope; launches in the session worktree, removes the session token from the app environment, and applies Codex's sandbox where configured (`machine/lib/screen.js:140-160,186-203`). Input uses X tools; screenshots are numbered PNGs, and status reports running/exited, log and PID, not a process exit code (`machine/lib/screen.js:249-267`; `machine/lib/screen-input.js:32-80`). Launch checks for handover and reports failure if it never occurs; success means handover, not eventual application success (`machine/lib/screen.js:209-231`). Stop, session death and archive have screen lifecycle cleanup (`machine/lib/screen.js:74-112`; `machine/service.js:1183-1189`).

For image cards, the agent supplies an absolute machine-side image path. The machine verifies type, regular file and 25 MB limit and copies it into thread uploads before posting the card (`viewer/app/card.js:148`; `machine/service.js:353-370,1991-2005`). The hub stores the uploaded basename, its file route streams from the thread's machine, and the page displays that file (`viewer/app/cards.js:133`; `viewer/app/routes.js:549`; `viewer/pages/thread.js:1062-1065`). A Windows-only path is therefore insufficient unless the machine can read the image or receives a local copy.

At startup `.mcp.json` is read from the worktree, capped at 32 KiB, and validates stdio, HTTP and SSE entries; tool roles are lead, sub-lead, worker and verifier (`machine/lib/project-mcp.js:8,69-105`). Claude enables accepted project entries through settings; Codex translates supported entries to command-line overrides, Antigravity writes a session plugin and points `agy` at it, and Kimi warns that project tools are unsupported (`machine/adapters/claude.js:63-74`; `machine/adapters/codex.js:31-93,124-130`; `machine/adapters/agy.js:31-67`; `machine/adapters/kimi.js:127-128`). Adapters differ in transport, expansion and header support; the shared reader alone does not guarantee a server will run. Project tools settings read and save the repository's `.mcp.json` via a GitHub PR (`machine/lib/project-tools.js:36-79,90-140`). For project stdio programs, the machine checks Linux executable paths relative to the worktree or colon-separated tmux PATH, not a Windows execution environment (`machine/service.js:670-681,776-783`; `machine/lib/project-programs.js:6-31`). Project key references for Claude/Codex can be injected through a temporary mode-600 environment file and launcher (`machine/service.js:803-820`; `machine/lib/env-launch.js:1-20`).

The Windows README explicitly calls WSL2 untested, requires systemd, advises Tailscale inside WSL and projects under the Linux home rather than `/mnt/c`, and describes keeping WSL alive (`README.md:63-87`). The installer chooses Linux or Darwin service setup and sets a Linux service PATH (`install.sh:233-237,373-406`); the searched runtime/install files contain no WSL-specific path translation or PowerShell interop handling (`README.md:63-87`; `machine/lib/project-programs.js:17-27`). This does not establish that WSL interop works in the service environment.

Validation entry points: `bash machine/test/run.sh` runs the machine `*.test.js` suite (`machine/test/run.sh:1-3`), including `screen*.test.js`, `project-mcp*.test.js`, `project-programs.test.js`, `project-tools*.test.js`, and `service.test.js`; `machine/test/screen-live.sh` is a separate live X-screen check (`machine/test/screen-live.sh:1-6`). `node --test viewer/test/*.test.js` includes `wc-screen.test.js`, `wc-cli.test.js`, machine and project-tools tests; browser coverage is `npm --prefix viewer run test:browser` (`viewer/AGENTS.md:45-50`). Installer fixtures run with `bash install/test/run.sh` (`install/test/run.sh:1-12`).

Not checked: live WSL or Windows, Tailscale deployment, Windows APIs or Unity/MCP vendor behavior, every archive failure and adapter edge case, and tests outside the named suites. Historical overlapping maps changed against origin/main and were not treated as current evidence.
