# Map: Windows stdio tools and copy lifecycle

Checked against: `87923e582b9b68a125ec2c34cbdcb321bd45a23d` (origin/main and HEAD). Files covered: `machine/service.js`, `machine/lib/win.js`, `machine/lib/win-apps.js`, `machine/lib/win-sync.js`, `machine/lib/project-mcp.js`, `machine/lib/project-programs.js`, `machine/adapters/{common,claude,codex,agy,pi}.js`, `machine/test/{win.test,win-service.test,win-launch.test,win-apps.test,project-mcp.test,project-mcp-codex.test}.js`, `docs/plans/windows-bridge-solid/PLAN.md`.

```text
.mcp.json -> validate -> adapter builds loaded entries -> ready copy and reconcile
                                                      -> 45 s deadline -> CLI starts
CLI starts Windows tool -> tool writes copy -> session ends -> final sync when eligible
```

The machine reads the worktree config, builds the adapter once, and decides `windowsTools` from its actual `loaded` list; it writes adapter files, waits for readying and then starts tmux (`machine/service.js:832-853,889-923`). Windows detection requires an `.exe` under a drive under the configured mount or `/mnt`, not any executable ending in `.exe` (`machine/lib/project-programs.js:16-21`).

Claude reads `.mcp.json` itself: the adapter enables accepted entries and disables rejected names, so changing the command needs an alternate config route rather than editing a translated entry (`machine/adapters/claude.js:63-68`). Codex builds per-entry `-c` overrides, including command, args and env; same-name env references become passthrough, and Windows entries explicitly pass `WHEELCHAIR_WINDOWS_PROJECT` and `WSLENV`; its size budget can drop all overrides (`machine/adapters/codex.js:55-60,75-100,131-143`). Antigravity translates stdio command, args and env into a per-session plugin config, dropping same-name env references and rejecting other substitutions (`machine/adapters/agy.js:31-67`; `machine/service.js:854-871`). Pi returns no loaded project tools (`machine/adapters/pi.js:61`). The service adds the Windows project path and appends its name to `WSLENV` for WSL tool roles; the environment lookup shares the 45-second launch budget and can return no variables if it times out (`machine/lib/win.js:362-369`; `machine/service.js:889-900`).

Readying is keyed by worktree, shared among concurrent starts, and creates then reconciles the copy; failures are caught and stored in memory, and the 45-second race lets launch continue while the task runs (`machine/lib/win.js:133-143,153-198`). `info` reports ready from the in-memory task and error maps plus the Windows version check; `.git` existence alone is not evidence that a post-start reconcile succeeded (`machine/lib/win.js:58-60,171-185,373-380`). There is no ready file in these paths for a separate process to poll. The bridge's authenticated `info` route also checks a live session (`machine/lib/win.js:39-49,383-403`).

```text
stop -> kill tmux -> stop tracked bridge apps -> await readying -> final sync if eligible
crash -> periodic sweep -> stop tracked dead-session apps -> sync eligible idle copy
archive -> stop sessions -> wait for running sync -> commit and remove copies
```

Bridge-launched apps, not CLI-owned MCP servers, use `AppTracker`: its Windows wrapper assigns itself to a named kill-on-close Job Object, starts the app, and waits for descendants; `apps.json` supports cleanup on service restart (`machine/lib/win.js:35-36,407-413`; `machine/lib/win-apps.js:59-84,210-246`). Stop waits for those tracked apps, then readying; a verifier copy is removed, while a lead/sub-lead copy is synced only when no other live session shares it and it is marked used (`machine/service.js:1187-1199`; `machine/lib/win.js:200-203,216-235`). No corresponding wait for CLI-owned Windows MCP descendants appears in this stop path; killing tmux alone does not establish that their last writes have finished before sync. The sweep runs every 60 seconds by default, kills tracked dead-session apps and reconciles eligible idle thread copies; archive checks stop/ready/sync tasks before committing and removing, keeps failed copies, and may require a retry (`machine/service.js:449,1236-1255,1289`; `machine/lib/win.js:255-289,303-312`). Worker merge and verifier cleanup remove copies under their separate rules (`machine/lib/win.js:238-252`).

After launch, the bridge marks a Windows-tool copy used, including after late readying; restart recovery conservatively tracks live tool-role sessions with an existing copy and marks it used (`machine/service.js:921-923`; `machine/lib/win.js:145-150,339-358`). The proposed `win-sessions.json` launch record was removed with the split: it is historical design, not current tracking (`docs/plans/windows-bridge-solid/PLAN.md:48,190-210`; historical `5950541c^:docs/plans/windows-bridge-solid/PLAN.md:194-211`). The parent records the rare failed lookup/recovery gap (`docs/plans/windows-bridge-solid/PLAN.md:310`).

Relevant tests cover bounded readying and environment, loaded-entry selection, Codex budget, shared copies, stop, restart and sweep (`machine/test/win-service.test.js:69,101,111,125`; `machine/test/win.test.js:119,238,249,293,351,373,402`). App tests use fake Windows processes for descendants, restart and dead-session cleanup (`machine/test/win-apps.test.js:42,96,109`); reader and Codex translation tests cover validation and environment (`machine/test/project-mcp.test.js:27,42,52`; `machine/test/project-mcp-codex.test.js:24,60,87,133`).
