# Map: visual design in threads

Checked against: `0682593b69c19bc93ee2af333f57cbf5b9efd685` (origin/main; paths checked in this worktree).
Files covered: `protocol/app/cards.md`, `protocol/app/cards-lead.md`, `protocol/app/lead.md`, `protocol/app/sub-lead.md`, `protocol/app/worker.md`, `protocol/app/verifier.md`, `protocol/graphs.md`, `protocol/templates/PLAN.md`, `viewer/app/card.js`, `viewer/app/cards.js`, `viewer/app/routes.js`, `viewer/app/html-download.js`, `viewer/app/wc.js`, `viewer/server.js`, `viewer/pages/diagram.js`, `viewer/pages/thread.js`, `viewer/pages/thread.css`, `viewer/pages/picture.js`, `viewer/pages/picture.css`, `viewer/package.json`, `viewer/playwright.config.js`, `viewer/test/helpers/server.js`, `machine/service.js`, `machine/lib/screen.js`, `machine/lib/screen-input.js`, `install.sh`.

```text
lead writes plan graph file -> diagram card -> thread picture -> full-size picture
user selects file -> upload to thread machine -> attachment path in message -> lead
agent runs app on screen -> screenshot path -> report -> lead image card -> thread
```

1. A lead writes `docs/plans/<slug>/graphs/<name>.html` or `.json` first and posts a `diagram` card naming plan, graph, title and format; only leads can post it (`protocol/app/cards-lead.md:180-194`; `viewer/app/card.js:30-43`). The hub registers the plan before storing the card (`viewer/app/cards.js:84-88`). The thread resolves live files in the worktree and archived files through the thread API (`viewer/pages/diagram.js:12-24`); the live server authenticates, requires a registered plan, resolves symlinks, and requires the actual file inside its `graphs` directory (`viewer/server.js:1673-1685`).
2. HTML is served as its original bytes, not rewritten by a sanitizer: the iframe has an empty sandbox and the response has a CSP forbidding scripts, network loads and form submission while allowing inline styles and data images/fonts (`viewer/pages/diagram.js:70-77`; `viewer/server.js:1690-1694`; `viewer/app/routes.js:19-20`). Download inserts a restrictive CSP and removes refresh metadata (`viewer/app/html-download.js:3-9`). The inline iframe is full width and 340px high; the full-size picture page uses a full-width, full-height iframe and its own scrolling container (`viewer/pages/thread.css:201-207`; `viewer/pages/picture.css:2-9`). “Open full size” links every diagram to that page (`viewer/pages/thread.js:1205-1212`); it offers PNG for graphs and forms but downloads HTML for HTML cards (`viewer/pages/picture.js:31-32,61-75`). HTML must therefore make its own responsive layout; the iframe does not scale a desktop mockup to a phone (`viewer/pages/thread.css:207`; `viewer/pages/diagram.js:70-77`).
3. Form JSON requires `explanation` and one of timeline, layers, before-after or 2–4 side-by-side columns; text is inserted with `textContent` (`viewer/pages/diagram.js:6-10,28-54`). Before/after and side-by-side stack under a 599px container (`viewer/pages/thread.css:325-350`). Form files have a 2 MiB server limit (`viewer/server.js:1686-1688`). The protocol reserves HTML for shapes the other forms cannot express and specifies static self-contained content (`protocol/app/cards-lead.md:196-211`).
4. A lead's `image` card takes an absolute PNG, JPEG, GIF or WebP path, title and at most 25 MiB; the machine checks a regular file and copies it to numbered `<stateDir>/uploads/<thread>/` before forwarding (`protocol/app/cards-lead.md:213-224`; `machine/service.js:332-345,386-403,2398`; `viewer/app/card.js:30-43`). The thread displays the copied file at responsive width (`viewer/pages/thread.js:1215-1218`; `viewer/pages/thread.css:340`). Image cards are lead-only; uploads are removed on archive (`protocol/app/cards-lead.md:222-224`).
5. A user attaches, pastes or drops a file; the composer uploads each, then appends `[attached: <absolute path>]` to the message (`viewer/pages/thread.js:1540-1563`; `machine/service.js:370-373`). The hub requires a live lead, an unarchived thread and a content length at most 25 MiB, then streams to the thread machine; the machine also enforces the limit (`viewer/app/routes.js:18,127-140`; `machine/service.js:352-367`). The lead can open the path (`protocol/app/cards.md:201-202`); the thread recognizes trailing markers and displays previews or file chips (`viewer/pages/thread.js:712-733`).
6. `wc.js screen` sends operations to the authenticated local machine route (`viewer/app/wc.js:100-104,181-182`; `machine/service.js:2445`); the screen manager rejects reviewers and non-Linux, queues calls per session, and `run` starts an Xvfb screen at 1280×800 if needed (`machine/lib/screen.js:260-274`). It requires Xvfb, xauth, mcookie, ffmpeg, xdotool, xwininfo, systemd-run and systemctl plus a working systemd user session; openbox and xprop are optional (`machine/lib/screen.js:10-25,140-145,177-197`). Launches have per-session X authentication and systemd scopes (`machine/lib/screen.js:151-158,213-225`). `shot` uses ffmpeg and returns the path and dimensions; input uses xdotool (`machine/lib/screen-input.js:50-67,70-90`). Files are `<stateDir>/screens/<thread>/<session>/shot-N.png`; only the newest 50 are kept (`machine/lib/screen.js:12,37-43,287-288`).
7. Workers must inspect visible desktop/game work on their screen and report an absolute screenshot path when useful; a sub-lead passes worker or verifier paths on to the lead, who posts an image card (`protocol/app/worker.md:45`; `protocol/app/sub-lead.md:179`; `protocol/app/lead.md:909-912`). The verifier's steps-only flow uses a phone-size headless browser for web apps and an invisible screen for desktop apps, reporting screenshot paths (`protocol/app/verifier.md:52-68`). These instructions do not establish a per-visible-task image card or a comparison against an agreed mockup (`protocol/app/worker.md:45`; `protocol/app/verifier.md:52-68`).
8. The lead draws proposed flows once the plan directory exists, using graph files and diagram cards; the Spec receives a Mermaid flow at approval (`protocol/app/lead.md:914-935`; `protocol/graphs.md:101-103`). The template's Spec is free prose for the settled design, boundaries and validation; it has no designated design-file reference field, though a reference can be written in that section (`protocol/templates/PLAN.md:44-51`).
9. Playwright is a viewer dependency, and the browser suite uses Chromium and Firefox (`viewer/package.json:8-11`; `viewer/playwright.config.js:11-18`); the installer normally installs both, unless dependency installation is skipped (`install.sh:147-155`). On this machine, the installed Playwright Chromium launched headlessly and produced a PNG in memory at 390×844; this is a local observation, not a guarantee for every agent machine. Viewer tests start isolated servers with a free port and cache root; a separate state directory must also be supplied to isolate app state (`viewer/test/helpers/server.js:66-74`; `protocol/app/verifier.md:60-67`).

## What I did not look at

Other providers' installed browser dependencies or remote machines, live phone rendering, every archived-file failure path, and every screenshot retention or upload race. No application test suite was run for this documentation-only map.
