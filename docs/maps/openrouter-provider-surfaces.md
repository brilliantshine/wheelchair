```text
settings and model pins -> account placement -> machine adapter -> CLI ready and role message
  -> turn event and transcript -> hub chat and report -> next queued message
```

1. The hub registry maps provider IDs to CLI names and capability flags; defaults create accounts and provider order, while normalization appends newly seen providers (`viewer/app/providers.js:3-6`; `viewer/app/settings.js:35-38,200-220`). Placement filters by role, configured cells and signed-in accounts, choosing or waiting; session start resolves the model and optional effort via `codex/model.sh`, selects the account and sends the start to the machine (`viewer/app/balancer.js:19-95`; `viewer/app/sessions.js:100-111,267-324,349-361`). Ready requires an eligible account and checks CLI problems (`viewer/app/ready.js:43-68`).
2. The machine adapter contract includes command, role message, readiness, prompt handling, transcript finding, hooks, usage and login (`machine/adapters/index.js:2-5`). Start chooses the registered adapter, prepares its account, creates the worktree and launches; readiness polls the pane before delivery of the initial message (`machine/service.js:657-659,740-749,782-827,1003-1022`; `machine/adapters/kimi.js:127-131`). Kimi passes a named session marker in the initial message, answers trust prompts, detects approval panes and warns that project tools are unsupported (`machine/adapters/kimi.js:127-145`).
3. Kimi binds a compatible main wire log using that marker and records its file identity (`machine/adapters/kimi.js:71-111`). Unlike a translated hook, its one-second poller reads complete main-agent turn ends, maps outcomes, gates on the event spool and persists the watermark and offset; missing or replaced logs can end the session (`machine/service.js:867-952`; `machine/adapters/kimi.js:146`). Kimi agent hook posts are ignored (`machine/service.js:2043`). The transcript copier verifies the opened file identity and chat has a Kimi-specific parser and turn-specific report selector (`machine/service.js:1215-1221,1291`; `viewer/app/chat.js:211-265,314`).
4. Login uses adapter account seeding, environment, command and pane parsing; status enumerates adapter accounts, but CLI status and Kimi version checking also have explicit service paths (`machine/service.js:1467-1478,1490-1517,1528-1581`; `machine/adapters/kimi.js:52-59,121-125`). Kimi returns no usage reading (`machine/adapters/kimi.js:146`); the usage endpoint requires an adapter probe and the documented probes are Claude and Codex (`machine/service.js:1907-1921`; `machine/API.md:94-96`).
5. The model script enumerates providers, defaults and model syntax, and separately exposes Kimi aliases from local config (`codex/model.sh:14-36,47-50,90-101,256-261,416-423`). The hub route and Settings page separately validate model IDs and effort; review-family values, labels and account plans are also maintained in multiple places (`viewer/app/routes.js:258-266,315`; `viewer/app/settings.js:35,220,280-283`; `viewer/pages/settings.js:15,160-183,213,571,970-973`; `viewer/pages/threads.js:14`; `viewer/pages/thread.js:3`). The API describes the accepted providers and session constraints (`viewer/app/API.md:43-46,142`).
6. Installer detection accepts Kimi on PATH or its fallback and propagates executable directories into service PATH; fixture cases cover Kimi-only, fallback and PATH installs, plus the exact generated pins (`install.sh:43-52,76,113,376-379`; `install/test/run.sh:276-303,393`). Machine tests cover auth, version, readiness, recovery, log identity, turn ordering and outage replay; hub tests cover settings, parsing, reports and archive (`machine/test/kimi.test.js:14,122,175,417,472`; `machine/test/kimi-turns.test.js:41-60,104-145,214-232`; `viewer/test/app-kimi-settings.test.js:21-94`; `viewer/test/app-kimi-hub.test.js:12-83`; `viewer/test/app-kimi-archive.test.js:9`). The live harness observes real wire events, interrupted turns, pinned model, trust and approval screens (`test-support/smoke/kimi-live.js:15-34,40-81`).
