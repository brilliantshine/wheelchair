# Map: agent provider flow

Checked against: `20074341b6b1be157c09f8d248d3965645feece9` (origin/main)
Files covered: `machine/adapters/`, `machine/service.js`, `machine/hook.sh`, `machine/lib/hook-post.js`, `machine/lib/aside-turns.js`, `machine/test/accounts.test.js`, `machine/test/fixtures/login/`, `viewer/app/providers.js`, `viewer/app/sessions.js`, `viewer/app/balancer.js`, `viewer/app/settings.js`, `viewer/app/ready.js`, `viewer/app/routes.js`, `viewer/app/chat.js`, `viewer/app/asides.js`, `viewer/app/usage.js`, `viewer/pages/settings.js`, `codex/model.sh`, `codex/preflight.sh`, `protocol/app/lead.md`, `protocol/app/sub-lead.md`, `protocol/app/reviewer.md`.

```text
Settings and account login -> placement and model pin -> machine adapter -> tmux CLI
    -> prompt and hook -> transcript and usage -> hub session and chat
```

1. The provider registry maps `claude` to CLI `claude` and `gpt` to `codex`, with flags for effort, preflight and role message delivery (`viewer/app/providers.js:3-5`). Settings establishes accounts, role orders and review-family policy (`viewer/app/settings.js:25-27`; `viewer/app/balancer.js:27-51`). Placement considers model availability, machine login, limits, reserve and requested or excluded provider; review and verifier constraints can fall back with a note (`viewer/app/balancer.js:38-80`). Sessions read provider/role model and effort through `codex/model.sh`, run GPT preflight, and send provider, account and model to the machine (`viewer/app/sessions.js:19-30,141-166,192-216`).
2. The machine resolves the CLI adapter, account directory and role prompt; it writes adapter settings when needed, builds a quoted command and launches it in a worktree tmux session, then detects readiness from the pane and submits queued initial text (`machine/service.js:462-505,517-577`). The adapter registry has exactly two entries (`machine/adapters/index.js:2-5`). Claude supplies a session ID, settings with Stop/Notification/StopFailure hooks and statusline, and a system prompt; Codex configures notify and trust, sandbox policy, and types its role prompt as the first message (`machine/adapters/claude.js:17-26`; `machine/adapters/codex.js:31-33`).
3. Claude locates a project JSONL by session ID; Codex binds its thread ID only when a turn notification starts with the role marker, then finds a matching session JSONL and reads complete new lines for rate limits (`machine/adapters/claude.js:27-29`; `machine/adapters/codex.js:12-28,34-36`). Claude translates Stop, permission notification and StopFailure, including rate-limit failures; Codex translates agent-turn-complete. Hook shell receives Claude JSON on stdin and Codex JSON as final argument; hook-post translates, posts with the session token or spools (`machine/hook.sh:16-30`; `machine/lib/hook-post.js:10-30`). Machine updates lifecycle and copies transcripts, while chat selects a CLI-specific parser (`machine/service.js:698-735,798-825`; `viewer/app/chat.js:172-199`). Claude usage comes from rate-limit payloads, Codex from transcript windows (`machine/adapters/claude.js:28-29`; `machine/adapters/codex.js:24-28,36`).
4. Each account uses the adapter's environment and seed; Claude uses `CLAUDE_CONFIG_DIR`, Codex `CODEX_HOME`, and the shared seed links instructions and records metadata (`machine/adapters/common.js:9-17`; `machine/adapters/claude.js:5-6,30-31`; `machine/adapters/codex.js:5-6,37-38`). Settings starts sign-in via hub routes; the machine launches a separate tmux login, captures its pane, optionally answers a menu, and calls the adapter parser (`viewer/app/routes.js:337-344`; `machine/service.js:904-934`). Claude unwraps its URL and may ask for a browser code; Codex runs device auth and requires an OpenAI URL plus a displayed code (`machine/adapters/claude.js:10-16`; `machine/adapters/codex.js:10-11`). The Settings sign-in card polls, shows URL and optional device code, and sends a pasted browser code back (`viewer/pages/settings.js:908-981`; `machine/service.js:1058-1064`). Captured screens and parser expectations are in `machine/test/fixtures/login/` and `machine/test/accounts.test.js:49-56`.
5. Ready compares machine and hub versions, then checks installation and at least one unpaused signed-in account for the thread's CLI (`viewer/app/ready.js:29-58`). The lead protocol instead says Ready checks both families (`protocol/app/lead.md:82-83`); that statement is stale. The older `app-provider-placement.md` also predates changes to its covered files and its Ready description is stale, so it was not reused.
6. Asides derive their parent ID differently for Claude and Codex, then use headless fork/resume adapters and different output parsers (`viewer/app/asides.js:38-44,94-109`; `machine/lib/aside-turns.js:38-41,72-107`; `machine/adapters/claude.js:9`; `machine/adapters/codex.js:9`).
