# Map: overlap decisions, cards and lead restart

Checked against: `b53f4f24313cc6e46ee58e24b18e02bcc9c5283d` (origin/main); pointers below are worktree HEAD `19c08756cb2e84ecd466db1442e57ff26ace31dc`. The checked paths in lead, sub-lead, machine, sessions and routes differ at origin, principally provider and unrelated changes; line numbers below identify this worktree. Files covered: `protocol/app/lead.md`, `protocol/app/sub-lead.md`, `protocol/app/cards.md`, `protocol/app/cards-lead.md`, `viewer/app/card.js`, `viewer/app/cards.js`, `viewer/app/threads.js`, `viewer/app/peers.js`, `viewer/app/sessions.js`, `viewer/app/wc.js`, `viewer/app/routes.js`, `machine/service.js`.

```text
lead lists peers -> notices overlap -> asks peer -> information arrives
                                      -> user decides in chat or planning question
user answer -> plan / review -> approval -> Start building -> sub-lead owns worktree
card CLI -> machine spool -> hub assigns id -> stored card -> press or retract
lead dies -> restart context + pending queue -> replacement reads plan and cards
```

1. `wc.js session leads` forwards a lead-only request. The hub lists same-machine, reachable same-project and linked threads; a prior lead with no live lead yields null. Same-project and linked entries include idea, stage and progress; `--all-projects` exposes limited information on other projects (`viewer/app/wc.js:72`, `viewer/app/sessions.js:651`, `viewer/app/peers.js:41`). The lead looks after mapping, before first ready-for-review, on request, and before a small fix; it asks a live overlapping lead with `asks: true`, but never waits on that lead. Cross-thread messages are restricted to leads, same machine and same project or linked threads (`protocol/app/lead.md:711`, `viewer/app/cards.js:144`).
2. A new overlap found at the pre-review planning check becomes a PLAN Open Question; elsewhere the current rule is a one-line mention in the next visible reply, with the user deciding in chat (`protocol/app/lead.md:715`). A hidden peer-message turn cannot itself be that visible reply. A peer's user-only question waits until IDEA is confirmed and other questions are closed (`protocol/app/lead.md:717`, `:721`). This conflicts with applying that wait unchanged to a small fix, which has no plan documents (`protocol/app/lead.md:122`). IDEA confirmation itself is a question before design questions; planning records decisions and saves consequences before the next question (`protocol/app/lead.md:187`).
3. During review, a deferred-item pull-back already has a durable `Pending pull-back:` Log entry, applied after triage before the next round or approval (`protocol/app/lead.md:250`). Review starts fresh reviewers and posts `checking`; triage posts `clean` or `fixing`, whose counts represent findings. A clean round has no upheld blocking/major finding or open user-decision (`protocol/app/lead.md:270`, `:298`, `:323`, `:365`). `fixing` requires at least one finding (`protocol/app/cards.md:81`): a pending change with zero findings needs an explicit progress path, as the prior review identified (`docs/plans/lead-chat/PLAN.md:466`). Approval is posted after a clean round and Ready check; changed plans return to review (`protocol/app/lead.md:375`). Start rechecks Ready, queues the press only if unchanged and ready, and marks the card answered (`viewer/app/threads.js:381`, `:417`). Once started, the lead must not write the worktree while the sub-lead owns it (`protocol/app/lead.md:401`, `protocol/app/sub-lead.md:13`).
4. `card.js` validates locally, posts to the machine and prints nothing on success (`viewer/app/card.js:285`). The machine spools before forwarding and may return 202 with only `ok` and `spooled` during an outage or backlog; later drain discards the successful hub response (`machine/service.js:1320`, `:1347`, `:2047`). The hub assigns a random card id and normally returns the stored card; duplicate delivery returns only a duplicate receipt, while title, resolve and retract return operation receipts (`viewer/app/cards.js:11`, `:61`, `:80`, `:89`, `:107`, `:158`). Thus printing a posted id cannot be guaranteed merely by printing the current response: a spooled success has no hub-assigned id yet. Retract requires the target id, refuses answered or replaced targets, marks the target and clears its pin (`viewer/app/card.js:248`, `viewer/app/cards.js:89`; `protocol/app/cards-lead.md:308`).
5. Restart builds context from non-replaced cards, pins, an id-to-kind map of all cards, and only the last 20 sent user/card messages; it does not include sent peer messages in `recent_messages` (`viewer/app/threads.js:138`). Queued non-context messages from dead leads are moved to the replacement (`viewer/app/threads.js:180`). The lead rereads plan files; existing pull-back recovery uses committed Log entries and recent `removed:` presses plus `card_kinds`, restarting live reviewers and discarding their reports (`protocol/app/lead.md:773`, `:796`). A pending overlap change stored only in a delivered peer message or older user message is therefore not reliably reconstructed from this context.
