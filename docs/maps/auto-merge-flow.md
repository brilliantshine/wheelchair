# Map: settings and pull request finishing

Checked against: `249d3a8ba14731806c3f2d40a25596b9294e6999` (origin/main)
Files covered: `viewer/app/settings.js`, `viewer/app/state.js`, `viewer/app/routes.js`, `viewer/pages/settings.js`, `viewer/app/diagram-sensitivity.js`, `sensitivity/set.sh`, `viewer/app/sessions.js`, `protocol/app/lead.md`, `protocol/app/cards-lead.md`, `viewer/app/pr-gate.js`, `viewer/app/pr-wait.py`, `viewer/app/hub.js`, `viewer/app/cards.js`, `viewer/app/card.js`, `viewer/app/threads.js`, `viewer/app/handoff.js`, `viewer/pages/thread.js`, `viewer/app/wc.js`, `machine/service.js`.

```text
Settings page -> hub preferences -> settings.json -> lead instructions / later message
verified work -> push and PR -> wait for readiness -> done card -> check card
                                                       -> merged poll -> merged card
user reports problem -> inspect PR state -> open: fix and verify -> done
                                       -> merged: follow-up stub
```

1. The Settings page loads `/settings`, renders sections, and preference controls PUT individual values and update their displayed value from the response (`viewer/pages/settings.js:494-505,1482-1508`). The route validates explicit preference fields and returns an explicit field list (`viewer/app/routes.js:286-343`). Defaults, normalization and the response are explicit lists too: an unlisted new property is lost on load, and needs adding to all three (`viewer/app/settings.js:37-39,222-240,298-307`). `update` serializes read/normalize/change/validation/write; state stores `settings.json` atomically (`viewer/app/settings.js:260-274`; `viewer/app/state.js:70,233-248`).
2. A new lead gets role layers composed from the current settings, including writing style (`viewer/app/sessions.js:318-324,342-343`; `viewer/app/settings.js:162-175`). A style change increments a version and reaches an already-running lead only when the next queued message is delivered, as a replacement `[wc:style]` trailer (`viewer/app/routes.js:396-401`; `viewer/app/sessions.js:512-528`). Diagram sensitivity is a different mechanism: the hub fans out to machines and stores no dial value; each machine runs the writer, which updates present Claude and Codex global instruction files (`viewer/app/diagram-sensitivity.js:3-4,26-48`; `machine/service.js:2047-2067`; `sensitivity/set.sh:10-26,253-259`). Neither mechanism automatically delivers a new merge preference; timing for changes to active leads needs a design.
3. A small fix is verified, pushed and opened as a PR; a planned build commits `status: done`, pushes and opens a PR after its sub-lead finishes. Both follow the finishing procedure before done; step 8 explicitly says “Never merge” (`protocol/app/lead.md:124-140,457-467`). After-done fixes on an open PR are committed, independently verified, reconciled with the remote, pushed and finished again (`protocol/app/lead.md:485-509`).
4. Finishing records the pushed remote head and polls GitHub in `pr-wait.py` for up to ten minutes at a time within a 30-minute window; it stops on changed head, closed/merged, conflict, behind, failure or readiness. No-check readiness waits five minutes (`protocol/app/lead.md:625-646`; `viewer/app/pr-wait.py:1-49`). `BLOCKED` without failed or pending checks is treated as ready even if a review rule remains, so ready does not prove an actual merge will succeed (`protocol/app/lead.md:639-645`; `viewer/app/pr-gate.js:15-28`). The hub's `done` gate independently queries GitHub with its own `gh`, checks PR branch, base and exact head, and accepts a matching merged PR or a qualifying open PR (`viewer/app/hub.js:189-200`; `viewer/app/pr-gate.js:8-14,24-43`).
5. If a PR merged at a different head, the lead fetches the PR head and checks ancestry: if its pushed commit is included, it posts done at the merged head; if not, it creates a dependent stub and posts no done. Fetch or ancestry errors become needs; closed PRs end the wait (`protocol/app/lead.md:647-662`). Restart recovery avoids redoing an accepted done, handles a matching PR head, and asks the user about other divergence (`protocol/app/lead.md:688-704`). Git command results must be checked for `ok` because failures can exit zero (`protocol/app/lead.md:706-707`).
6. The lead-facing `wc.js git` allowlist has no PR-merge operation; `merge` means local `git merge`, and `pr` means `gh pr create`. Adding one needs CLI parsing/allowlist, machine allowlist and dispatch, contract and tests, plus appropriate PR/head/role authorization and error handling; that latter policy is a design decision, not an existing check (`viewer/app/wc.js:49-68`; `machine/service.js:1535-1560,2257`). The existing agent route authenticates the session and runs from its recorded worktree; this makes the machine service the natural boundary for a lead-invoked `gh pr merge`, whereas hub `gh` calls are currently read-only gate and polling actions (`machine/AGENTS.md:3-5`; `machine/service.js:1541-1547`; `viewer/app/pr-gate.js:31-43`; `viewer/app/threads.js:458-478`). These run in different service environments and may use different GitHub credentials.
7. After each accepted done, the lead drafts check steps, has a fresh verifier try the exact done head, and posts a check; already-merged done cards omit the merge from update instructions (`protocol/app/lead.md:514-545`). The hub accepts one check per current done head (`viewer/app/cards.js:120-125`). A broken check's fix button goes through the current-head check and then the after-done PR-state path; once merged, fixes become dependent stubs rather than changes to the old PR (`viewer/app/threads.js:358-364`; `protocol/app/lead.md:580-587,485-512`).
8. The hub polls eligible unarchived threads' done/imported PR URLs at startup and every minute; on GitHub `MERGED`, it records the URL and adds one system merged card; errors retry on a later sweep (`viewer/app/hub.js:93-102`; `viewer/app/handoff.js:109-110`; `viewer/app/threads.js:454-481`). The page renders merged, done and check cards, and keeping a merged card resolves it (`viewer/pages/thread.js:1032-1087`; `viewer/app/threads.js:351-356`). An auto-merge before done still needs done acceptance before the normal done-based poll can find the URL.

Not checked: GitHub repository branch-protection configuration, actual credentials, merge method selection, installation and rollout on running machines, and complete test coverage.
