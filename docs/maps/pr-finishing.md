```text
build and verify -> lead pushes and opens PR -> lead posts done -> machine spool -> hub saves card
                                                                     -> GitHub reports merged -> app posts merged
```

1. A small fix is committed and independently verified, then pushed, opened as a PR and reported with `done`; after two failed verification attempts Collin may choose to push anyway (`protocol/app/lead.md:112-122`). For a feature, the sub-lead runs full validation, commits the completion and verifying status, starts verifier(s), and on pass reports the verified commit; the lead stops it, commits `status: done`, pushes and opens the PR, then posts `done`. Step 8 says never merge the PR (`protocol/app/sub-lead.md:207-233,250-251`; `protocol/app/lead.md:312-325`). The verifier checks a detached commit, runs applicable validation and reports its commit and verdict; it cannot edit or post cards (`protocol/app/verifier.md:13-17,31-40,50-74`). Neither finishing path requires waiting for GitHub CI or merging the default branch.
2. After done, the lead checks PR state. An open PR can receive a verified fix; it fetches and merges changes on the remote **PR branch**, re-verifies if needed, pushes, then checks state and head. A merged PR with the just-pushed head still gets a new `done`; an older merged head gets a stub; closed gets no fix unless requested (`protocol/app/lead.md:333-359`). The `done` card requires title, `can_do`, `left_as_is` and PR URL; its optional note can disclose a fix pushed after failed verification (`protocol/app/cards-lead.md:109-119`). An app-only `merged` card is a separate later notice (`protocol/app/cards-lead.md:124-128`).
3. `wc.js git` sends an authenticated request to the local machine; it permits fetch, commit, merge, cherry-pick, revert, push, pr and worktree-remove, passing flags through except commit's message and explicit paths (`viewer/app/wc.js:49-68,155-170`). In the authenticated session worktree, the machine runs `git fetch/merge/cherry-pick/revert/push`, `gh pr create`, or `git add` then path-limited `git commit`; worktree removal has separate worker/ancestor checks (`machine/service.js:963-1001,1308`). Thus `wc.js git merge origin/main` is supported after fetch; it is a Git merge into the worktree, distinct from merging the PR. Git reports conflict details through the returned `ok`, `status`, `stdout`, `stderr` JSON; the HTTP response itself is 200 and the CLI prints that JSON, so a Git failure is not automatically a nonzero CLI exit (`machine/service.js:70-75,991-1001,1308`; `viewer/app/wc.js:169-190`).
4. `card.js` checks the JSON schema and sends with a session token; `done` is lead-only at role validation and its URL is merely nonempty text (`viewer/app/card.js:24-32,116-121,150-165,251-269`). The machine authenticates the agent, attaches session and thread, persists a delivery-id spool and relays to the hub; outages and an existing queue can return 202 while only spooled (`machine/service.js:869-877,1272-1305`). The machine-secret route enters a per-thread lock; the hub checks the session, archive state, deduplicates, validates the role and schema again, then adds and saves the card (`viewer/app/routes.js:374-378`; `viewer/app/hub.js:143`; `viewer/app/cards.js:51-61,120-122,149-153`). A gate before `addCard` could use thread/session context; however a later 4xx from a spooled delivery moves it to rejected storage, while the original agent may already have received success (`machine/service.js:883-888,911-923,1293-1304`). No existing acceptance check reads PR state or checks.
5. Independently, the hub polls at startup and every minute; it takes the latest done URL for unarchived threads, checks a GitHub URL pattern, runs `gh pr view <url> --json state` with a 15-second timeout, and adds one system merged notice on `MERGED`. Errors are retried on the next sweep (`viewer/app/hub.js:63-65,71-73,154-157`; `viewer/app/threads.js:359-387`). Waiting dependent stubs use `gh pr list` from the project clone (`viewer/app/threads.js:390-409`). These `gh` subprocesses and machine PR creation inherit their service process environments; the call sites supply no GitHub token or credentials (`viewer/app/threads.js:372,400-402`; `machine/service.js:70-71,991-1000`). The actual credential source and whether hub and machine credentials match were not inspected. These paths read merged state, not mergeability or CI; the git wrapper exposes PR creation, not `gh pr checks` (`viewer/app/wc.js:49-67`; `viewer/app/threads.js:359-409`).
6. The sole workflow, `.github/workflows/macos.yml:1-17`, runs on PRs and pushes to main, on macOS with a 30-minute job timeout. It installs tmux, runs sensitivity, codex, installer and machine aside-turn suites, installs services with fake CLIs, and checks them (`.github/workflows/macos.yml:18-41`). A read-only `gh run list --workflow macos.yml --limit 10 --json conclusion,createdAt,updatedAt,event,status` on 2026-11-17 Pacific showed five successful PR runs taking approximately 1m41s–3m12s from creation to update; this is a small recent sample including queue time, not a guarantee.
