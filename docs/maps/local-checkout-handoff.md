# Map: local checkout handoff surfaces

Checked against: `207c02f5e0b56cfbcc96046cca10a8df92002a9c` (origin/main and worktree HEAD).
Files covered: `install.sh`, `machine/service.js`, `viewer/server.js`, `viewer/app/state.js`, `viewer/app/routes.js`, `viewer/app/threads.js`, `viewer/app/sessions.js`, `viewer/app/machine-client.js`, `viewer/pages/new.js`, `viewer/pages/thread.js`.

```text
phone selects machine and project -> hub checks that path on machine -> thread stores both
  -> machine fetches project origin -> creates thread worktree -> agent commits and pushes
  -> done card on phone -> card press -> hub -> lead queue
  -> separate hub-only handoff calls -> machine git on project or recorded worktree
```

1. The installer creates `machines.json` only if absent, with hostname, host, port and secret file; it contains no project paths (`install.sh:149-167`). The hub resolves a machine name, including its `hub` alias, from that registry (`viewer/app/state.js:146-168`). The new screen selects a machine and project (`viewer/pages/new.js:100-107,229-241`); saved directories are `{name,path,machine}`, while previous project paths are derived from matching threads (`viewer/app/routes.js:125-152,163-178`). The hub's `projects.json` is a flat list of path strings, not a per-machine repository identity (`viewer/app/state.js:171-173,196-203`). A thread records its selected machine and machine-checked project path (`viewer/app/threads.js:20-25,41-64,72-76`). The check expands `~`, requires an absolute directory, acceptable basename and a `.git` entry; it does not establish checkout identity, cleanliness, or remote identity (`machine/service.js:1198-1205,1223-1232`). A selected project can therefore be Collin's working checkout, but no field distinguishes it as such or records a separate personal checkout; no cache clone is created in this flow.
2. The hub passes that path as `project_dir` to the thread's machine, and records the returned worktree and `wc/<id>` branch (`viewer/app/sessions.js:304-330,360-364`). The machine serializes fetch-and-add per repository, fetches origin, resolves its default branch, then creates a branch from `origin/<default>` in `~/.local/state/wheelchair/worktrees/<project>/wc/<id>` by default; worker branches start from the thread branch and verifiers get detached worktrees (`machine/service.js:29-30,460-496,530-552`; `viewer/app/sessions.js:625-630`). Fetch and worktree registration write the selected repository's Git metadata even though the files checked out for the agent live elsewhere. The installer starts the machine as a systemd user service or a GUI-domain launch agent; subprocesses inherit that service's operating-system permissions (`install.sh:312-338,392-404`; `machine/service.js:78-79,530-540`). Agent git requests use the session's recorded worktree as cwd, permit a fixed set of operations and restrict explicit commit paths; arguments to several git operations are passed through (`machine/service.js:1042-1067,1603`).
3. The done renderer has a PR link and per-item start-thread buttons (`viewer/pages/thread.js:831-859`). The shared press helper POSTs to the hub (`viewer/pages/thread.js:90-97,545-551`; `viewer/app/routes.js:524-525`). Ordinary card presses need a live lead, mark the card answered and enqueue a message to that lead; they do not run machine git directly (`viewer/app/threads.js:374-390`). A direct action can instead follow the hub's existing machine-client pattern: look up `thread.machine`, resolve its registry entry, and send the machine secret to that host (`viewer/app/threads.js:130-133`; `viewer/app/machine-client.js:53-77,98-108`). Browser app writes require a remember cookie or token and matching origin; machine callbacks use a separate machine-secret path (`viewer/server.js:1292-1298,2104-2110`).
4. `/v1/handoff` is hub-secret-only, not an agent-token endpoint (`machine/service.js:403-420,1528-1532,1602-1604`). Its git actions accept an absolute checked project and can fetch remote refs, make claim commits, push with leases, or force a local branch ref in that project (`machine/service.js:1236-1246,1250-1275,1321-1344,1361-1365`). Its fast-forward action only accepts a recorded thread-created worktree, checks dirty state, branch and ancestry, then merges and changes upstream config (`machine/service.js:1277-1287,1346-1359`). It is not an arbitrary personal-checkout switch endpoint. A normal agent has its own session token; a recovered session without one cannot authenticate (`machine/service.js:407-420`).
5. The machine already uses `symbolic-ref`, `rev-parse` and `status --porcelain` to inspect the recorded thread worktree; status also fetches the remote branch, so this endpoint is not a read-only general checkout inspection (`machine/service.js:1408-1420,1236-1246,1277-1282`). The service can attempt those commands against a local checkout it can access, but this code supplies no arbitrary-checkout status API or snapshot guarantee. Project validation checks `.git` presence rather than proving the path is a repository root (`machine/service.js:1198-1205,1223-1232`); path identity, symlinks, access rights, ignored files, concurrent edits, detached HEAD, linked-worktree branch conflicts and Git side effects need explicit treatment before using a result to authorize a write. A clean check and a later write are separate operations in the existing fast-forward sequence (`machine/service.js:1350-1357`).

## What I did not look at

Live machine configuration or the user's actual checkout, all possible Git configuration, hooks and filesystem permissions, every API route and test case, Git behavior across platforms, or whether a new operation should switch, merge, or otherwise update a checkout. No tests were run for this documentation-only map.
