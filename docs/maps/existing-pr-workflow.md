# Map: working on an existing pull request

Checked against: `25f34a4572c4beb9032f16f818b6502cc59f62bd` (origin/main)
Files covered: `protocol/app/lead.md`, `protocol/app/sub-lead.md`, `viewer/pages/new.js`, `viewer/pages/thread.js`, `viewer/app/routes.js`, `viewer/app/threads.js`, `viewer/app/sessions.js`, `viewer/app/wc.js`, `viewer/app/chat.js`, `viewer/app/handoff.js`, `viewer/app/peers.js`, `viewer/app/card.js`, `viewer/app/cards.js`, `viewer/app/hub.js`, `viewer/app/pr-gate.js`, `viewer/app/pr-wait.py`, `viewer/app/auto-merge.js`, `machine/service.js`.

```text
New thread -> new thread branch and worktree -> lead verifies and pushes -> create PR
                                                    -> GitHub gate -> done -> check -> optional auto-merge
```

1. New-thread UI sends project, machine and optionally message or title; POST creates a random-id thread, checks the project, saves it and starts a lead (`viewer/pages/new.js:229-241`, `viewer/app/routes.js:542-544`, `viewer/app/threads.js:16-24`, `viewer/app/threads.js:59-83`). The normal start supplies no target branch; the machine fetches origin and creates `wc/<thread-id>` from `origin/<default branch>` with no tracking; the hub records that name (`viewer/app/sessions.js:368-390`, `machine/service.js:643-647`, `machine/service.js:701-713`, `viewer/app/sessions.js:425-429`). The remote checkout path exists for handoff/restart, but requires a 40-hex SHA on an origin branch named `wc/<12 hex>`, and checks ancestry before creating or fast-forwarding the checkout; it is not exposed by ordinary new-thread creation (`machine/service.js:668-699`, `viewer/app/threads.js:125-134`, `viewer/app/threads.js:172-180`).
2. Small fixes and planned builds verify, push `HEAD:wc/<thread-id>` and create a PR; the lead must not merge it, and the app may auto-merge (`protocol/app/lead.md:125-140`, `protocol/app/lead.md:458-470`). After done, an open PR gets a fix and verifier, then fetch/merge of its own remote branch and push; merged work becomes a stub and closed work stays unchanged. The protocol explicitly forbids pushing another thread's branch (`protocol/app/lead.md:482-516`). The sub-lead works on the feature branch and merges workers locally (`protocol/app/sub-lead.md:12`, `protocol/app/sub-lead.md:126`, `protocol/app/sub-lead.md:186-189`).
3. `wc.js git` forwards non-commit arguments unchanged; the agent route authenticates and uses the session's recorded worktree. Fetch and push run `git fetch ...args` and `git push ...args`, and pr runs `gh pr create ...args`; this dispatch has no role, branch, remote or refspec check for these operations (`viewer/app/wc.js:49-68`, `machine/service.js:1588-1613`, `machine/service.js:2291`). The prohibition is therefore protocol policy, not enforcement in this git dispatch. Git errors appear in the JSON `ok` field even when the wrapper exits zero (`protocol/app/lead.md:725-726`).
4. Finishing reads the pushed `origin/wc/<thread-id>` tip and waits on GitHub; changed heads fetch and merge that same branch, and rejected pushes retry after reconciliation and verification. Repair, restart, timeout and merged/closed cases have separate paths (`protocol/app/lead.md:632-653`, `protocol/app/lead.md:672-739`). `verified: true` requires a contextual passing verifier or build result, no non-plan file differences from its commit to done head, and no prior choice to ship a surviving gap (`protocol/app/lead.md:654-665`).
5. A done card supplies PR URL, exact head and optional verified flag (`viewer/app/card.js:148-155`). The machine relays done synchronously; hub checks GitHub before accepting it (`machine/service.js:2263-2272`, `viewer/app/hub.js:197-208`). The gate compares head branch name to `thread.branch`, base name to `thread.default_branch`, and head SHA to the card; it accepts a matching merged PR or qualifying open readiness (`viewer/app/pr-gate.js:8-28`). It queries no head repository identity or `maintainerCanModify` (`viewer/app/pr-gate.js:31-43`). A different PR head branch is rejected even if its URL and SHA are correct.
6. The thread view derives `pr_url` from the latest qualifying done card or imported PR and shows its link; peer `session leads` returns the recorded branch and current done PR URL for same-project or linked threads on the same machine (`viewer/app/chat.js:144-153`, `viewer/app/handoff.js:112`, `viewer/pages/thread.js:193`, `viewer/app/peers.js:42-63`). It does not discover a collaborator's PR on another machine by itself.
7. A check must match the latest done head, one per head; acceptance starts auto-merge (`viewer/app/cards.js:53-55`, `viewer/app/cards.js:150-155`, `viewer/app/cards.js:261-263`). Auto-merge requires the setting on, a current check with no broken steps, no prior attempt for that head, no import, every done verified, and at least one matched step; it rechecks GitHub and sends an exact-SHA merge API request (`viewer/app/auto-merge.js:19-43`, `viewer/app/auto-merge.js:52-90`). It can optionally delete the head branch after merging, including a fork branch identified by GitHub's head repository fields (`viewer/app/auto-merge.js:64-67`, `viewer/app/auto-merge.js:92-96`). No `maintainerCanModify` check appears in these covered PR paths; actual permissions and credentials are GitHub's decision.
