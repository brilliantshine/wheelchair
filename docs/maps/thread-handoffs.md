## Flow

```text
new screen -> thread record -> lead and worktree -> cards and plan stages
                                              -> restart context -> replacement lead
                                              -> archive -> branch documents
```

The new screen chooses machine/project, creates a thread and optionally uploads files before sending its message (`viewer/pages/new.js:103`, `viewer/pages/new.js:213`, `viewer/pages/new.js:219`, `viewer/pages/new.js:232-240`). The hub validates the project on that machine, assigns a random id, saves the thread and starts a lead; title comes from the first message or supplied title (`viewer/app/threads.js:16-38`, `viewer/app/threads.js:43-80`). State is atomic JSON at the hub state directory's `threads/<id>.json`; older sent history rolls into `<id>.sent.jsonl` (`viewer/app/state.js:9`, `viewer/app/state.js:41-48`, `viewer/app/state.js:84-104`, `viewer/app/state.js:113-129`). Provider/CLI are chosen at lead start and worktree, branch and default branch are recorded after machine start (`viewer/app/sessions.js:264`, `viewer/app/sessions.js:303-324`, `viewer/app/sessions.js:357-362`). A stub inherits project and machine and stores title, summary, parent id/title, dependency and optional commits; a dependent stub waits for its parent unless started now, and its context sends summary and commits, not parent cards (`viewer/app/threads.js:91-118`). Merged-parent polling marks waiting stubs ready (`viewer/app/threads.js:384-403`).

The machine fetches origin and creates `wc/<thread-id>` from `origin/<default branch>` by default; `input.base` can specify another git ref, but ordinary creation does not pass a base. Workers use the thread branch as base; verifiers check it out detached (`machine/service.js:425-474`, `viewer/app/threads.js:74-77`, `viewer/app/sessions.js:619-621`). The hub records the thread branch as `wc/<id>` even if the machine was given another branch (`viewer/app/sessions.js:357-360`). Agent git commands run in the session worktree; fetch and push call git, and pr calls `gh pr create` (`viewer/app/wc.js:50-67`, `machine/service.js:965-984`). Thus an arbitrary remote base is a machine capability, not an existing new-thread option; choosing an existing branch as the new local branch also conflicts with `worktree add -b` (`machine/service.js:461-470`).

Cards are appended to the thread record with ids, session, timestamps and `answered`; singleton pins replace prior records, and approval has its own pin (`viewer/app/cards.js:11-33`). Presses store answer action/value and unpin accepted approval; retraction marks the target answered with attribution and time and removes its pin (`viewer/app/threads.js:272-280`, `viewer/app/threads.js:310-336`, `viewer/app/cards.js:43-47`, `viewer/app/cards.js:82-97`). Restart refuses a live lead, builds JSON from slug, all non-replaced cards, pins and the last 20 sent human/card messages, starts a lead in the existing worktree/branch, moves pending non-context queues, and prepends the new context (`viewer/app/threads.js:122-157`). This includes answered and retracted cards unless replaced; the restart function itself does not read PLAN.md. Session startup passes role, project, worktree, branch and role layers to the machine (`viewer/app/sessions.js:303-327`).

The lead confirms IDEA before creating PLAN (`protocol/app/lead.md:167-172`); IDEA has draft/confirmed and PLAN has planning, ready-for-review, approved, implementing, verifying, done (`protocol/templates/IDEA.md:3`, `protocol/templates/PLAN.md:3`). The lead writes planning, ready-for-review, approved and done; the sub-lead writes implementing and verifying (`protocol/app/lead.md:443-455`, `protocol/app/sub-lead.md:30-33`, `protocol/app/sub-lead.md:207-214`). Mapper commits MAP; lead commits IDEA, PLAN and graphs; completion and remediation reports are created during verification (`protocol/app/lead.md:154-159`, `protocol/app/lead.md:196-197`, `protocol/app/sub-lead.md:207-214`, `protocol/app/sub-lead.md:231-244`). Mapper and reviewers are stopped after results, workers after merging, verifiers after reports, and sub-lead after its build result (`protocol/app/lead.md:156-159`, `protocol/app/lead.md:233-238`, `protocol/app/sub-lead.md:168`, `protocol/app/sub-lead.md:224-228`, `protocol/app/lead.md:306-315`). These rules describe cleanup, not an automatic guarantee that every status alone means no live child session.

Attachments stream via the hub to machine uploads; the composer sends their absolute paths as `[attached: ...]` lines, and the page offers links for servable uploads (`viewer/app/routes.js:69-85`, `viewer/pages/thread.js:371-396`, `viewer/pages/thread.js:1007-1021`). Existing GET upload streaming and archived document/graph routes serve specific artifacts (`viewer/app/routes.js:442-464`); the inspected routes do not define a thread export download. Archive asks the machine to stop sessions, save dirty work locally where possible, remove clean worktrees and uploads; retained worktrees and errors are reported, and rebase or upload removal failure leaves the hub thread unarchived (`viewer/app/threads.js:161-201`, `machine/service.js:740-792`). Archived plan documents and graphs are read from the local branch (`viewer/app/threads.js:205-243`); archive itself is not a push (`machine/service.js:740-792`).
