# Map: planning modes and follow-up handoff

Files covered: `protocol/app/lead.md`, `protocol/app/reviewer.md`, `protocol/app/sub-lead.md`, `protocol/app/verifier.md`, `protocol/app/cards.md`, `protocol/app/cards-lead.md`, `protocol/templates/PLAN.md`, `protocol/templates/IDEA.md`, `viewer/app/card.js`, `viewer/app/cards.js`, `viewer/app/chat.js`, `viewer/app/threads.js`, `viewer/app/hub.js`, `viewer/app/routes.js`, `viewer/app/state.js`, `viewer/app/settings.js`, `viewer/app/sessions.js`, `viewer/app/views.js`, `viewer/pages/new.js`, `viewer/pages/settings.js`, `viewer/pages/thread.js`, `viewer/pages/doc.js`, `viewer/doc.js`, `viewer/server.js`.

```text
new thread -> lead confirms idea -> plan -> review -> approval -> build -> verify -> done
                                  |                                    |
                              accepted risks                      stub card -> child thread -> open -> lead
```

1. A new-thread form sends project, machine and optionally message or title; the hub validates the project, saves a thread, starts a lead with an empty brief, then enqueues the message (`viewer/pages/new.js:228`, `viewer/app/routes.js:413`, `viewer/app/threads.js:57`). The lead maps, confirms IDEA, creates PLAN, settles questions and writes a complete Spec before review (`protocol/app/lead.md:154`, `:165`). IDEA has a separate confirmed status; PLAN has six lifecycle statuses (`protocol/templates/IDEA.md:3`, `protocol/templates/PLAN.md:3`).
2. Reviewers read IDEA and PLAN: round one attacks the whole Spec, later rounds examine changes and whole-Spec coherence; accepted risks are not re-raised without contrary evidence (`protocol/app/reviewer.md:20`, `:34`, `:51`). Lead triage records accepted risks, repeats until clean, commits approved documents, checks Ready and posts approval (`protocol/app/lead.md:224`, `:240`, `:263`). Start building reruns Ready; changes return the Spec to review (`viewer/app/threads.js:291`, `protocol/app/lead.md:283`).
3. The sub-lead commits implementing, builds and validates, writes COMPLETION and commits verifying; verifiers independently check each Spec item and IDEA's success and non-goals (`protocol/app/sub-lead.md:31`, `:205`, `protocol/app/verifier.md:31`). On failure the sub-lead records every gap for remediation and re-verifies; after two unsuccessful fixes the lead asks Collin (`protocol/app/sub-lead.md:234`). Only after a passing result does the lead commit done, push, open a PR and post done (`protocol/app/lead.md:311`, `:316`). Deferring verification discoveries therefore changes an explicit existing remediation rule.
4. The card CLI and hub use the same validator; it rejects unknown fields and unauthorized roles and checks stage-dependent progress fields (`viewer/app/card.js:71`, `:151`, `viewer/app/cards.js:51`). Question, approval, progress, done and stub schemas are explicit (`viewer/app/card.js:76`, `:90`, `:100`, `:116`, `:125`); the browser renders each (`viewer/pages/thread.js:574`, `:603`, `:656`, `:722`, `:769`). Card storage pins progress and approval, and chat returns cards and pins (`viewer/app/cards.js:22`, `viewer/app/chat.js:242`). Presses enqueue markers to the lead; question/offer presses are single-use (`viewer/app/threads.js:272`). A done card's left-as-is buttons request a stub from the lead (`protocol/app/cards-lead.md:109`).
5. A stub card immediately creates a saved child containing title, summary, parent, dependency and optional commits, but no lead or developed plan (`viewer/app/cards.js:140`, `viewer/app/threads.js:91`). Opening it starts a lead and queues the summary as context; dependency can delay opening until ready unless started early (`viewer/app/threads.js:107`, `viewer/app/routes.js:484`, `viewer/pages/thread.js:229`). The stub lead currently starts at step 1, not at an already approved follow-up plan (`protocol/app/lead.md:378`). The requested automatic new thread is therefore different from automatic execution: the present stub creates the thread but waits for a person to open it.
6. Settings are normalized from hub state and saved atomically; preferences are explicitly validated and returned by the route, rendered and updated by the settings page (`viewer/app/state.js:176`, `viewer/app/settings.js:193`, `:248`, `viewer/app/routes.js:239`, `viewer/pages/settings.js:448`). At session start, settings build role layers, including lead style and selected template, then pass them with the brief to the machine (`viewer/app/settings.js:151`, `viewer/app/sessions.js:266`, `:316`). A per-thread mode would need persistence in the thread and delivery on both initial start and restart, not merely a new request field: `emptyThread` retains only its named fields and restart builds a new lead (`viewer/app/threads.js:20`, `:122`).
7. The app finds a thread slug only if exactly one newly created plan directory exists compared with the default-branch merge base; two new plan directories leave it unset (`viewer/app/views.js:65`, `:99`). PLAN status is read from a `status:` line and mapped to feature groups; the separate viewer list parses frontmatter (`viewer/app/views.js:11`, `:109`, `viewer/server.js:1622`). The app document page and archived-document endpoint allow only MAP, IDEA and PLAN, whereas the standalone plan viewer lists Markdown files (`viewer/pages/doc.js:3`, `:24`, `viewer/app/threads.js:12`, `:205`, `viewer/server.js:1536`, `:1659`). A separate follow-up document needs an explicit access and handoff design.

Not checked: machine-side prompt assembly beyond the hub request, remote merge behavior beyond stub opening, and unrelated provider, security and graph flows.
