# Map: New thread and stub flow

Checked against: `8f8b262c5270c8ae4d38aa0b65feb7e028b53566` (origin/main). Files covered: `viewer/pages/new.html`, `viewer/pages/new.js`, `viewer/pages/new.css`, `viewer/pages/threads.js`, `viewer/pages/thread.js`, `viewer/app/threads.js`, `viewer/app/routes.js`, `viewer/app/cards.js`, `viewer/app/peers.js`, `viewer/app/chat.js`, `connectors/hub-common.js`, `protocol/app/lead.md`, `protocol/app/cards.md`, `protocol/app/cards-lead.md`, `viewer/test/app-new-thread.spec.js`, `viewer/test/app-threads.spec.js`, `viewer/test/app-hub.test.js`, `viewer/test/app-lead-list.test.js`, `viewer/test/app-chat.test.js`.

```text
New thread form -> create thread -> start lead -> send first message -> thread page
                     | attachments
                     -> upload files -> send message with paths -> thread page
lead stub card -> save child without session -> list -> child page -> open -> start lead -> context
```

- The form selects machine and project, offers an optional first message, attachments, Start and import; its CSS lays out the form and stacks actions on smaller screens (`viewer/pages/new.html:15`, `viewer/pages/new.html:26`, `viewer/pages/new.css:5`, `viewer/pages/new.css:31`). `new.js` loads machine-specific saved, found and previous projects, disables Start when no project exists, and accepts picked, pasted or dropped files up to 25 MB each (`viewer/pages/new.js:38`, `viewer/pages/new.js:62`, `viewer/pages/new.js:100`, `viewer/pages/new.js:165`).
- With text and no files, the form posts `message` to `/threads`; with files it posts `title` first, uploads each file sequentially using the returned ID, then posts the text plus `[attached: path]` lines to `/messages`. A failed upload or message leaves the created thread accessible via a link and prevents a duplicate Start (`viewer/pages/new.js:208`, `viewer/pages/new.js:229`). The POST route calls `createThread`, which checks the project on the machine, saves a thread, sets the title from the first line truncated to 60 characters, starts a lead and queues `message` if supplied (`viewer/app/routes.js:613`, `viewer/app/threads.js:44`, `viewer/app/threads.js:60`). Even an empty first message starts a lead (`viewer/app/threads.js:77`).
- Uploads require a valid content length, an unfrozen, unarchived thread and a live lead; the hub streams them to the thread's machine (`viewer/app/routes.js:160`). The messages route likewise rejects an ordinary thread without a live lead (`viewer/app/routes.js:755`). Consequently the existing attachment and first-message sequence cannot write into an unopened stub as it stands.
- A lead's stub card without `adds_to` creates a child with the parent's project, machine, ID and title; card summary becomes `context`, and dependency and commits are stored. It has no sessions (`viewer/app/cards.js:297`, `viewer/app/threads.js:22`, `viewer/app/threads.js:96`). Opening an unready dependent stub without `start_now` marks it waiting; otherwise `openStub` starts a lead and queues `[wc:context stub]` with context and optional commits. Restart includes nonempty context as `stub_summary` (`viewer/app/threads.js:112`, `viewer/app/threads.js:128`). The merge watcher requires a parent for dependent stubs (`viewer/app/threads.js:546`).
- The list links every row to its thread page, marks only stubs with no sessions, and names the parent when waiting; its lean response omits context (`viewer/pages/threads.js:62`, `viewer/pages/threads.js:73`, `viewer/app/routes.js:588`). The unopened page shows context and only renders the parent link when a parent name exists; dependency warnings and ready text nevertheless interpolate that name (`viewer/pages/thread.js:627`). The open button calls `/threads/<id>/open` (`viewer/pages/thread.js:653`, `viewer/app/routes.js:777`). Stub cards in a parent link to the child or addition target (`viewer/pages/thread.js:1461`).
- The transcript parser always replaces a stub marker with `Started from <parent title>`, falling back to `parent thread`; a parentless stub would therefore display a misleading attribution (`connectors/hub-common.js:97`, `viewer/app/chat.js:49`). The thread page expands that context item to show the title and current context (`viewer/pages/thread.js:849`). `cards.md` also describes the marker as “Started from <parent thread>”; lead instructions describe summaries in terms of the originating thread but tell a stub lead to treat the marker as starting context (`protocol/app/cards.md:210`, `protocol/app/lead.md:906`, `protocol/app/lead.md:926`).
- `session leads` includes same-project, same-machine candidate unopened stubs even with no lead, with context as `summary`, `takes_additions: true`, and `waits_on_parent` based on dependency and readiness (`viewer/app/peers.js:12`, `viewer/app/peers.js:44`). A stub card with `adds_to` validates the target's project, machine, candidate status and lack of sessions, then appends a dated source paragraph to its context; this applies based on those fields, not on whether the target has a parent (`viewer/app/cards.js:250`). The lead protocol tells agents to compare candidate summaries and use additions for matching unopened stubs (`protocol/app/lead.md:915`, `protocol/app/cards-lead.md:242`).
- Existing coverage includes new-thread text, attachment order and failure recovery (`viewer/test/app-new-thread.spec.js:40`); child creation, opening, dependency, restart and additions (`viewer/test/app-hub.test.js:667`, `viewer/test/app-hub.test.js:2220`, `viewer/test/app-hub.test.js:2273`); list and child UI (`viewer/test/app-threads.spec.js:114`, `viewer/test/app-threads.spec.js:632`); discovery (`viewer/test/app-lead-list.test.js:34`); and parent transcript attribution (`viewer/test/app-chat.test.js:123`).

Not checked: machine-side upload storage and cleanup, all provider-specific transcript parsers, handoff and archive behavior beyond the guards above, and unrelated screens and tests.
