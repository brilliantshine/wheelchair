## Flow

1. A graph node or edge is normalized with `origin: proposed` and `was: null` if absent; canonical output sorts entries by id and explicitly writes both fields (`viewer/server.js:108-145,193-194,310-311`). GET parses and validates disk data before returning it, with the raw file's hash (`viewer/server.js:398-403,1640-1661`).
2. The page selects entries by click, marquee or group selection; approve/reject buttons apply a verdict to the effective selection. Bulk actions skip entries already ruled; a single entry can be reversed. Changing a verdict clears `was` (`viewer/index.html:803-864,2369-2372`). Node dragging separately saves positions (`viewer/index.html:867-872,2434-2445`).
3. Page writes queue a cloned graph and hash to PUT /view, re-reading and reapplying the intent after a 409 (`viewer/index.html:498-565`). The server checks authentication, registration and hash, then structural identity; it permits position and verdict changes, permits clearing `was` only with a verdict change, and allows at most one reversal (`viewer/server.js:1500-1540,1614-1637`).
4. Agent PUT /graph checks authentication, registration and hash, validates, checks agent rules and containment, lays out and atomically writes canonical bytes; run pictures retain positions if layout inputs have not changed (`viewer/server.js:1570-1610`). New or proposed entries cannot receive verdicts; rejected entries cannot change or disappear, agreed entries must remain identical or reset to proposed with `was: agreed`, and landed reset records cannot be cleared by agents (`viewer/server.js:523-565`). Run node `task`, `status`, `needs`, and positions are exempt from preservation comparison, while /view cannot edit run fields (`viewer/server.js:371-383,1500-1512`; `protocol/graphs.md:856-865`).
5. Removing or retargeting a container walks its old subtree: verdicts refuse `container-orphan`; unreadable children refuse `container-unreadable-child`. Cycle detection is separate (`viewer/server.js:568-627,1585-1595`). Planning rereads rejections and requires prose accounting before review; approved-spec Mermaid leaves rejected entries out (`protocol/planning.md:87-98,206-211`; `protocol/diagrams.md:84-90`). The older implementation stage turns rejected run choices into follow-up tasks (`protocol/implementation.md:219-229`); the app lead still directs approved or struck proposals to the graph page (`protocol/app/lead.md:364-371`).

```text
agent graph -> validate -> preserve verdicts and child subtrees -> layout -> disk
                                                                      |
page <- GET graph <- disk <- PUT /view <- select entries and approve or reject
```

## Consequences

- `bad-origin-value`, `agent-verdict`, `preservation-rejected`, `preservation-agreed`, `bad-was`, `bulk-not-additive`, and the two verdict-dependent container refusals have distinct checks (`viewer/server.js:208-209,317-318,532-562,600-625,1531-1540`). `bad-origin` is instead HTTP origin authentication and remains a separate concept (`viewer/server.js:1422-1434`). Positional prose, cycle checks, registration, stale hashes and run layout also serve independent purposes (`viewer/server.js:489-506,568-584,1577-1598`).
- Rendering uses verdict classes, strikethrough, color-coded arrow markers, data attributes, reset dots, legend and button hints (`viewer/index.html:9,115-123,176-187,255-266,1334-1339,1513-1556,1639-1646,1679,1781-1798,1825-1838,1988-2006`). Run status shares some colors and overrides box styling (`viewer/index.html:135-151`). Graph card iframes reuse this page rather than independently interpreting graph verdicts (`viewer/pages/thread.js:177-188,644-656`). The `origin` in transcript human detection is unrelated (`viewer/app/chat.js:146`).
- Current schema requires the three allowed origin values; groups and explanations have no verdict (`protocol/graphs.md:113-120,189-193,275-279,634-669`). If normalization and ordered output stop recognizing these fields, existing JSON still parses because unknown keys are dropped, but the next write loses them; archived JSON bypasses that normalization and the page currently relies on `origin` for arrow marker IDs (`viewer/server.js:157-160,193-194,310-311,134-145`; `viewer/app/threads.js:216-229`; `viewer/index.html:1334-1339,1679`). Compatibility therefore needs both live and archived rendering considered.
