## Hook signals and limits

The machine creates Claude's per-session settings at launch, registering `Stop`, `Notification`, `StopFailure` and the statusline; Codex gets a `notify` command in argv (`machine/adapters/claude.js:55-60`; `machine/adapters/codex.js:50`). `install.sh` removes the retired seen hook; it does not register these session hooks (`install.sh:130`). Claude sends hook JSON on stdin, Codex appends notify JSON as an argument; without a session token the bridge exits (`machine/hook.sh:6-24,36`). Translation accepts only Claude Stop, permission Notification, StopFailure and rate-limit status input, or Codex `agent-turn-complete`; all other payloads are dropped (`machine/adapters/claude.js:66-67`; `machine/adapters/codex.js:54-55`; `machine/lib/hook-post.js:13-17`). None of the hooks wheelchair registers emits per-tool steps today.

Claude documents `PreToolUse` with `tool_name`, `tool_input`, and `tool_use_id`; `PostToolUse` adds `tool_response` and optional `duration_ms`; `PostToolUseFailure` has the same identity/input plus `error`, optional `is_interrupt` and `duration_ms`. Hook receipt times would be needed for absolute start/end. Parallel calls must be paired by ID. Invalid calls can bypass both hooks; permission denial has no failure hook, and cancelling a running tool does not fire that failure hook. See [Claude hooks reference](https://code.claude.com/docs/en/hooks#pretooluse), including its PostToolUse and PostToolUseFailure sections.

Codex's configured `notify` is turn-complete only (`machine/adapters/codex.js:50,54`). OpenAI's [migration reference](https://github.com/openai/skills/blob/main/skills/.curated/migrate-to-codex/references/differences.md) describes experimental `PreToolUse`/`PostToolUse` hooks for shell commands only, requiring `codex_hooks`; its [hook tests](https://github.com/openai/codex/blob/main/codex-rs/core/tests/suite/hooks.rs) show `tool_name`, `tool_input.command`, `tool_use_id`, and post `tool_response`. The current [registry](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/registry.rs) runs the post hook on successful tool results; it is not a general failure signal. The migration reference may lag current upstream: establish the installed CLI's version and actual coverage before relying on it. There is no general per-tool end/failure signal in wheelchair's current Codex notify, and no evidence here that hooks cover every tool. Timestamps and failures cannot be assumed from the shown hook payload.

## Context and copies

Claude's [statusline input](https://code.claude.com/docs/en/statusline#available-data) exposes `context_window_size`, `used_percentage`, `remaining_percentage` and `current_usage` (input, cache and output counts); values can be null before the first response or after compaction. The current statusline forwards only when `rate_limits` exists, throttles to once per minute, and the adapter extracts only account rate-limit windows, not context (`machine/lib/statusline.js:8-21`; `machine/adapters/claude.js:66-67`). Claude assistant transcript `message.usage` can contain input, output and cache token counts; these are request usage, not by themselves a reliable window size or current fill. The statusline carries the direct denominator and calculated percentage.

Codex rollout `token_count` events can carry `payload.info.last_token_usage`, `total_token_usage` and `model_context_window`; upstream's [token usage implementation](https://github.com/openai/codex/blob/main/codex-rs/tui/src/token_usage.rs) distinguishes latest active context from accumulated session usage. The machine scans new complete rollout lines at turn end for `rate_limits` only (`machine/adapters/codex.js:31-48,53-55`); no context value is forwarded. The machine copies complete JSONL lines without selecting fields, deduplicates identical lines, and serves them on demand; Claude can be discovered before Stop, while Codex binds its rollout only after a matching first turn-complete notification (`machine/service.js:724-777`; `machine/adapters/claude.js:65`; `machine/adapters/codex.js:31-40,53`). Thus usage fields present in the source are retained in the copy, subject to discovery, complete lines and content deduplication; copying does not itself extract or push context. The hub reads copies via `/v1/sessions/:name/transcript`, caching the last successful fetch (`viewer/app/chat.js:206-222`; `machine/API.md:19`).

## Machine to hub and question path

The post helper authenticates with the session token to `/v1/agent/hooks` or writes an atomic local event spool (`machine/lib/hook-post.js:18-30`; `machine/service.js:1207`). The service binds the managed session and thread, then emits or prepares the event (`machine/service.js:836-866`); drain sends ordered files with delivery IDs to `/api/machine/events`, retries outages and moves 4xx refusals aside (`machine/service.js:779-835`; `machine/API.md:31,40-41`). Hub event processing deduplicates delivery IDs and updates session turn/hold state (`viewer/app/sessions.js:408-484`). Cards take the parallel `/v1/agent/cards` and `/api/machine/cards` path, with a durable machine spool (`machine/service.js:1177-1199`; `viewer/app/cards.js:55-58,115-154`). The browser polls `/wheelchair/api/agents` every five seconds; the machine does not push directly to the page (`viewer/app/routes.js:64`; `viewer/pages/agents.js:53-54`; `viewer/app/API.md:158`).

Workers and sub-leads can post a `message` to a named session; the hub stores `session` as sender and `to` as recipient, queues `[wc:from <sender>]` text and waits for the target to be ready and turn-ended (`viewer/app/cards.js:11-20,115-125`; `viewer/app/sessions.js:327-348`). Successful delivery is recorded with recipient, text, source and time; sent history is capped at 500 (`viewer/app/sessions.js:353-385`). A lead alone can post a question for Collin (`protocol/app/cards.md:20-36,94-107`; `viewer/app/card.js:24-27,187-188`); a card stores its author and time, but there is no question ID joining earlier messages and the lead's question (`viewer/app/cards.js:11-20,115-125`). The inferred `waiting_on` heuristic is not proof a message is a question, nor that separate messages are the same question (`viewer/app/agents.js:40-53`). Amber path attribution therefore needs new explicit correlation or an acknowledged inference.

## Screen and tests

The tree and selected panel are created by `branch` and `render`; the side panel currently has status, model, effort, machine, duration, terminal and brief, while `TermView` mounts in a separate bottom panel (`viewer/pages/agents.js:7-16,48-54`; `viewer/pages/agents.html:14-19`). New activity, latest four steps, normal-duration comparison and context would need data exposed by the Agents API and rendered there; none is computed today (`viewer/app/agents.js:14-60`; `viewer/pages/agents.js:48-54`).

Existing coverage includes hook configuration, offline events, turn binding and spools (`machine/test/service.test.js:199-246`), statusline and failure translation (`machine/test/accounts.test.js:38-47`), copy deduplication, partial lines and concurrent reads (`machine/test/service.test.js:246-247,375-399`), usage forwarding (`machine/test/service.test.js:891-922`), and agent tree and message waiting (`viewer/test/app-agents.test.js:20-106`). Browser screen and terminal coverage lives in `viewer/test/app-views.spec.js` and `viewer/test/app-threads.spec.js`; question presses and queues are exercised in `viewer/test/app-hub.test.js:196-219`.
