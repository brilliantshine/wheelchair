# Map: lead reserve and review count

```text
Settings -> provider orders and reserve -> session placement -> reviewers -> builders -> verifier
                                                  | unavailable family
                                            fallback or wait
```

The detailed placement flow and test pointers are in `docs/maps/app-provider-placement.md`. This map is checked against `e8911e23e46df47f7264aacd9d8d4cc9d5af3133` (origin/main).

1. Lead order and worker order are independent, and `any` expands to worker order; order can omit a provider. Today both moving a provider behind others and the per-role margin are tied to Claude's `saveForLeads` flag, not lead order (`viewer/app/balancer.js:28-46`; `viewer/app/providers.js:3`). The checkbox and margin are independent, and saved settings use the Claude-named key (`viewer/app/settings.js:25-27`; `viewer/pages/settings.js:1136-1149`). Deciding what “selected” means when lead order ends in `any`, a provider is signed out, or a model cell is unused matters to the new behavior (`viewer/app/settings.js:200-201`; `viewer/app/balancer.js:28-41`).
2. Ready fails when the other CLI is installed but signed out, even with a working lead family; if it is absent, Ready skips it (`viewer/app/ready.js:38-58`). Reviewers and verifiers can drop `--not-provider` and use the only eligible family with a note; workers cannot drop an exclusion, and a worker explicitly requesting a signed-out provider waits unless that provider is below its margin (`viewer/app/balancer.js:48-59`; `viewer/test/app-balancer.test.js:66-75`). Critical work explicitly requests Claude (`protocol/app/sub-lead.md:63-69`), so a GPT-only setup can wait indefinitely. A margin can also exclude the only signed-in family, leaving non-leads waiting (`viewer/app/balancer.js:35-46,58-72`).
3. App plan review always starts two fresh reviewers, intent preferring Claude and mechanics avoiding the first provider; when the first waits, the second gets no constraint (`protocol/app/lead.md:176-185`). A small fix and a post-done fix each ask for one verifier avoiding the lead's provider (`protocol/app/lead.md:100-105,287-293`). The sub-lead asks for one verifier if builders used one provider, but two if both built; preference fallback can reduce the latter to one (`protocol/app/sub-lead.md:168-176`). Reviewer and verifier roles define their work rather than choose counts (`protocol/app/reviewer.md:1-21`; `protocol/app/verifier.md:1-8`). Existing Settings only selects role tiers, and labels describe two reviewer providers and a checker different from the builder (`viewer/app/settings.js:27`; `viewer/pages/settings.js:366-367`). A configurable single reviewer and verifier therefore reaches both protocol instructions and settings delivery, not just placement.
4. The separate CLI workflow still requires two review lenses, using two same-family reviewers for one family; GPT reviewers are sequenced (`protocol/plan-review.md:49-52,89-95`). CLI verification uses one cross-family verifier per implementing family, or same-family Heavy when only one family is available; mixed-family work still gets two dispatches even if only one family survives (`protocol/verification.md:28-41`). The earlier one-account work explicitly retained these distinctions and attribution, and treated an announced authentication failure differently from a silent failed lane (`docs/plans/one-account-setups/PLAN.md:159-186`). The app's role protocol is separate from those CLI stage files (`protocol/app/AGENTS.md:3-5`), so a count setting needs an explicit scope decision.
