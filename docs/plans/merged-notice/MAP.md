## Flow today

```text
lead opens PR -> done card with PR URL -> hub stores thread cards -> chat derives latest URL
                                                                 -> thread page links PR
hub timer -> waiting dependent stub -> gh on hub -> merged parent -> stub ready
thread page -> confirm archive -> hub -> thread's machine -> stop and clean up -> save result
```

1. Small fixes push, open a PR and post `done`; features do the same after verification. An after-done fix on an open PR posts another `done` with the PR link when it lands; a fix that misses a merge instead becomes a stub. Each stub starts its own PR (`protocol/app/lead.md:105-115,292-300,303-338`). The required `done.pr_url` is only checked as nonempty text (`viewer/app/card.js:114-119`); the hub stores the card in `thread.cards` (`viewer/app/cards.js:85-86`; `viewer/app/state.js:113-130`). Chat computes `pr_url` from the newest `done` with a truthy URL, and `parent_pr_url` separately from the parent; these are response fields, not a separately maintained PR status (`viewer/app/chat.js:242-268`). A dependent stub with no `done` yet therefore has the parent's URL in chat, not its own.
2. The hub already asks GitHub: `pollWaiting` uses `gh pr list --head <parent.branch> --state merged --json number`, with `cwd` set to the child's project path, to mark unopened dependent stubs ready; errors, including missing `gh` or an unavailable remote, leave them waiting (`viewer/app/threads.js:334-355`). This subprocess runs on the hub, even though project existence is checked on the selected thread machine (`viewer/app/threads.js:41-64`). The machine service also runs `gh pr create` in the calling session's worktree for `wc.js git pr` (`machine/service.js:849-870`); the lead directly runs `gh pr view` in after-done work (`protocol/app/lead.md:309-313,325-334`). Ready checks only the thread's agent CLI and its login, not `gh` (`viewer/app/ready.js:29-58`); GitHub authentication on the hub is not guaranteed by that gate.
3. `Hub.init()` starts unref'd timers: dead sessions every 10 seconds, queue retries and quiet checks every five seconds by default, waiting stubs every minute, and idle usage polling every minute plus an initial 30-second delay. Waiting stubs are also checked at startup (`viewer/app/hub.js:40-45,48-74`). The stub poll reloads each thread under `withThread`, changes its fields, and saves; the lock covers read through save and state uses atomic JSON replacement (`viewer/app/threads.js:334-355`; `viewer/app/hub.js:85-99`; `viewer/app/state.js:21-29,113-119`). Usage polling separately throttles account attempts to nine minutes and calls a selected machine (`viewer/app/usage-poll.js:7-43`).
4. The app makes system `needs` cards directly with `addCard`: stuck and permission events set `system: true` and a session, and clear the card when the hold clears; the dead-session sweep posts “Sessions ended”, closed when a lead restarts (`viewer/app/sessions.js:427-455,597-617`; `viewer/app/threads.js:139-150`). `addCard` assigns id, time, session, `answered` and `system`, then appends to the thread; callers save the thread (`viewer/app/cards.js:11-28`; `viewer/app/sessions.js:450-455,617`). Chat returns unreplaced cards and the page renders them in the conversation; system needs cards get a terminal link only when associated with a session, and do not get lead-needs buttons (`viewer/app/chat.js:264-269`; `viewer/pages/thread.js:289-295,496-502,632-653`). Agent cards pass `card.js` kind, field and role validation before acceptance (`viewer/app/card.js:10-40,70-140,142-155`; `viewer/app/cards.js:38-48`), while direct `addCard` does not invoke that validator. A new app-only kind needs a browser rendering and an action path; validator/role changes are needed if agents are to submit it, but adding it there alone does not make the app post it. Ordinary card presses require a live lead and enqueue a message, so an archive action needs its own direct handling (`viewer/app/threads.js:266-270,287-319`).
5. The page's Archive button expands to Confirm archive and Cancel, with a warning that sessions stop and the worktree is removed; confirmation posts to the archive route and repolls (`viewer/pages/thread.js:159-164,213-215`; `viewer/app/routes.js:476-477`). `hub.archive` takes the thread lock; archive closes asides, requests cancellations, calls the thread's machine, records the result and marks sessions dead and the thread archived (`viewer/app/hub.js:148`; `viewer/app/threads.js:158-195`). The machine stops sessions, commits dirty work where possible, removes clean worktrees and uploads, and reports retained worktrees (`machine/service.js:619-683`). A rebase in progress or failed upload removal leaves the thread unarchived and creates a system needs card so archive can be retried (`viewer/app/threads.js:177-195`).

## Constraints on the idea

- The current GitHub poll watches dependent stubs, not each thread's own PR, and identifies a PR by parent branch rather than the stored URL (`viewer/app/threads.js:334-355`; `viewer/app/chat.js:254-262`). A new check must select the thread's own PR and avoid producing repeated notices; existing `addCard` only replaces its three singleton kinds (`viewer/app/cards.js:9-28`).
- The hub may not have the chosen machine's project path, `gh`, credentials or network access. Existing poll errors are swallowed and mean no ready update, so copying it can silently miss a merge (`viewer/app/threads.js:41-64,343-354`). The `done` URL validator does not establish that the text identifies a GitHub PR (`viewer/app/card.js:42,114-119`).
- A merge can race with an after-done fix: the lead distinguishes a merge containing the pushed commit from one that missed it, and creates a stub for the latter (`protocol/app/lead.md:325-335`). Archive stops sessions and can commit and remove worktrees, so the button's timing and confirmation matter (`machine/service.js:625-662`; `viewer/pages/thread.js:159-164`).

## What I did not look at

GitHub API behavior or rate limits, actual machine credentials and filesystem availability, all tests and historical thread data, and unrelated card kinds or page styling.
