# Map: Agents, terminal and session signals

Checked against: `3065046af16a1f6b2822d308b5c32431ca39a449` (origin/main)
Files covered: `viewer/pages/agents.html`, `viewer/pages/agents.js`, `viewer/pages/terminal.html`, `viewer/pages/terminal.js`, `viewer/pages/views.css`, `viewer/app/agents.js`, `viewer/app/routes.js`, `viewer/app/sessions.js`, `viewer/app/cards.js`, `viewer/app/card.js`, `viewer/app/threads.js`, `viewer/app/state.js`, `machine/service.js`, `machine/hook.sh`, `machine/lib/hook-post.js`, `machine/lib/statusline.js`, `machine/adapters/claude.js`, `machine/adapters/codex.js`, `machine/adapters/agy.js`

## Flow

```text
thread and session records -> /api/agents -> nested Agents cards -> terminal link
message card -> recipient queue -> tmux submission -> recipient turn
CLI hook -> machine translation and spool -> hub event -> session state
terminal pane poll <- hub <- machine capture-pane
terminal input -> hub -> machine send-keys -> tmux
```

Agents fetches `/wheelchair/api/agents` and the thread list every five seconds, using thread timestamps to sort leads (`viewer/pages/agents.js:99-107`; `viewer/app/routes.js:64`). The hub reads unarchived threads, chooses the newest lead, attaches nonleads by `started_by` (old leads' children move to the newest lead, missing parents fall back to it), cuts cycles, and prunes non-live leaves (`viewer/app/agents.js:3-27`). It probes registered machines for reachability (`viewer/app/agents.js:31-40`). The page recursively renders nested details, roles, session names, status, wait labels, and for live non-capacity-waiting nodes a local or SSH tmux attach command, copy button and terminal link (`viewer/pages/agents.js:10-12,25-91`; indentation and status CSS `viewer/pages/views.css:109-119`). Finished non-live leaves and wholly ended trees therefore do not survive this view.

A thread stores the checked project path (`viewer/app/threads.js:20-38,43-64`). Hub session creation stores role, starter, timestamps and lifecycle fields, then merges the machine's response; its start request carries `brief`, project path and basename (`viewer/app/sessions.js:140-146,192-228,251-273`). Machine records have no independent project or brief field: the brief becomes `pending_initial`, which the machine clears before submit (`machine/service.js:488-499,530-540`). The start response is merged into the hub record, so it may retain a snapshot of that combined first message; it is not a separate, consistently available brief field (`machine/service.js:1108`; `viewer/app/sessions.js:251-264`). A capacity-waiting session temporarily keeps `pending_start` with the input (`viewer/app/sessions.js:140-147`); an unanswered start can temporarily keep the start body (`viewer/app/sessions.js:238-246`). The generic JSON persistence and public-session spread permit adding a project field, but the existing agents response does not include `thread.project` at the lead level (`viewer/app/state.js:18,127-130`; `viewer/app/agents.js:11-13,27`). Results are stored as cards with their author, not copied into a session summary; reviewer/verifier results are synthesized from last assistant text (`viewer/app/cards.js:115-133`; `viewer/app/sessions.js:276-300`).

A message card identifies a recipient and text; hub stores it with its author and enqueues a marked message to that recipient, then delivers when ready and idle, recording sent text (`viewer/app/card.js:39,71`; `viewer/app/cards.js:115-125,139-152`; `viewer/app/sessions.js:317-329,332-377`). Only leads may post a question card (`viewer/app/card.js:24-40`). No question linkage is recorded by this path: a later lead question is a separate card, and message text has no question or parent-card identifier. `waiting_on` is not a question state: on each Agents read it is computed for a turn-ended session as *all its live unfinished children*, and is otherwise empty (`viewer/app/agents.js:11-14`). It cannot identify a child waiting for its parent or the route of a question.

The terminal page loads vendored xterm and binds it to a page element (`viewer/pages/terminal.html:6-20`; `viewer/pages/terminal.js:94-103`). It polls a colored visible pane snapshot every 500 ms, replaces the display, and sets xterm scrollback to zero (`viewer/pages/terminal.js:94-103,109-139`; `viewer/app/routes.js:482-491`; `machine/service.js:347-353,1126-1132`). xterm `onData` is unconditionally split into tmux keys; unknown multi-character escape sequences are split into individual characters (`viewer/pages/terminal.js:32-70,72-86,103`). If xterm produces a mouse/scroll escape sequence, this conversion can send its components as literal keys; the code does not distinguish input origin. The exact triggering mouse mode was not reproduced. There is no browser history supplied by the current snapshot endpoint. On-screen buttons also send keys, and the hub forwards to managed tmux `send-keys`; Enter marks the turn busy (`viewer/pages/terminal.js:105-107`; `viewer/app/routes.js:493-517`; `machine/service.js:589-593`). The page is ordinary HTML/JS around an element, so it can be embedded or refactored into a panel, but its fixed IDs, URL parameters, focus, polling and input handlers are currently page-global (`viewer/pages/terminal.html:12-29`; `viewer/pages/terminal.js:6-16,94-107,137-139`).

Claude is launched with per-session settings defining Stop, Notification, StopFailure and a status line; Codex receives `notify` on its command line; Antigravity (`agy`, the Gemini provider here) installs a Stop hook in its hooks file (`machine/adapters/claude.js:55-66`; `machine/adapters/codex.js:50-54`; `machine/adapters/agy.js:9-33,39-53`). `hook.sh` receives Claude/agy JSON on stdin and Codex notify JSON as an argument; `hook-post.js` translates with the adapter, authenticates to the local service or spools (`machine/hook.sh:6-36`; `machine/lib/hook-post.js:15-30`). The machine associates the authenticated session and thread, enriches usage and relays events; hub records readiness, turn end, failure, permission prompts and account readings, then uses turn end to deliver queued work (`machine/service.js:806-835`; `viewer/app/sessions.js:396-455`). Claude prompt clearing is detected from the pane (`machine/service.js:570-577`). These are not per-tool histories.

For tool events, Claude documents `PreToolUse`, `PostToolUse` and `PostToolUseFailure`, including tool IDs; these would have to be added to the generated settings and translated/transported by the bridge ([Claude hook reference](https://code.claude.com/docs/en/hooks); `machine/adapters/claude.js:55-67`; `machine/lib/hook-post.js:15-17`). Codex documents `PreToolUse` and `PostToolUse` through hooks configuration, distinct from the current `notify`: user/project `hooks.json` or inline config, with trust review for non-managed definitions. Its documented coverage has exceptions, and `PostToolUse` includes failed shell commands, so it is not evidence that every kind of failure or every tool is covered ([Codex hooks](https://learn.chatgpt.com/docs/hooks); `machine/adapters/codex.js:50-55`). Installed CLI versions and actual payloads were not tested.

The Claude status-line handler reads only account five-hour usage and forwards rate-limit payloads, and its adapter extracts five-hour/week windows (`machine/lib/statusline.js:8-21`; `machine/adapters/claude.js:66-67`). Codex scans rollout lines at turn end for rate-limit windows, not context use (`machine/adapters/codex.js:31-48,55`). Antigravity's usage parser returns null (`machine/adapters/agy.js:39-53`). These are account limits, not session context fullness; the inspected hub and Agents path does not expose a context percentage.
