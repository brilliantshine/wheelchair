# T4 report — the hub and the thread page for sudo cards

## What I changed

- `viewer/app/card.js`: `sudo` joins `shown` and `roles` (lead only). `fields.sudo` is `command` (≤ 4096 bytes, no NUL), `does`, `why`. `validate(kind, card, role, {machine})` takes an extra field set (`request_id` 32 hex, `url` starting `https://`, `editable` array of strings) only when the hub accepts a machine-posted card. `card.js sudo` never passes `machine`, so an agent sending those fields is refused as an unknown field.
- `viewer/app/cards.js`: `acceptCard` validates with `{machine:true}`, refuses a repeated `request_id` (422), stores the card with `state: 'waiting'` and writes `thread.sudo_index[request_id] = card id` in the same save. New `applySudoState(hub, thread, request_id, status)` (rank `waiting` < `running` < terminal; ignores `waiting` and same-or-older; sets state and `exit_code`/`output`/`truncated`/`reason`; on the first terminal state queues one lead message through `hub.enqueue`, in the same save). New `sudoOutcome(hub, body)` (body check, finds the thread by index, 409 if none, runs the handler under the thread lock) and `validSudoStatus`.
- `viewer/app/routes.js`: `POST /api/machine/sudo-outcome` in `handleMachine`; `sudo_index` left out of `?view=list`.
- `viewer/app/threads.js`: `pressSudo` for `talk` (value fixed to `sudo request`, card stays `waiting` and unanswered) and `decline` (synchronous machine call; any valid answer goes to `applySudoState`; unreachable, timeout, non-2xx or malformed answer is `502 "Couldn't reach <machine> to decline. Try again."` with nothing saved). 409 once the card is not `waiting`; other actions 400.
- `viewer/app/machine-client.js`: `sudoCancel(machine, request_id)`: `POST /v1/sudo/<id>/cancel`, 10 s overall deadline (`sudoCancelTimeout` is overridable for tests).
- `viewer/app/chat.js`: the chat bubble for `sudo ran:` keeps only its first line.
- `viewer/pages/thread.js`, `thread.css`: the `sudo` card (command in a wrapping monospace block, editable warning above it, does/why, the three controls while waiting, "Declining…", running, each outcome, the decline error beside unchanged buttons). All text via `textContent`; no input of any kind.
- `viewer/app/API.md`, `protocol/app/cards.md`: documented (kinds table, `### sudo` section, press forms).
- Tests: new `viewer/test/app-sudo.test.js` (18 tests) and `viewer/test/app-sudo.spec.js` (6 tests × phone/desktop × Chromium/Firefox). No existing test needed a kinds-list edit.

## Choices

- `applySudoState` takes `hub` as a first argument (`applySudoState(hub, thread, request_id, status)`) because it saves and enqueues; it lives in `viewer/app/cards.js`.
- `sudoOutcome` is called from `routes.js` via `require('./cards.js')`, not through a `Hub` method, to keep `hub.js` (not in my boundary) untouched.
- Idempotence for `delivery_id` duplicates comes from the rank rule alone; I do not record the `sudo-outcome` `delivery_id` anywhere, so a machine reusing one id for different states is still applied. The body must carry a non-empty `delivery_id` (400 otherwise).
- A second card with an already-indexed `request_id` is refused with 422 (viewer/app/cards.js), except an exact redelivery with the same `delivery_id`, which the existing check answers 200.
- `sudo-outcome` `ran` requires an integer `exit_code`; `waiting` as an outcome state is a 400 (the handler itself also ignores it).
- Lead picked for the message: the latest live lead, else the card's posting session, else the latest lead; with none, the state is saved and nothing is queued.
- Both presses on a non-`waiting` sudo card are 409; any action other than `talk`/`decline` is 400. `talk` ignores the sent `value` and always sends `sudo request`.
- The decline error text uses `thread.machine` as `<machine>`, and the page shows it without the usual "Could not send:" prefix for sudo cards (`viewer/pages/thread.js`).
- The Decline answer is checked with the same status validator as the outcome body; a `waiting` or malformed answer counts as unreachable. A `running` answer is applied (card shows Running…, no lead message).
- The "Declining…" state is page-only, kept in a `declining` map and part of the chat redraw signature.
- `chat.js` bubble for `sudo ran:` is cut to its first line so the output does not appear as a bubble from Collin.
- `sudo_index` is left out of the `?view=list` summaries (`viewer/app/routes.js`).
- Tests use their own front for the fake machine (proxy for everything except `/v1/sudo/`) so `helpers/app-machine.js` stays untouched; the browser Decline-error test relies on the stock fake machine having no sudo route.
