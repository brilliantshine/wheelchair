# T3 — blocked after repeated focused-test failure

The focused gate failed twice in `failed readying becomes ready after a later successful sync`: expected `failed`, found `waiting`. The first adjustment awaited tasks currently in the readying map; the second run failed identically, so I stopped iteration under the brief's guardrail. The 10 ms launch timeout may expire before asynchronous context lookup inserts a task in that map; this is a hypothesis, not a verified diagnosis. The machine suite also reproduced this new failure. The implementation and coverage remain unverified and need follow-up before acceptance.

## Changes

- `machine/service.js:853`: computes the git common directory and supplies wrapped entries to the adapter for eligible WSL tool roles; `machine/service.js:872` writes the Claude config atomically and `machine/service.js:948` removes both artifacts on failed start; `machine/service.js:973` removes the config on stop, including bare-service fixtures.
- `machine/service.js:478`: scans Antigravity, Claude MCP and ready directories together, filtering new-directory entries before the single tmux query and protecting per directory.
- `machine/lib/win.js:113`: adds queued ready-file operations and per-attempt tokens; `machine/lib/win.js:155` publishes successful reconciliation and `machine/lib/win.js:202` handles waiting and failures; `machine/lib/win.js:276` queues invalidation on stop. Existing Windows-tool readying already creates/reconciles even when the copy exists.
- Code read matched the brief's existing adapter, wrapper and proxy contracts. `machine/test/win-tool-ready.test.js`, `machine/test/win-tool-service.test.js` and `machine/test/win-tool-sweep.test.js` add the cases below.

## Validation mapping

1. `WSL Claude writes wrapped config and waiting before tmux; stop removes both`: service fake tmux reads ready file at `new-session`; also checks Claude config contents, mode and stop removal.
2. `existing copy remains waiting until a post-start reconcile completes`: gated existing-copy reconcile and ready-file modes.
3. `failed readying becomes ready after a later successful sync`: **failed twice before the later-sync assertion**, so this required behavior remains unverified.
4. `context errors before a readying task write failed`: context error before task creation.
5. `stop removes ready file and a late readying result cannot recreate it`; `stop serializes behind an in-progress temporary ready write and removes it`: late result and deterministic write gate.
6. `tmux failure removes both files and late readying cannot recreate them`; `cancelled start removes both files and late readying cannot recreate them`: two failed-start paths.
7. The service test in item 1 covers the WSL Claude entry, argv, mode, waiting and stop removal.
8. `sweep removes dead files and keeps starting and live files in each directory without agy-tools`; `only ordinary settings files do not call tmux or remove anything`: stale, starting, live, absent directory and no-query cases. The machine run includes unchanged `kimi-turns.test.js` (`fatal stop refuses input and waits for confirmed absence` passed).

The late-result tests should be reviewed for whether their gate has reached the readying task before start returns, given the timing failure above.

## Choices

- `machine/lib/win.js`: use UUID attempt tokens and a per-name promise queue; log ready-file publication errors without turning a completed reconcile into a failed sync.
- `machine/lib/win.js`: initialize `waiting` in `beforeLaunch` before starting its timeout, passing the token into `prepareLaunch`; direct `prepareLaunch` calls also initialize it.
- `machine/service.js`: use a UUID temp name for the Claude file and remove the temp in a `finally` block.
- `machine/test/win-tool-ready.test.js`: intercept the shared `fs/promises.writeFile` temporarily to deterministically pause an in-progress ready-file write.
- `machine/test/win-tool-service.test.js`: use a direct `MachineService` fixture with fake tmux/systemd and fake Windows executables, stubbing service persistence and readiness polling.
