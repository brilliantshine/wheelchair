# R5-1 report

## Changed
- `viewer/pages/project-tools.js`
  - Gap 2: setting/header rows keep `rawName`/`rawValue` and a `dirty` flag (set by name, mode, value, prefix, key-name input). `buildEntry` copies untouched rows exactly as read; only dirty and new rows are built from the form. Fields `command`, `url`, `args` are copied unless touched; `type` changes only when the kind changes; env/headers are rebuilt only when a row was touched, added or removed. Trim-and-compare (`rowsSame`, `f.orig`) removed. Edited/new row names with leading/trailing whitespace are refused ("<name> has a space at the start or end."); key names are no longer trimmed.
  - Gap 3: `applyKeys` refreshes the open editor's key rows (`formState.refreshers`), so the value field follows key set/unset, keeping what was typed.
  - Gap 4: `lockBtn` helper (disabled while loading or busy, handler refuses too, tagged `data-lock`) used for Save, Start over, key Set/Add/Remove and its confirm, and the failed-reload Reload button; `applyLock`/`setBusy` disable every `data-lock` control (including the one in the status area) and both selects; select change handlers refuse while locked.
- `viewer/test/app-project-tools.spec.js`: four new tests (one per brief item). Five stale-reply tests drove the picker while it was locked (forced past `disabled`); with the handler now refusing, that state is unreachable, so they now assert the pickers are locked during a pending save, read, post-save reload, remove-key and machine load, and that the reply lands.

## Choices
- Tool name (not a row name) is still trimmed; only row names refuse whitespace (viewer/pages/project-tools.js).
- Typing in the new-key value field does not mark a row dirty (it is not part of the entry).
- Rewrote five stale-reply tests as lock assertions because the brief's handler refusal makes their forced-change scenario impossible (spec file).
- Local-only confirm in a tool card ("Yes, remove <tool>") still uses a plain button, as it starts no request.
