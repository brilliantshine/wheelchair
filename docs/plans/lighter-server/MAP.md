## Thread reads, writes, and archive

`allThreads` lists the thread directory, reads and parses every `.json` file in parallel, drops missing files and sorts by `updated_at`; it does not filter archived records or lock a coherent snapshot (`viewer/app/state.js:134`). A direct `thread(id)` reads from disk. `save` and `updateThread` both queue by file, set `updated_at` and atomically replace the JSON; `updateThread` reads and modifies inside that queue (`viewer/app/state.js:21`, `viewer/app/state.js:51`, `viewer/app/state.js:107`). `withThread` is a separate in-process per-id queue spanning the read, remote call, mutation and save; it is not a cross-process lock (`viewer/app/hub.js:114`). `hub.thread()` can itself save a missing provider migration (`viewer/app/hub.js:111`).

Creation, session/events/queues, cards, asides, thread lifecycle, handoff/import, slug/status discovery, quiet and routes save through `hub.save` / `saveWithLeadName`; card acceptance also uses `updateThread` (`viewer/app/threads.js:20`, `viewer/app/sessions.js:193`, `viewer/app/cards.js:57`, `viewer/app/asides.js:91`, `viewer/app/handoff-ops.js:127`, `viewer/app/views.js:54`, `viewer/app/quiet.js:54`, `viewer/app/routes.js:512`). Failed handoff creation can unlink the thread file directly (`viewer/app/handoff-ops.js:45`). Sent history is an append-only `.sent.jsonl` sibling, not an allThreads record (`viewer/app/state.js:91`). Tests and external edits can write the files outside the hub's in-process queues (`viewer/test/helpers/app-views-setup.js:1`; `viewer/app/state.js:54`). A cache that shares mutable objects or misses create, replace, deletion, migration, or outside writes can return stale data or expose uncommitted mutations; list snapshots currently consist of independently parsed objects (`viewer/app/state.js:107`, `viewer/app/state.js:134`).

Archive stays in the same JSON as `archived: true`; archive first records pending aside cancellations, calls the machine, and leaves `archived: false` if a rebase or failed upload removal needs retry; success also marks sessions not live (`viewer/app/threads.js:197`). Handoff advance can reopen a record (`viewer/app/handoff-ops.js:107`). Archive does not imply the record or its chat disappears (`viewer/app/threads.js:233`, `machine/service.js:925`).

- Timers: aside pump/cancel, dead detection, retry queues and quiet, waiting stubs, merged PRs, retry waiting and limits; idle usage probes can scan twice per candidate, then retry waiting (`viewer/app/hub.js:79`, `viewer/app/sessions.js:698`, `viewer/app/quiet.js:32`, `viewer/app/threads.js:424`, `viewer/app/usage-poll.js:13`). A cache must preserve these freshness and serialization properties; a stale listing can also omit newly eligible work until a later scan.

## Hub timers

- Every 2s aside scans all threads; pump selects nonarchived threads with a running or pending aside, while cancellation sweep selects **any** thread with `pending_cancels`, including archived ones (`viewer/app/hub.js:79`, `viewer/app/asides.js:204`, `viewer/app/threads.js:200`).
- Every 10s `pollDead` groups nonarchived threads by machine, calls `/v1/sessions`, and reconciles managed session liveness under lock (`viewer/app/hub.js:81`, `viewer/app/sessions.js:698`).
- Default 5s, configurable, retries deliverable queues on nonarchived threads, then checks quiet on nonarchived threads, including report reminders and escalation (`viewer/app/hub.js:47`, `viewer/app/hub.js:83`, `viewer/app/sessions.js:790`, `viewer/app/quiet.js:33`).
- Every 60s waiting-stub polling needs nonarchived eligible stubs **and their parents**, which may be archived; merged PR checks nonarchived eligible threads; retryWaiting and releaseLimits scan all records and select live waiting/limited sessions, with no archive filter (`viewer/app/hub.js:87`, `viewer/app/threads.js:424`, `viewer/app/threads.js:450`, `viewer/app/sessions.js:766`).
- `pollIdle` starts after 30s and repeats at configurable interval default 60s; it scans live account use before and after an asynchronous usage probe, then retries waiting if a reading was recorded (`viewer/app/hub.js:91`, `viewer/app/usage-poll.js:13`).

Routes dispatch to the modules above (`viewer/app/routes.js:69`, `viewer/app/routes.js:501`). `/features` can inspect plan directories/status; `/sessions` calls every configured machine's `/v1/sessions`, falling back to recorded live sessions if unreachable (`viewer/app/views.js:33`, `viewer/app/views.js:146`). `/usage` includes machine account status; `machineAccounts` calls `/v1/status` per machine (`viewer/app/usage.js:50`, `viewer/app/usage.js:88`).

## Transcripts and machine service

Chat fetches every lead session transcript, parses all JSONL rows into turns and folds later tool results into earlier calls; human markers, timestamps and stable assistant indices depend on prior rows (`viewer/app/chat.js:38`, `viewer/app/chat.js:56`, `viewer/app/chat.js:88`, `viewer/app/chat.js:125`, `viewer/app/chat.js:154`, `viewer/app/chat.js:263`). Hub `transcriptCache` holds the last nonempty **whole** response per machine/session only as chat's failure fallback; reviewer/verifier report delivery explicitly does not use that stale fallback, and extracts the last assistant message if the event lacks it (`viewer/app/chat.js:217`, `viewer/app/sessions.js:373`).

Machine `/v1/sessions/:name/transcript?offset=` already accepts a byte offset and returns `{offset, data}`, but `transcript()` reads the whole kept file before slicing it, including for archived forgotten sessions (`machine/service.js:925`, `machine/service.js:1559`). Live reads first serialize copy operations per session; source path, inode and shrink reset the source offset, incomplete JSONL tails wait for newline, and the copy hashes the **entire** existing kept file to deduplicate additions before persisting session state (`machine/service.js:890`, `machine/service.js:900`). An incremental consumer therefore has an existing byte-offset contract, but must retain parser context, handle source replacement/shrink and UTF-8 boundaries, preserve archive access, and distinguish fresh report reads from chat's stale fallback. Offset slicing alone does not eliminate the machine's full-file reads or hashing (`machine/service.js:906`, `machine/service.js:915`, `machine/service.js:940`).

`command` uses synchronous `spawnSync`; `tmux` delegates to it, and `liveTmux` lists sessions, distinguishing no server from an unknown failure (`machine/service.js:79`, `machine/service.js:382`, `machine/service.js:427`). Every 2s readiness captures panes for starting/stuck sessions and ready prompt checks; every 500ms trust also checks eligible starting sessions younger than 30s (`machine/service.js:371`, `machine/service.js:703`, `machine/service.js:735`). Every 2s Codex steps synchronously lists tmux, then tails bound live Codex rollouts; per-session reads serialize, track byte offsets and partial lines, spool events and persist the entire session registry when advancing (`machine/service.js:373`, `machine/service.js:655`, `machine/service.js:660`). `status()` synchronously checks adapter login status, CLI availability/version and account directories, and calls sessionList; `/v1/sessions` avoids those CLI checks but still calls `liveTmux` (`machine/service.js:1161`). A tmux failure is not equivalent to an empty list for worktree safety or dead-session decisions (`machine/service.js:382`, `machine/service.js:448`, `viewer/app/sessions.js:706`).

## Tests and process cleanup

Playwright config selects `*.spec.js` for Chromium and Firefox, with no `workers` override; `npm run test:browser` invokes Playwright and `npm test` invokes `node --test test/*.test.js`, also without a concurrency override (`viewer/playwright.config.js:9`, `viewer/package.json:6`). Both runners may run work concurrently under their own defaults; the repository does not fix a worker count. Viewer helper allocates a free port and isolated cache root, registers the spawned server, and stops it explicitly (`viewer/test/helpers/server.js:66`).

`run-dir` creates one temp run directory per process, records owner PID/start and explicitly tracked children, kills tracked processes on normal/signal cleanup, and on a future allocation sweeps abandoned owner directories only when identity checks allow it; old legacy folders are removed by age without discovering or killing their processes (`test-support/run-dir.js:48`, `test-support/run-dir.js:67`, `test-support/run-dir.js:93`, `test-support/run-dir.js:101`, `test-support/run-dir.js:121`). Smoke separately registers a cleanup callback to kill its tmux server (`test-support/smoke/harness.js:170`). The brief reports an old test Claude session and viewer server still running; their identity, ownership and cause were not verified here. Tracked-child cleanup does not cover arbitrary untracked descendants or old processes lacking a usable owner record (`test-support/run-dir.js:48`, `test-support/run-dir.js:121`).

Relevant existing coverage includes lock/write queues and timer races (`viewer/test/app-state-queue.test.js:1`, `viewer/test/app-hub.test.js:1`, `viewer/test/app-quiet.test.js:1`, `viewer/test/app-merged.test.js:1`); chat parsers and browser list/thread/agents behavior (`viewer/test/app-chat.test.js:1`, `viewer/test/app-threads.spec.js:99`, `viewer/test/app-views.spec.js:1`, `viewer/test/app-agents.test.js:1`); usage and waiting (`viewer/test/app-usage.test.js:1`); transcript shrink, incomplete lines, concurrent copies, archived copies and fast trust (`machine/test/service.test.js:259`, `machine/test/service.test.js:412`, `machine/test/service.test.js:439`, `machine/test/service.test.js:549`); Codex steps (`machine/test/service.test.js:1357`, `machine/test/codex-steps.test.js:1`); and cleanup (`test-support/test/run-dir.test.js:1`).
