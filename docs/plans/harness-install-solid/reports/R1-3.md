# R1-3: Settings Cancel error shows only on its own running row

## What changed

- `viewer/pages/settings.js`
  - `step()`, `running` branch: the new job record carries `cancelErr` alongside `cancelling`, so a Cancel error survives polls while the install runs. Terminal states still build fresh records without it, so the error clears when the install ends.
  - `cancelInstall()`: no longer touches `hz.rowErr`. On the press it clears `job.cancelErr`; on failure it sets `now.cancelErr` to the same two strings as before.
  - `harnessRow()`: the alert renders from `hz.rowErr[provider] || (job && job.state === 'running' && job.cancelErr)`, using the same `<p class="inline-err" role="alert">` element. Other `hz.rowErr` uses (switch errors, the POST 409) are unchanged.
- `viewer/test/app-harnesses.spec.js`: two new tests, inserted before "no Cancel while the row says it cannot reach the machine". The two existing Cancel tests are unchanged.
  - `a Cancel failure clears once the install reports cancelled`
  - `a Cancel failure shows only on the row of the machine it failed on`

## Choices

- `viewer/pages/settings.js`, `harnessRow()`: when both `hz.rowErr[provider]` and `job.cancelErr` are set, the alert shows `hz.rowErr[provider]`, because the brief's expression puts it first.
- `viewer/test/app-harnesses.spec.js`, clears-on-cancelled test: the GET is switched to `cancelled` only after the alert is seen, rather than on a timer, so the test does not depend on poll timing.
- `viewer/test/app-harnesses.spec.js`, two-machine test: it waits for node-2's kimi row to read "Not installed" before asserting no alert, so the check cannot pass on a row that has not re-rendered yet.
