# R4 — new threads carry the default project_tools record

Remediation 2, gap from verification attempt 2: a new thread had no `project_tools` record until a machine returned a snapshot, so `POST /threads` returned 201 without the required default (spec §8).

## What changed, by file

- `viewer/app/threads.js` — `emptyThread(input)` now returns
  `project_tools: { boot: null, seq: 0, created_at: null, state: null, card: null, card_names: [] }`
  next to `archived`, before the timestamps. `createThread` and `createStub` both build on `emptyThread`, so both get the default.
- `viewer/test/app-project-tools.test.js` — one new test: "a new thread gets the default project_tools record when the machine start answer has none". It creates a thread with `POST /api/threads` against the fake machine (`viewer/test/helpers/app.js` `setup()`), asserts the fake's session records carry no `project_tools`, then asserts both the 201 response body and the record re-read from disk via `new Hub({ stateDir }).thread(id)` deep-equal the default object.
- `viewer/app/sessions.js` — unchanged. The lazy creation in `applyProjectTools` stays as is (old saved threads still lack the record and get it on first snapshot).

## Not done / caveats

- `run.test.js` failed once in the first full run on the port collision above. It passed on a rerun alone and in the second full run. The cause was not investigated further; it is outside this brief's ownership.
- `createStub` also goes through `emptyThread`, so stub threads now carry the default record too. That follows from the brief's single-function change and matches §8 ("a thread record gains"); nothing in this task tests stub threads directly.

## Choices

- `viewer/app/threads.js` `emptyThread`: placed the `project_tools` field after `archived` and before the timestamps; the brief said "next to the other default fields" and did not fix the position.
- `viewer/test/app-project-tools.test.js`: asserted the "no project_tools on the start answer" precondition by reading the fake machine's session map (`c.machine.sessions`) rather than injecting a custom answer, since the default fake start carries none and the test goes through the real HTTP route.
