# Silent stops: map

Checked against `be198998f46768a07d03019a25d1d4fd6890bf71` (origin/main); see also `docs/maps/app-session-tree.md` and `docs/maps/app-sessions.md`.

```text
brief -> machine types initial message -> session turn -> card posted -> recipient queue
                                            | turn ends -> machine event -> hub marks idle
                                            | silent -> no result or notice today
```

1. The hub saves `started_by` and passes `brief` at start (`viewer/app/sessions.js:174-185,196-210`). The machine prepares `pending_initial` and submits it at readiness (`machine/service.js:445-447,478-488`); Codex includes a role prompt and Claude sends the brief (`machine/adapters/codex.js:32`; `machine/adapters/claude.js:24`). Hub `first_message` distinguishes that case from a fresh ready session with no initial turn (`viewer/app/sessions.js:243-247,283-288`). The initial submission does not go through the hub's `thread.sent` bookkeeping (`machine/service.js:482-486`; `viewer/app/sessions.js:330-346`).
2. Claude Stop or Codex notify translates into `turn-ended`; `hook.sh` forwards the payload and `hook-post.js` posts with the session token, spooling on failure (`machine/adapters/claude.js:28`; `machine/adapters/codex.js:35`; `machine/hook.sh:16-30`; `machine/lib/hook-post.js:15-30`). The machine copies transcripts where provided, processes the hook, adds its own session/thread identity, spools and relays events with delivery IDs (`machine/service.js:462-465,703-727,738-768,1033`). The hub deduplicates event IDs, sets `turn_ended`, persists, then tries delivery (`viewer/app/sessions.js:353-360,392-397,422-430`). Limits also set idle and can defer reports (`viewer/app/sessions.js:365-376,396`).
3. The hub queues messages in session order, delivering only when live, ready, idle and not held; successful machine submit shifts the queue, sets `turn_ended = false` and adds `thread.sent`, while failure leaves it queued (`viewer/app/sessions.js:297-315,317-350`). The machine submits via tmux paste and Enter (`machine/service.js:523-531`). The initial brief bypasses this marker, so a detector based only on `thread.sent` misses the first turn.
4. `card.js` validates, posts with the session token to the machine origin (default port 7374), and the service spools cards before relay (`viewer/app/card.js:211-229`; `machine/service.js:1011-1028`). The hub validates the role and stores the card: `message` goes to its named recipient, `result` marks the sender finished and goes to `started_by`; card and queue persist before delivery (`viewer/app/card.js:23-38,114-120,124-136,165-168`; `viewer/app/cards.js:38-48,79-95,101-115`). Separate event and card spools drain independently (`machine/service.js:703-727,1015-1023`): a delayed card can reach the hub after its turn-end event, so hub arrival order alone cannot prove silence.
5. Reviewers and verifiers cannot post cards (`viewer/app/card.js:35-37`): on an eligible turn end the hub takes the last assistant text from the hook or transcript, synthesizes a result and sends it to the starter; no text means no result, and limits suppress this path (`viewer/app/sessions.js:257-280,392-397`). This differs from worker, mapper and sub-lead result cards and needs explicit scope in the plan.
6. `turn-failed` marks idle and queues `[wc:from app]` to the starter; for a lead it creates a system needs card (`viewer/app/sessions.js:378-385`). Dead-session polling rechecks the machine under the thread lock, marks missing sessions ended and messages their starter, or creates `Sessions ended` for a lead (`viewer/app/sessions.js:528-545,558-587`). Stuck startup and permission events set a hold and create a system needs card; ready, prompt clear or permission-turn-end clears the hold and answers that card (`viewer/app/sessions.js:399-420`). Lead turn end closes its failure card, and lead restart closes `Sessions ended` and lead-failure cards (`viewer/app/sessions.js:392-395`; `viewer/app/threads.js:148-150`). Lead `resolve` refuses system needs cards (`viewer/app/card.js:171-180`).
7. Agents `waiting_on` lists live, unfinished direct children only when the parent has `turn_ended === true` (`viewer/app/agents.js:11-18`). It is derived from state, not evidence that a parent is actively waiting or that an idle child posted a result.

## Rules and test seams

The worker brief is its contract; it must use `wc.js` for git, message the lead on unresolved plan questions, and finish with a result, including `blocked` and its reason when applicable (`protocol/app/worker.md:3-6,22-33,41-58`). Sub-lead briefs specify objective, boundary, validation and lead contact; it waits for results, handles turn failure by asking to carry on, and restarts dead workers (`protocol/app/sub-lead.md:28-48,86,98-108`). Lead briefs carry role, paths, report and ownership, and the lead handles dead or failed children (`protocol/app/lead.md:48-71,355-365`). These passages do not state an explicit exception for the session's own `wc.js`/`card.js` calls to port 7374.

Hub fixtures create an isolated server and expose `event` and `machinePost` helpers (`viewer/test/helpers/app.js:9-27,62-68`); `viewer/test/app-balancer.test.js:185-215,336-349` covers failed and limited turns and transcript results, `viewer/test/app-ended.test.js:9-17` creates worker trees for death polling, and `viewer/test/app-agents.test.js:18-33` checks waiting relationships. Machine fixtures fake tmux and a hub (`machine/test/service.test.js:19-76`); hook, offline spool, replay, and card ordering are exercised at `machine/test/service.test.js:216-233,248-249,408-416`. These seams allow a failing-first test of the first brief, later delivered messages, card/event ordering, duplicate events, and notice closure.

## What I did not look at

Browser rendering of needs cards, full transcript parsing, all provider and rate-limit edge cases, or unlisted tests.
