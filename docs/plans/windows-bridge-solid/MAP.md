# Map: Windows bridge follow-up

The shared runtime map is [windows-bridge-runtime](../../maps/windows-bridge-runtime.md), checked against `cb736689c215175211cdc324422c65d7c8a08a70`. The five deferred items and original decisions are in `docs/plans/windows-bridge/PLAN.md:40,44,118,356-380,497-505`; completion records the live check and Codex environment fix (`docs/plans/windows-bridge/COMPLETION.md`, Remediation rounds).

```text
Project tools form -> .mcp.json -> session reads and translates tools
                              -> ready copy -> agent CLI starts its tools
agent win info -> bridge checks paths and Git -> health / readiness / copy paths
stop / archive -> reconcile -> remove copy and temporary refs
```

1. **Windows localhost HTTP/SSE.** The Settings form parses command and HTTP entries; SSE is not editable in that form (`viewer/pages/project-tools.js:82-93`). Saving writes `.mcp.json` through a project-tools PR (`machine/lib/project-tools.js:90-140`); `readProjectMcp` accepts stdio, HTTP and SSE (`machine/lib/project-mcp.js:72-78,86-125`). Claude enables project servers from the file, Codex translates HTTP URLs to CLI overrides but rejects SSE, and Antigravity emits a per-session plugin and rejects SSE (`machine/adapters/claude.js:69-74`; `machine/adapters/codex.js:34-39,52-74`; `machine/adapters/agy.js:34-64`). Those URL paths pass the configured URL through; a host-address rewrite must reach each provider's actual configuration, including Claude's file-based loading, or a forward must make the configured address reachable. `hasWindowsProgram` recognizes only stdio `.exe` commands, so HTTP/SSE alone does not trigger copy readying (`machine/lib/project-mcp.js:80-83`; `machine/service.js:816-825`). WSL detection checks interop and mount, not networking mode (`machine/lib/win-env.js:8-27`). Tests: `machine/test/project-mcp-reader.test.js:10`, `machine/test/project-mcp-codex.test.js:24,103`, and `machine/test/win-env.test.js:8`.

2. **Unity preset.** A possible user-facing insertion point is the Project tools form and its save flow (`viewer/pages/project-tools.js:82-100,741`; `machine/lib/project-tools.js:115-139`); no specific MCP has been selected (`docs/plans/windows-bridge/PLAN.md:502`). On tool roles, `sessionEnv` passes the Windows copy path as `WHEELCHAIR_WINDOWS_PROJECT` and lists it in `WSLENV` (`machine/lib/win.js:296-304`; `machine/service.js:865-879`). Codex explicitly passes those names to Windows stdio tools (`machine/adapters/codex.js:81-86`); Pi warns and loads no project tools (`machine/adapters/pi.js:59`). Tests: `machine/test/win.test.js:45`, `machine/test/project-mcp-codex.test.js:133`, `machine/test/win-service.test.js:101`. The optional live Unity check starts Unity itself, not a Unity MCP (`machine/test/windows-live.js:159-172`).

3. **Disk use.** Copies have their own Git repositories and can contain seeded ignored caches (`machine/lib/win-env.js:160-163`; `machine/lib/win-sync.js:71-118`). Temporary-index `git add` writes raw snapshot objects, and Windows snapshot fetches and kept conflict refs add objects to the common Linux repository (`machine/lib/win-sync.js:149-163,259-285,306-310`; common directory recorded at `machine/lib/win.js:58-64`). Cleanup and retained failures are detailed in the shared map. `info` has no size fields (`machine/lib/win.js:307-312`); neither per-copy size nor shared/reachable Git object attribution is established by this interface. Tests: `machine/test/win-sync.test.js:194,225,294,372`, `machine/test/win.test.js:179,193,207,291`.

4. **Restart after readying.** The machine waits up to 45 seconds for `beforeLaunch`, then starts the provider CLI even if readying continues (`machine/lib/win.js:129-185`; `machine/service.js:865-893`). The provider CLI owns its MCP processes through its configuration; `WinBridge` tracks bridge-launched apps separately and the inspected launch/readying paths contain no MCP restart action (`machine/adapters/claude.js:69-74`; `machine/adapters/codex.js:52-86,137`; `machine/lib/win.js:22-32,129-185,339-345`). Completion records the timeout and its tests (`docs/plans/windows-bridge/COMPLETION.md`, coverage item 31). Tests: `machine/test/win.test.js:119`, `machine/test/win-service.test.js:69`.

5. **Broken bridge warning.** The existing screen warning is added when a lead posts an approval card, not when the session starts: `screenTools()` supplies missing commands and the machine appends the text to `warnings` (`machine/service.js:2116-2128`; `machine/test/screen-tools-warning.test.js:17`). `win info` resolves copy paths, then runs Linux and Windows Git version checks; failures and readying errors become `reason` (`machine/lib/win.js:307-329`; `machine/lib/win-env.js:85-90,118-124,141-155`). Detection requires both Microsoft kernel and registered interop, so a WSL installation with broken/missing interop can be classified as non-WSL before `info` runs (`machine/lib/win-env.js:8-27`; `machine/lib/win.js:315-316`). Tests: `machine/test/win-env.test.js:8,22`, `machine/test/win.test.js:323`, `machine/test/win-service.test.js:52`.

Store-packaged apps can escape the Job Object and are unreachable by the bridge's window and stop operations (`docs/plans/windows-bridge/PLAN.md:118`; `README.md:92`). The original accepted sync risks remain relevant (`docs/plans/windows-bridge/PLAN.md:507-518`).

Not checked: provider MCP restart capabilities outside this repository, actual WSL networking modes, Unity MCP vendor setup, actual disk accounting and garbage collection, or a new live run.
