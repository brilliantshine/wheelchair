## Picker flow and safety

The picker lists tracked files at head, identifies only top-level viewer `*.test.js`, viewer `*.spec.js`, and machine `*.test.js`, and compares name-status including both ends of renames/copies. A changed recognized test selects itself only if it exists at head, then skips every other rule; a deleted test selects nothing (`test-support/pick-tests.js:19-33,45-60`).

For each other path outside docs and any `test/` directory, it scans non-browser test text: same-component test names beginning with the source basename plus dot or hyphen match (`byName`); a regex finds literal relative `require`, `from`, static or dynamic `import`, resolving relative to the test and comparing exact path, `.js`, `.json`, or `/index.js` (`test-support/pick-tests.js:61-74`). Both set `mapped` and `covered`. Transitive traversal would replace or extend this direct scan at lines 63–73, reading intermediate files at head, resolving relative to each importer, retaining original test roots, and stopping on cycles. The existing source-path guard excludes changes under `test/` from this scan even if reached by a helper; fan-out handles relevant test directories separately (`test-support/pick-tests.js:61,82-88`).

Map entries match changed paths; targets are recognized test files or suite names. Missing files and unknown suite names return false silently. Successful non-additive targets set `mapped`, `covered`, and `mapEntry`; additive targets select readers but set none of those flags (`test-support/pick-tests.js:33-34,76-80`). The map has broad suite targets (`test-support/test-map.json:3-13`) and individual viewer/machine file targets (`test-support/test-map.json:16-27,135-168`). A tracked-tree check using the picker's glob semantics found **no missing targets and no unmatched globs** at HEAD; it includes both additive and ordinary entries (`test-support/pick-tests.js:35-43`; `test-support/test-map.json:1-169`).

Fan-out selects both viewer suites for viewer helpers/fixtures and viewer config/package files; machine test paths select machine; `test-support/run-dir.js` selects both viewer suites, machine and test-support; other test-support, sensitivity, codex, install and sudo-helper paths select their suite; root `install.sh` selects install. Fan-out sets `covered` but not `mapped` (`test-support/pick-tests.js:82-88`). If not `mapped`, viewer or machine source falls back to its whole suite(s); front-end pages, HTML/CSS and `viewer/doc.js` require `mapEntry` even if imported (rule 6). These fallbacks exclude docs, markdown and test paths. If still not `covered`, non-doc, non-markdown paths other than `.gitignore` select every suite (`test-support/pick-tests.js:89-96`). Whole-suite selections override file lists in output; otherwise browser gets spec basenames and Node gets explicit files (`test-support/pick-tests.js:99-106`).

**Risk:** an additional transitive match sets `mapped` and suppresses a fallback, but static imports do not enumerate runtime readers. A narrower pick can therefore omit tests unless those readers are accounted for; the old plan's assertion that the fallback only makes picks larger does not establish safety after this change (`docs/plans/faster-full-runs/PLAN.md:180-184`; `test-support/pick-tests.js:73,89-96`). Browser specs are deliberately excluded from reading (`test-support/pick-tests.js:55-56`); rule 6 explicitly relies on map entries for browser coverage of front-end files (`test-support/pick-tests.js:89-93`). Other server-side paths can also reach browsers through a spawned server.

## Dependency shape and non-import readers

A literal-require scan of tracked top-level Node tests found 53 of 92 viewer tests importing a path named helper/helpers, and none of 80 machine tests importing a path with that name; 66 machine tests directly import shared `test-support/run-dir`. This definition is lexical, not a count of all shared code. For example viewer `app-sudo` imports both helpers; `app.js` imports `server.js` and `app-machine.js`, and server helper imports `run-dir`, while the machine double imports server helper (`viewer/test/app-sudo.test.js:12-13`; `viewer/test/helpers/app.js:4-7`; `viewer/test/helpers/server.js:9-10`; `viewer/test/helpers/app-machine.js:4-8`). A tree-wide scan using the picker's literal regex found cycles, including `machine/lib/project-programs.js` ↔ `machine/lib/project-mcp.js` and `viewer/app/settings.js` ↔ `viewer/app/background.js` (`machine/lib/project-programs.js:4`; `machine/lib/project-mcp.js:82`; `viewer/app/settings.js:317`; `viewer/app/background.js:66`); a visited set is necessary. Built-in and package requires such as `node:fs` and `@playwright/test` are non-relative (`viewer/test/helpers/server.js:3-9`; `viewer/playwright.config.js:5`). No tracked `.mjs` or `.cjs` files appeared in `git ls-files`; a search of specs found no actual ESM import declarations. The regex supports textual ESM forms but is not a JavaScript parser (`test-support/pick-tests.js:67-71`).

Concrete edges missed by static relative import reading:

## Tests, timing and law

`pick-tests.test.js` makes temporary git repositories with a small map, source files and test roots, commits a base and each change, and invokes the actual picker as a child. It asserts renames/deletes, direct imports, basename matches, maps, additive behavior, JSON extension resolution, fan-out, front-end and general fallbacks, full selection, docs and invalid base (`test-support/test/pick-tests.test.js:8-37,72-73`). A separate real-tree case clones the checkout, copies the working map and checks selected readers across eight changes (`test-support/test/pick-tests.test.js:38-71`); an independent real-tree map integrity test could sit beside it and inspect the tracked file set and working map.

`full-run.sh` starts browser in parallel, then waits for each other suite in order, with machine after viewer-node, and writes per-suite wall seconds (`test-support/full-run.sh:47-73,84-105`). `machine/test/run.sh` invokes one `node --test` with all test files and no `--test-concurrency` override; it does not explicitly serialize files (`machine/test/run.sh:1-3`). A previous build recorded machine 387 s, browser 349 s and viewer-node 96 s, with another full run and verifier active; that is one historical observation, not a controlled benchmark (`docs/plans/faster-full-runs/COMPLETION.md:82-100`). No per-file timings from that run were available here; slowest files remain unknown.
