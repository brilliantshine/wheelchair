## Keys

Script tools can declare `keys`: an array of 1–20 unique environment-variable names. Names contain letters, digits and `_`, cannot start with a digit, and cannot be names that change how the agent runs. For example:

```json
{
  "name": "lookup",
  "description": "Look up a record",
  "kind": "script",
  "inputs": {
    "query": { "type": "string", "description": "Record to look up", "required": true }
  },
  "run": ["./run.sh"],
  "keys": ["LOOKUP_API_KEY"]
}
```

A server tool with `keys` is not connected and shows `keys for server tools aren't supported yet`.

A project tool uses the project's keys, set on its Tools page under Keys on this machine. A shared tool uses the machine's shared keys, set in Settings under Shared tools, Shared keys. In the shared tools project's own threads, its tools use the shared keys too. Each machine keeps its own keys. A usable value is 8–4096 characters of letters, digits and `. _ ~ + / = -`; other values count as not set.

At each call, the values are added only to the tool's own process, never to the agent's environment, MCP configs or instructions. A key also used by a `.mcp.json` server still reaches the agent that way; moving that server to a folder tool removes it. Agents run as the same OS user, so an agent that looks for key files on disk can find them.

A tool with a missing key is not offered; problems show `needs key <KEY>, not set on this machine` (or `needs keys A, B, …` for several). On Kimi and Pi the problems line is as of session start. For MCP, a key added mid-session is usable from the next agent start (a new session, resume or account switch). A replaced value applies from the next call; a removed key makes the next call fail without running. For MCP, if a tool's `keys` change mid-session, it is refused as changed until the next agent start. On Kimi and Pi, an added key and a changed `keys` list both apply from the next `wc.js tool run`, with no refusal.

Keys printed as-is or with up to three layers of common escapes are replaced with `[key]`. This covers JSON and backslash escapes such as `\u002B`, `\x2B` and `\/`, and percent-encoding such as `%2B`. Base64, hashing, splitting and web-page codes such as `&#43;` are outside this protection, and deeper escaping may leave a key visible. A backslash right before a key is hidden with it. At a cut edge, text that looks like part of an escaped key is dropped, and a cut-off stretch made entirely of key characters, percent signs and backslashes can be dropped whole. Very escape-heavy output can show `[not checked for keys]` in place of stretches of those characters. Never print or log a key in any form. Never write a key into a tool's files: they are committed. Node's child-process debug output (`NODE_DEBUG`) on in the bridge refuses keyed tools. Claude, Antigravity and unrestricted Codex use keyed tools through MCP with no extra step. Kimi and Pi run keyed tools through `wc.js tool run`, which asks the machine to run them with their keys and returns redacted output; key values never appear in the result. Sandboxed Codex cannot use keyed tools; set Codex to unrestricted in Settings to use them.

Tools may rely only on `PATH`, `HOME`, `WHEELCHAIR_PROJECT_DIR`, their declared keys and variables they set themselves. Keys a tool happens to find in its environment exist only on some AIs and projects.


## Make and test

Run `node <wheelchair-root>/viewer/app/wc.js tool` followed by these commands. In a session they use its worktree and pinned shared copy; outside a session they use the current git checkout only. `new` writes into the current worktree and refuses an existing folder. `list` shows each tool's name, kind, source and `ok` or the reason it can't be used (`--json` gives JSON). `check [name]` validates tools and checks a server's MCP handshake and advertised tool list, with a 30-second deadline. `run name --input '<json>'` runs a script, with `{}` as the default input. In a session, `list` shows each keyed tool's key names and whether each is set. `check` validates without using keys. On Kimi and Pi, `run` uses the machine for keyed tools. If the connection is lost, the tool may already have run, so check before running it again. Otherwise, `run` runs in your own shell without folder-tool keys and says so; variables already in your environment pass as usual. On the other AIs, to try a keyed tool for real, use it through MCP in a session that offered it.

For example, in a scratch checkout:

```text
$ wc.js tool new demo --kind script
/tmp/wc-t7-demo.480ZI9/.wheelchair/tools/demo
Next: wc.js tool check demo
$ wc.js tool list
demo	script	project	ok
$ wc.js tool check demo
demo: ok
$ wc.js tool run demo --input '{"text":"hi"}'
Input: {"text":"hi"}
```

Create a template with `new`, edit it, run `check` and `run` with representative input, then commit before asking for review. Use `--kind server` for the Node server template; server tools are tested with `check`, not `run`. A changed `tool.json` reaches MCP at the next agent start: a new session, resume or account switch. Script files themselves run live. If the description changes during a session, the bridge asks you to run it from the shell or wait for the next start.


## AI limits

Claude, unrestricted Codex and Antigravity receive folder tools through MCP in roles that receive project tools. Kimi, Pi and sandboxed Codex run script tools from the shell with `wc.js tool run`; set the shell call timeout above the tool's `timeout_seconds`. Kimi and Pi run keyed tools through the machine as above. Sandboxed Codex cannot use keyed tools; its problems and `wc.js tool list` say so, with the message `set Codex to unrestricted in Settings to use it`. They have no server tools; Codex needs unrestricted mode for those. Codex keeps `.mcp.json` entries first, then tries folder entries one at a time (bridge first, then server tools by name). Any entry that would push the launch arguments over Codex's 64 KiB budget is left out and named on the problems card; later smaller entries can still fit.

Codex sets the bridge's MCP call deadline to 260 seconds. Codex 0.172.0 defaults to 300 seconds per call for server tools. Claude Code 2.1.332 defaults to 100,000,000 ms per MCP call (it reads `MCP_TOOL_TIMEOUT`, in milliseconds), well above 260 seconds. Wheelchair sets the Antigravity bridge's `timeoutSeconds` to 260; Antigravity's default for server tools was not established.
