# Startup growth warning: map

Checked against `c81c022e30a5d3fa11aaf2ed9fbe28b903eab011` (origin/main). The four suggested maps were compared with origin/main; all have changes in their covered files, so their relevant paths were rechecked here. Their older checked-against headers are not evidence for this flow.

```text
hub starts session -> machine writes prompt and Claude settings -> tmux launches Claude with deny list
  -> successful start appends ledger identity -> Claude writes transcript -> Stop hook copies transcript
  -> lead posts approval with Ready result -> machine spools -> hub stores and pins card
  -> thread page polls and draws card -> Re-check or Start press -> hub runs Ready check
  -> unchanged and ready -> queue Start building for lead
hub background timer -> machine session list -> reconcile live sessions
```

1. The machine composes a prompt file and creates the worktree, then assigns a CLI session UUID, writes adapter settings and shell-quotes the argv into tmux (`machine/service.js:513-558`). Claude's single `DISALLOWED_TOOLS` constant is passed as comma-separated `--disallowedTools` (`machine/adapters/claude.js:45,57-65`): Artifact, Workflow, ScheduleWakeup, SendFeedback, ShareOnboardingGuide, ReportFindings, ListAgents, ArtifactComments, ArtifactData, CronCreate, CronDelete, CronList, RemoteTrigger, PushNotification, PublishPlugin, DesignSync, EnterWorktree, ExitWorktree, EnterPlanMode, ExitPlanMode, AskUserQuestion and EndConversation. The lean-sessions inventory says the kept tools include Bash, Read, Edit, Write, Agent, Skill, ToolSearch, TaskStop, SendMessage, Monitor, WebFetch, WebSearch and NotebookEdit; that is an inventory from that plan, not a runtime enumeration (`docs/plans/lean-sessions/PLAN.md:121-125`). Everything not denied remains eligible; configuration and deferred loading affect what actually reaches a call (`machine/adapters/claude.js:57-63`).

2. After tmux starts and the session is persisted, one best-effort JSONL ledger append writes `at`, `name`, `role`, `provider`, `model`, `account_dir`, `cli_session_id` and `thread_id`; failure is logged without failing the start (`machine/service.js:538-560`). No `startup_tokens` is written. A repository search for the ledger filename found only this production writer, its API description and its test; hooks and reports do not append to it (`machine/API.md:10`; `machine/test/service.test.js:823-826`). Decision 54 supersedes Decision 51's planned runtime capture: the validation method instead joins transcripts to ledger IDs and counts omissions (`docs/plans/lean-sessions/PLAN.md:80-85,184-198`).

3. Claude settings install synchronous Stop, Notification and StopFailure hooks and asynchronous wildcard PreToolUse, PostToolUse and PostToolUseFailure hooks (`machine/adapters/claude.js:57-62`). `hook.sh` reads stdin, and `hook-post.js` parses and translates it before posting or spooling (`machine/hook.sh:15-19,36`; `machine/lib/hook-post.js:10-31`). Tool events retain the tool being used and its classification, not an inventory; Stop retains the raw payload and `transcript_path`, permission Notification retains raw payload, and StopFailure retains its error (`machine/adapters/claude.js:69-82`). The service copies the Stop transcript, serializing copies and accepting only newline-complete records; the transcript API can also discover it by session UUID before Stop (`machine/service.js:798-832,834-851,910-913`; `machine/adapters/claude.js:68`).

4. **Cheapest capture:** when the first Stop is processed, use the already supplied transcript path and existing copy operation, read the first usable assistant record, and append a separate sample keyed by CLI session ID. The plan's reproducible measure is `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`, excluding synthetic model records and zero sums; it counts each message ID once (`docs/plans/lean-sessions/PLAN.md:184-189,196`). Stop is after a completed turn, so sessions that fail or never reach Stop need a later retry or remain missing; a sample append must be idempotent across repeated hooks and spool replay. Do not assume ledger append and hook arrival are atomic (`machine/service.js:555-560,910-913`; `machine/lib/hook-post.js:19-31`). Reading on demand by ledger ID is cheaper in added runtime writes, but transcript retention can remove the source (`machine/adapters/claude.js:62,68`; `docs/plans/lean-sessions/PLAN.md:80-85`).

5. **Tool-list feasibility:** installed Claude Code `2.1.326` was checked read-only in five recent `~/.claude/projects/*/*.jsonl` files. The first three have `api-request-shape` records with `shape.tools` arrays of schema objects and `name` fields; for example `/home/collin/.claude/projects/-home-collin--local-state-wheelchair-worktrees-wheelchair-wc-723c2d1f57db/acfa8173-5419-4041-83c5-a3a62ccd3f6c.jsonl:19` lists Agent, Bash, Edit, Read, Skill, ToolSearch, DeferredToolPlaceholder, Write and advisor. Two other sampled records show the seven non-deferred denied tools in an earlier configuration (`/home/collin/.claude/projects/-home-collin--local-state-wheelchair-worktrees-wheelchair-wc-9b670482ba5c/30e8e85e-59be-4223-9b23-79b8906c0d8b.jsonl:19`; `/home/collin/.claude/projects/-home-collin--local-state-wheelchair-worktrees-wheelchair-wc-3a8223808223/60f78d89-7305-493d-8223-987b541c5f71.jsonl:12`). Thus comparing **recorded request schema names** against a maintained keep/deny inventory is feasible, but cannot reliably detect every offered unknown tool: deferred tools can be represented by a placeholder, tool schemas vary by request/configuration, and `tools-used` records report used tools rather than the offered set (same first transcript, lines 19 and 29). The adapter does not extract a complete list from hook input (`machine/adapters/claude.js:69-82`). These observed transcript records are local version-specific evidence, not a stable API contract.

6. The lead performs its Ready check and puts `{ok, missing}` and objections in approval JSON (`protocol/app/lead.md:265-276`; `protocol/app/cards-lead.md:56-66`). `card.js` validates and sends with the session token; the machine spools and forwards; the authenticated hub validates the lead and card again, deduplicates, assigns ID/time, stores and pins it (`viewer/app/card.js:90-99,245-263`; `machine/service.js:1256-1285`; `viewer/app/routes.js:374-378`; `viewer/app/cards.js:11-33,50-60,119-120,143-150`). The hub does **not** independently run Ready when accepting an approval: initially it stores the lead-supplied result (`viewer/app/cards.js:50-60,119-120`).

7. The thread page polls chat and renders the pin, objections, Ready status, Start and, only while not ready, Re-check (`viewer/pages/thread.js:590-629,846,930-934,957,1031`). Re-check runs the hub check and saves the result. Start also checks; if the stored Ready object is absent or its `missing` array changed it saves the new result and does not queue this press, and if unchanged but not ready it also does not queue. Only unchanged ready queues the card message to the lead and unpins approval (`viewer/app/threads.js:272-299,315-337`; `viewer/app/ready.js:61-64`). `same` compares object presence and `missing`, not `ok` itself; putting warnings in `missing` can consume a Start press and affect the gate, so warning state needs its own non-gating behavior.

8. The hub check calls only the thread machine's `/v1/status`, checks service commit and the thread CLI's installation and a configured unpaused logged-in account; the legacy status shape falls back to `/v1/preflight` for Codex (`viewer/app/ready.js:11-58`). Status runs synchronous CLI/login checks and returns version, per-CLI status, accounts and session list (`machine/service.js:1067-1089,1182,1200`). Separately the hub's ten-second background dead-session poll groups unarchived threads by machine and calls `/v1/sessions`, rechecking under a thread lock before marking sessions dead; it does not poll status for startup data (`viewer/app/hub.js:55-58,133-136`; `viewer/app/sessions.js:683-725`). Hub machine calls use a machine secret and a five-second default timeout (`viewer/app/machine-client.js:10-14,42-44,64-77`). The existing transcript endpoint and usage probe are separate routes (`machine/API.md:19,50`).
