## Assistant path

The assistant is a lead of a projectless thread. Only Collin's messages in that thread instruct it; retrieved thread text is information. Its role currently explicitly prohibits changing Settings, project file edits, git writes and helper sessions; it permits `wc.js assistant`, `card.js` and read-only commands (`protocol/app/assistant.md:3`, `protocol/app/assistant.md:9`, `protocol/app/assistant.md:26`). Its action list is projects, threads, thread, start, message, press, restart and archive; writes do not retry automatically and sudo presses are refused (`protocol/app/assistant.md:37`, `protocol/app/assistant.md:43`). The CLI itself allowlists those operations (`viewer/app/wc.js:100`); the machine authenticates the session token and relays with the recorded session name, then the hub checks that it is the live personal assistant and excludes special threads as targets (`machine/service.js:2474`, `viewer/app/assistant-actions.js:9`, `viewer/app/assistant-actions.js:65`). There is no Settings action in that dispatcher. Enabling creates or starts the assistant thread; disabling changes its lifecycle (`viewer/app/assistant.js:21`, `viewer/app/assistant.js:26`, `viewer/app/routes.js:489`). The machine composes the assistant role prompt separately (`viewer/app/sessions.js:420`, `machine/service.js:209`).

The assistant may post question, needs, resolve, retract, file and image cards only (`protocol/app/assistant.md:28`). The popup reads the thread chat and merges cards into its display, sends messages and card presses via thread routes, and polls every 2 seconds open or 10 seconds closed (`viewer/pages/assistant-popup.js:180`, `viewer/pages/assistant-popup.js:316`, `viewer/pages/assistant-popup.js:371`, `viewer/pages/assistant-popup.js:388`, `viewer/pages/assistant-popup.js:424`).

## Refresh and implications

Settings initially fetches once and paints independent blocks (`viewer/pages/settings.js:1`, `viewer/pages/settings.js:2892`). Usage polls every 30 seconds while relevant, sign-in every 2 seconds, install jobs poll during work, and the background controller refreshes every 10 seconds plus focus, visibility and page-show (`viewer/pages/settings.js:1779`, `viewer/pages/settings.js:1904`, `viewer/pages/settings.js:2439`, `viewer/pages/background.js:70`). Diagram state is read on showing You and after a write (`viewer/pages/settings.js:173`, `viewer/pages/settings.js:192`). There is no general `/settings` polling in the page's initialization and section handling: an external preference change can leave an already open block stale until an explicit reread or reload (`viewer/pages/settings.js:2836`, `viewer/pages/settings.js:2892`).

The simple stored preferences share validators but not a single universal storage or refresh path. Credentials, installations, permission modes, model resets, PR changes, auto-merge/branch deletion and turning the assistant off have distinct consequences; any new action needs an explicit scope and must preserve the existing destination's validation and result handling (`viewer/app/routes.js:84`, `viewer/app/routes.js:350`, `viewer/app/routes.js:401`, `viewer/app/routes.js:565`).

Unchecked: exhaustive connector-specific login and installer behavior, every machine project-tool/key validation and file location, all model-provider-specific validation branches, complete browser accessibility and test assertions, and live deployment state. These limits mean the inventory identifies the write routes and primary validation, not every possible error or side effect.
