# Map: idle usage polling

Checked against: `20074341b6b1be157c09f8d248d3965645feece9` (origin/main). Placement details: [app-provider-placement.md](../../maps/app-provider-placement.md).

```text
Claude status line / Codex turn-end rollout
  -> local hook and machine event spool -> hub session event
  -> account reading in usage.json -> placement / waiting-start retry
```

Claude's session settings install a status-line command and Stop/StopFailure hooks (`machine/adapters/claude.js:17-22`). The status line displays five-hour use and, at most once per minute per session, passes rate-limit payloads to `hook-post.js` (`machine/lib/statusline.js:10-21`). Claude maps five-hour and seven-day percentages to windows with a current timestamp; StopFailure maps a rate-limit error to `limit-hit` (`machine/adapters/claude.js:28-29`). Codex's configured notify calls `hook.sh` at turn end; its adapter identifies the session rollout, reads complete appended lines since its offset and takes the last rate-limit reading, mapping 300 and 10080 minutes to five-hour and weekly windows (`machine/adapters/codex.js:12-36`; `machine/hook.sh:16-30`).

The hook helper translates payloads and posts with the session token; on failure it atomically spools the raw event locally (`machine/lib/hook-post.js:10-30`). The machine attaches the managed session's account, saves its last reading, and forwards a usage or turn-ended event; a reached Codex limit or Claude limit-hit derives its hold from the reading (`machine/service.js:796-825`; `machine/lib/limits.js:1`). Prepared events also enter the durable spool: it drains in filename order to the hub, removes acknowledged items, rejects 4xx, and retries after failures (`machine/service.js:508-511,739-793,1137-1139`; `machine/API.md:35-39`).

The hub resolves the thread and session, deduplicates deliveries, records readings with the thread's machine, and on a future limit records a hold against the session account (`viewer/app/sessions.js:360-378`). `usage.json` is serialized per file and keyed by account ID, not machine; only a strictly newer `at` replaces a reading, retaining an unexpired prior hold if the new reading omits it (`viewer/app/usage.js:39-45`). `effective()` treats a passed reset as zero used without changing the stored reading (`viewer/app/usage.js:10-17`). A nonduplicate event carrying a reading triggers waiting-start retry after the thread lock is released (`viewer/app/hub.js:121`; `viewer/app/sessions.js:603-610`).

Settings own account IDs, provider, plan, weight and pause state; defaults are restored when missing (`viewer/app/settings.js:24-27,171-181,220-234`). A non-default login and session use `~/.wheelchair/accounts/<id>` on the target machine; the service validates the path, seeds metadata and passes it as `CLAUDE_CONFIG_DIR` or `CODEX_HOME`; default accounts use each CLI's usual environment or `~/.claude` / `~/.codex` (`viewer/app/sessions.js:190-202`; `machine/service.js:47-54,484-490,903-911`; `machine/adapters/claude.js:5-6,30-31`; `machine/adapters/codex.js:5-6,37-38`; `machine/adapters/common.js:9-17`). Codex seed sets file credential storage only if config is absent; the repo's fixture places `auth.json` in the account dir and prior research identifies it as Codex's auth file (`machine/adapters/common.js:13`; `machine/test/service.test.js:896`; `docs/plans/app-accounts/PLAN.md:613-615`). The code does not locate or read a Claude OAuth credentials file; its exact location and token format were not verified (`machine/adapters/claude.js:28-31`).

`GET /v1/status` checks the two default logins and scans account directories with valid `wheelchair-account.json`, running the appropriate CLI's login-status command per folder (`machine/service.js:937-948,1047`; `machine/adapters/claude.js:30`; `machine/adapters/codex.js:37`; `machine/adapters/common.js:16`). The hub calls machine routes through `hub.call`, using the configured machine address and machine-secret header (`viewer/app/hub.js:108-111`; `viewer/app/machine-client.js:53-77`; `machine/API.md:28`).

Placement counts sessions with `s.live && s.account === account.id` across all threads, without a machine filter; the session account is assigned on selection, while waiting starts are live without an account (`viewer/app/balancer.js:60`; `viewer/app/sessions.js:129-135,190-194`). `pollDead` checks nonarchived threads against machine session lists and rechecks missing sessions under the thread lock before marking them ended (`viewer/app/sessions.js:537-579`). It runs every ten seconds with overlap suppression; other hub intervals pump asides every two seconds, retry queues and quiet checks, and retry waiting starts/release limits every minute (`viewer/app/hub.js:54-65,126-129`). The machine has readiness and trust timers (2 s and 500 ms), spool retry (default 5 s), and sudo polling (default 2 s) (`machine/service.js:175,282-286,1137-1142`).

A delayed poll and a live reading can race: the storage queue serializes writes, but the later timestamp wins for the entire account record, including both windows, regardless of machine or source; equal timestamps lose and a newer partial reading can replace a fuller one (`viewer/app/usage.js:39-45`). A delayed raw Claude spool payload receives its timestamp when parsed, not when originally emitted (`machine/lib/hook-post.js:25-30`; `machine/service.js:773-779,812-817`; `machine/adapters/claude.js:29`). The old D9 says unknown usage is treated as full, but current `hasRoom` admits missing windows; this is a code/decision mismatch (`docs/plans/app-accounts/PLAN.md:38`; `viewer/app/usage.js:19-22`).

Tests: `viewer/test/app-usage.test.js:97-141,245-263` covers room, ranking, serialization and holds; `viewer/test/app-balancer.test.js:131-184` covers both reading event types promoting waits; `machine/test/accounts.test.js:18-46,71-73` covers adapters and offline status-line spool; `machine/test/service.test.js:896` has an account-folder fixture. The fake machine exposes mutable login accounts, sessions and route responses (`viewer/test/helpers/app-machine.js:25-33,123-128`).
