# R3-1 — Add account browser tests stop racing their settings reload

## Changed files

- `viewer/test/app-harnesses.spec.js` (only file changed; no product code touched)
  - New helper `patchSettings(r, patch)`: fetches the real `GET /api/settings`, patches the body, fulfils. Any failure (including "Test ended while running route callback" or "Response has been disposed") is caught and the route is aborted inside a `catch`, so a late callback cannot throw.
  - New helper `settingsGet(page)`: a `page.waitForResponse` for the page's `GET /api/settings`, registered before the click that sends the POST.
  - Every `page.route('**/api/settings', ...)` that called `r.fetch()` now goes through `patchSettings` (switch-off 409/kimi test, switching-a-harness-off test, moving-a-provider test, `stubAccounts`).
  - `test.afterEach` in each `test.describe(label)` block: `await page.unrouteAll({ behavior: 'ignoreErrors' })`.
  - Both Add account tests (`Add account never hides a switched-off provider…` and `switching off the provider chosen in an open Add account form resets it`) register `settingsGet(page)` before the submit click and `await` it after their existing assertions. No assertion was removed or weakened.
  - `switching off asks first when threads use it, then saves and refreshes`: the `fresh=1` count assertion is now `await expect.poll(...)` instead of a one-shot `expect(...)`. See Choices.

## Choices

- `viewer/test/app-harnesses.spec.js`, switching-off-with-threads test (`switching off asks first when threads use it…`): changed the `fresh=1` refetch count check from a one-shot `expect` to `expect.poll`. The brief did not list this test; it was the one failure seen in the first 10-repeat run, and the change keeps the same assertion.
- `viewer/test/app-harnesses.spec.js`, `patchSettings`: on any failure it calls `r.abort()` (itself wrapped in `.catch`) rather than returning without an action, so the request is never left hanging.
- `viewer/test/app-harnesses.spec.js`, `settingsGet`: waits for any `GET .../api/settings` response after registration, not a specific request. The first matching response after the submit click is taken as the post-POST reload.
- `viewer/test/app-harnesses.spec.js`, `afterEach` placement: added inside each `test.describe(label)` block (phone and desktop), not at file level, so it sits beside the existing `test.use` for each block.
