# T3 — Protocol text

Updated the session start and provider routing guidance in the two owned protocol files. No other files were changed. The remaining tier-setting references to “CLI” describe provider-specific tier settings, not a provider choice; there are no remaining `--cli` options.

## Changed passages

### `protocol/app/lead.md`

Start command.

Before:

> Use `node <root>/viewer/app/wc.js session start --role <role> --cli <claude|codex> --tier top --brief-file <path> --attempt <id>`, and `session stop <name>`, `session list`. The hub checks the rules and refuses anything else with the reason. A refusal is final: change the request rather than resending it.

After:

> Use `node <root>/viewer/app/wc.js session start --role <role> --tier top --brief-file <path> --attempt <id>`, and `session stop <name>`, `session list`. The hub chooses the provider and account. Workers, reviewers and verifiers may pass `--provider <claude|gpt>` or `--not-provider <claude|gpt>`; leads, sub-leads and mappers may not. The hub checks the rules and refuses anything else with the reason. A refusal is final: change the request rather than resending it.

Provider constraints and machine availability.

Before:

> When both CLIs are installed on the machine, start one of the two reviewers and the verifier on the other family from yours; with one family installed, use it for both. A CLI is installed when `command -v claude` or `command -v codex` finds it. The Ready check covers both families' logins; a start for a missing CLI fails at the machine with the reason.

After:

> The hub drops a provider constraint it cannot meet and says so in the start output's `note`. The Ready check covers both families' logins; a start for a missing CLI fails at the machine with the reason.

Project selection.

Before:

> Collin picks the project, the CLI and the machine, then writes in plain words.

After:

> Collin picks the project and the machine, then writes in plain words.

Small-fix verifier.

Before:

> Start a verifier on that commit with a brief that says what Collin asked for; its `result` names the commit it checked.

After:

> Start a verifier on that commit with `--not-provider <the provider the lead runs on>` from `session list` and a brief that says what Collin asked for; its `result` names the commit it checked.

Plan reviewers.

Before:

> Two reviewer sessions, each fresh, each given only the plan path and repo access, never this conversation; cross-family when both CLIs are installed. Brief them from `<root>/protocol/app/reviewer.md`: one takes the mechanics lens, one the intent lens (with both families, give the intent lens to Claude).

After:

> Two reviewer sessions, each fresh, each given only the plan path and repo access, never this conversation. Start the intent-lens reviewer with `--provider claude` (a preference: it moves to GPT rather than wait). Read the provider from that start's output and start the mechanics-lens reviewer with `--not-provider <that provider>`. If the intent reviewer's start came back `waiting`, start the mechanics reviewer with no provider flag. The hub drops a provider constraint it cannot meet and says so in the start output's `note`. Brief them from `<root>/protocol/app/reviewer.md`: one takes the mechanics lens, one the intent lens.

After-done verifier.

Before:

> Start a verifier on that commit, briefed with the reported problem and the plan's Spec. Its `result` names the commit it checked.

After:

> Start a verifier on that commit with `--not-provider <the provider the lead runs on>` from `session list`, briefed with the reported problem and the plan's Spec. Its `result` names the commit it checked.

Restarting what died.

Before:

> The hub tells the session that started a dead one, as a `message` from the app. As lead you restart a dead sub-lead, mapper or reviewer. A new sub-lead resumes from PLAN.md's Implementation Tasks and the committed `reports/`; a dead verifier you started is started fresh. A dead worker is the sub-lead's to restart. Use a new `--attempt` id for each restart.

After:

> On `[wc:from app] your session <name>'s turn failed: <error>`, that session is still live. Send it a `message` asking it to carry on. Only if it fails again, run `session stop` on it, then replace it by its role's restart rule: a worker uses `--replaces <name>` and a new `--attempt`; a sub-lead resumes from PLAN.md's Implementation Tasks and the committed `reports/`; a reviewer, verifier or mapper starts fresh. Never start a replacement while the failed session is live.

### `protocol/app/sub-lead.md`

Which family.

Before:

> Interface, frontend and other taste-sensitive work goes to Claude when Claude is installed; on a machine with only one family, use it and say so in your progress message. A family that is not logged in holds back only its own tasks; do not reroute them to the other family.

After:

> Start interface, frontend and other taste-sensitive work with `--provider claude`. The hub holds it until Claude has room, including while Claude is signed out on that machine, and sends it elsewhere only when Claude is below its margin. Other work passes no provider flag.

Worker start command.

Before:

> Start a worker with `node <root>/viewer/app/wc.js session start --role worker --cli <claude|codex> --tier <tier> --brief-file <path> --attempt <id>`.

After:

> Start a worker with `node <root>/viewer/app/wc.js session start --role worker --tier <tier> --brief-file <path> --attempt <id> [--provider <claude|gpt> | --not-provider <claude|gpt>]`. The tier is `light`, `standard`, `heavy`, `critical` or `top` (Heavy), for both CLIs.

Turn failure restart rule.

Before:

> A dead worker is restarted on the same brief, in the same worktree and branch, using `--replaces <dead worker's session name>` and a new `--attempt` id. A dead verifier is started fresh.

After:

> On `[wc:from app] your session <name>'s turn failed: <error>`, that session is still live. Send it a `message` asking it to carry on. Only if it fails again, run `session stop` on it, then replace it by its role's restart rule: a worker uses `--replaces <name>` and a new `--attempt`; a sub-lead resumes from Implementation Tasks; a reviewer, verifier or mapper starts fresh. Never start a replacement while the failed session is live.

Verifier routing.

Before:

> Start a verifier (`--role verifier`, top tier, the family opposite the builders' when both CLIs are installed; with both families having built, one verifier per family).

After:

> If every builder ran on one provider, start one top-tier verifier with `--not-provider <that provider>` from `session list`. If both providers built, start one top-tier verifier with `--provider claude` and one top-tier verifier with `--provider gpt`. If the first start's output has a `note` saying its provider was not honoured, start no second verifier. If the second start's output has such a note (it landed on the first verifier's provider), stop the second verifier at once.

Remediation routing.

Before:

> Route to the same family that built the work.

After:

> Route to the same provider that built the work, using `--provider <that provider>` from `session list`.
