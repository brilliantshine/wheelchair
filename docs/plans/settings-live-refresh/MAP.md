# Settings live refresh map

Checked against `9517d3bc06afb8ca3f94c22ee760e8bf5ec48faf` (fetched origin/main and worktree HEAD). Sources: `viewer/pages/{settings.html,settings.js,nav.js,background.js,project-tools.js}`, `viewer/app/{routes,settings,state,background,harnesses,usage,assistant-actions,hub}.js`, and the tests cited below. Existing `docs/maps/settings-page.md`, `assistant-settings-runtime.md`, and `project-tools.md` have changes in covered files since their checked commits; the observations below are rechecked at this commit, not a wholesale revalidation of those maps.

```text
open Settings -> GET settings -> build active category -> paint individual blocks
                 -> usage / harness / diagrams / background / keys fetch separately
browser or assistant write -> settings queue or other store -> local reply / selective reread
future external refresh -> must reconcile each source with drafts, focus and local writes
```

## Page and sources

`settings.html` loads background, nav, project tools and Settings scripts and supplies navigation and panel hosts (`viewer/pages/settings.html:3-22`). The initial GET `/settings` populates `data`; category hosts are built and only named blocks are replaced by `paint`; category changes rebuild the category (`viewer/pages/settings.js:2824-2845,2912-2926`). `data` is a snapshot, not generally polled. All API paths below are under `/wheelchair/api`.

`wcPoller` uses an interval only when visible, calls immediately on becoming visible and resets the interval; `stop()` removes both timer and listener. It neither awaits nor serializes `fn` (`viewer/pages/nav.js:6-15`). Usage runs every 30 seconds only in providers/usage and also immediately on entry; harness unreachable retry is separate (`viewer/pages/settings.js:1776-1785,2410-2453`). Background independently polls every 10 seconds while visible, refreshes on focus/pageshow and uses request and image-load guards (`viewer/pages/background.js:44-85,98-109`).

## Drafts, focus and ordering

- Name and folder drafts start/return to `null`, and input updates them (`viewer/pages/settings.js:70-71,521-570`). Style uses persistent `styleDraft`, preview state, plus DOM-only unadded `pending` Never say input (`viewer/pages/settings.js:64-66,1564-1567,1584-1591,1616-1644`). Tier Other has a DOM-only input (`viewer/pages/settings.js:273-333`). Template `draft` is a clone without a stored baseline; selection, confirmation and full-prompt state are separate (`viewer/pages/settings.js:58-63,1024-1035,1127-1174`).
- Lessons hold role, text edits, removal set, confirmation, history and saving state; `lessonDirty()` compares against current `data`, and is not a template dirty test (`viewer/pages/settings.js:61,1028-1035,1264-1309`). `saveLessons` preserves the editor on error but does not reload/reconcile a 409; `lessonAction` and import do explicitly retain surviving edits and show lost text (`viewer/pages/settings.js:1264-1290,1318-1365,1450-1466`; `viewer/app/routes.js:288-295`).
- Accounts hold `editing`, `adding`, `justAdded`, sign-in card and DOM inputs; `accountsBusy()` covers edit/add and focused inputs/selects/textareas, while refresh also protects a connected waiting sign-in card. It does not cover focused buttons (`viewer/pages/settings.js:1710-1721,1750-1765,1947-2058`). Balancing holds `balDraft` including nested `held_back` across blur; saves selected keys and resets those draft values (`viewer/pages/settings.js:1717,2093-2122`). Harness state includes jobs, selection, pending and polls (`viewer/pages/settings.js:2399-2455`). Project tools has separate state and form/key inputs (`viewer/pages/project-tools.js:126,682-716,1052-1094`). Shared keys have DOM-only secrets; `readKeys` sequences reads but a pending response can replace newly typed fields (`viewer/pages/settings.js:2725-2770`).
- Background visit keeps file, opacity, preview ownership, dirty/pending and generation; its subscription avoids repaint when dirty or pending, but this alone is not a general focus guard (`viewer/pages/settings.js:2243-2284,2315-2388`; `viewer/pages/background.js:90-96`). `swapKeepingFocus` restores only controls with `data-focus` after replacement; general `paint` replaces children and preserves placement rather than all control values or focus (`viewer/pages/settings.js:229-247,2824-2835`).
- Existing ordering is scoped: `modelSaves` tickets saved-cell rereads; `saveInOrder` queues per setting; `leadSaves`, `diagramReads`, `usageAsks`, `reserveReads`, `hz.seq` and shared key sequence protect specific flows (`viewer/pages/settings.js:51-78,169-180,250-271,464-487,650-673,1720-1721,1756-1765,2138-2154,2430-2443,2728-2735`). No single generation covers all GETs and writes. `reload()` and account saves replace all `data`, and lesson import and background commits use raw fetch (`viewer/pages/settings.js:1049-1055,1450-1465,1923-1929,2000-2009,2315-2321`). A deferred old snapshot must not overwrite a later local save, including after the draft clears. Read/stamp ordering around asynchronous `describe` and restart-safe revision identity remain design concerns, not existing guarantees (prior review `docs/plans/assistant-settings/PLAN.md:225-300`).

## Writes and hub state

Browser preference/name/folder/mode/escalation, tiers/orders and model/head-up actions send individual PUT/POSTs, update local slices or reread model data; per-setting queues handle rapid choices (`viewer/pages/settings.js:289-365,464-487,521-622,650-716,854-880`). Templates create/update/delete/toggle then `reload()` and repaint; lesson save/action/import use their paths above; style PUT replaces style and repaints (`viewer/pages/settings.js:1057-1100,1264-1283,1318-1338,1450-1466,1685-1691`). Accounts add/update/delete/restore reread `/settings`, usage and harness status; signin and machine install have separate machine-facing requests (`viewer/pages/settings.js:1811-1901,1923-1932,1969-2009,2064-2066,2460-2515`). Balancing, harness switch, diagram save, shared repo/key saves and background upload/commit each update their own slices or reread (`viewer/pages/settings.js:189-202,2106-2122,2315-2332,2524-2546,2720-2770`). Project tools has its own POST actions and form lifecycle (`viewer/pages/project-tools.js:63,252-347,894-1029,1052-1094`).

Hub routes include lesson import, shared-key read/save/remove forwarded to machines, harness installation, usage seen, Settings harness/accounts/balancing/models/heads-up/preferences/saved-dirs/templates/style/lessons, diagram and background routes (`viewer/app/routes.js:49,73-109,138-152,261-355,373-401,497-555`). Machine sign-in and project-tool actions also affect displayed status (`viewer/app/routes.js:82-109,140-145,565-575`). Assistant `setting` uses the same Settings handler for style, harness, accounts, balancing, models, templates, lessons and allowed preferences; diagram and background have dedicated dispatch, with background revision required for remove (`viewer/app/assistant-actions.js:104-155,23-28`). Other hub writes such as lesson merge and saved directories also affect the snapshot (`viewer/app/routes.js:73-80,497-508`).

`settings.update` normalizes and changes settings within the per-file queue and atomic file write; models additionally live in `codex/model.sh`, and diagram settings are read/written per machine (`viewer/app/settings.js:420-442`; `viewer/app/state.js:238-253`; `viewer/app/routes.js:261-265,350-371`). `/settings` invokes `describe`, which loads settings then concurrently calls `models` and `headsUp` (two `model.sh` subprocesses), projects and all threads; it also computes live template counts and returns lessons/history (`viewer/app/settings.js:437-442,523-532`; `viewer/app/routes.js:265`). Background alone has a persisted, incrementing per-background revision and compares it under the settings queue (`viewer/app/background.js:7-15,63-88`). It is not a global revision for models, machine state, usage, diagram or keys. No general settings revision route/counter is present in this checked route/Hub implementation (`viewer/app/routes.js:261-265,897-898`; `viewer/app/hub.js:19-103`). An in-memory counter starting again on hub restart could collide with a cached value, as the prior review found (`docs/plans/assistant-settings/PLAN.md:282-293`).
