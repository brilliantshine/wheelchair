# T6 — project lead lifecycle

## Built

- `viewer/app/routes.js`: serializes messages under the thread lock, guards the setting inside the lock, and starts a project lead on use while preserving the ordinary-thread refusal.
- `viewer/app/project-lead.js`: stores the first message in a pending non-live lead, starts or restarts the lead, preserves failed queues on the latest lead, stops leads on Off, and retries pending stops on successful machine contact.
- `viewer/app/hub.js`: schedules retry work from successful machine contact without nesting machine calls or thread locks.
- `viewer/test/helpers/app-machine.js`: adds a stop failure switch.
- `viewer/test/project-lead.test.js`: exercises first use, failure and queue order, concurrent sends, restart and turn-end delivery, Off and retry, and ordinary-thread refusal.

No screenshots: this task changes backend lifecycle behavior and names no mockup.

## Validation

The first targeted run failed two test assumptions: immediate delivery removes the first message from the queue, and the new-thread route contacts the machine only when a default folder is configured. Both assertions were corrected. The first viewer run encountered a test-server port collision; its test process remained open, so it was sent SIGTERM after the run stalled. The clean retry passed. Browser and machine suites were excluded by the brief; the installer fixture was also explicitly skipped.

## Choices

- `viewer/app/project-lead.js`: use a pending non-live lead record for the first queued message and reuse it for the initial start; consolidate failed restart queues on the newest ended lead for visibility.
- `viewer/app/project-lead.js` and `viewer/app/hub.js`: schedule machine-contact retries asynchronously and deduplicate them per machine to avoid nested thread locks and reentrant stop calls; a pending machine stop remains marked for a later contact.
